# ClaView A파트 작업 내용 및 진행 결과

## 개요

A파트의 목표는 자연어 질문에 필요한 **통계표를 탐색하고 확정해 B파트로 전달하는 것**이다. 초기에는 사용자가 검색 후보를 선택하는 흐름을 구현했고, 실제 모델 선택 실험에서 확인한 문제를 바탕으로 **A1 후보 탐색 / A2 표 확정** 구조로 발전시켰다. 이후 기존 골든셋으로 평가하고 B 구현을 통합한 뒤 실행·검수용 공유본을 구성했다.

현재는 A1/A2와 사용자 표 확정, B로의 모의 연결까지 동작한다. 기존 22건의 정답은 모두 상위 5개 후보 안에 있지만, 일반 자연어 질문을 자동으로 확정하는 기능은 아직 검증 범위를 넓혀야 한다.

| 현재 핵심 결과 | 확인 내용 |
|---|---|
| A 검색 | 기존22의 정답 후보 포함·Top5 **22/22**, 첫 후보 정답 **11/22** |
| A 자동 채택 | 개선 6단계 평가에서 **0/22**. 기본은 사용자 확정 유지 |
| B 연결 | 지정 B ZIP 반영, 원 질문·확정 표 목록 전달과 저장·복구 모의 시험 |
| 공유본 검수 | 별도 환경 설치 후 **516개 시험 통과, 2개 skip** |

아래는 작업을 진행한 순서다. 초기 검색 구현·실측과 후속 A1/A2 개선 6단계를 구분했다.

## 1. A의 책임과 공통 입출력 정리

먼저 A와 B의 책임을 구분했다. A는 필요한 **표**를 선택하고, B는 선택한 표 안에서 실제 조회할 **항목·분류·기간·주기**를 확정한다. A도 표의 적합성을 판단하는 범위에서는 기간·주기를 검사할 수 있다.

공통 계약은 원 질문 보존과 기존 `A.tables` 유지로 정했다. 검색용 표현·구조화 정보·사용자 추가 답변으로 원 질문을 덮어쓰지 않으며, A 내부 처리 필드를 팀 공통 스키마의 필수 확장으로 요구하지 않는다.

```json
{
  "tables": [
    {
      "org_id": "301",
      "table_id": "DT_401Y018",
      "table_name": "수입물가지수(용도별)"
    }
  ]
}
```

한 표 안의 여러 항목·계열과 여러 표를 구분하도록 기준도 정리했다. 질문에 지표가 여러 개 있다고 해서 표도 같은 개수만큼 선택하는 방식은 사용하지 않는다.

## 2. 공식 자료 기반 검색과 사용자 확정 구현

공식 349개 표의 표명·ID·계층 경로·depth와 저장 메타를 검색 자료로 구성했다. 표명만으로 부족한 경우 항목·분류·주석·수록 정보를 함께 활용한다. 표 목록의 계층과 표 내부 항목의 계층은 구분한다.

검색은 기존 `SearchIndex`를 사용하고, `TableDiscovery`에서 후보 검색·조건 검사·표시 순위·사용자 확정을 연결했다. 후보와 확정 상태는 `CandidateStore`에 저장해 재시작·중복 확정·B 재시도를 처리하도록 했다.

**초기 실행 흐름**

원 질문 → 후보 검색 → 조건 검사·순위 정렬 → 사용자에게 후보 표시 → 공식 ID로 표 확정 → A.tables 반환

한 페이지에 표시하는 5개는 후보의 표시 개수다. 최종 표를 반드시 5개 선택한다는 뜻은 아니며, 한 개 또는 필요한 여러 표를 확정할 수 있다.

용어 사전 적용 코드도 연결했다. 다만 운영 사전 79건은 모두 draft이고 승인된 매핑은 0건이므로, 사전 기능 구현과 검수된 사전의 운영 적용을 구분했다.

## 4. A1/A2 구조로 개선 — 1~4단계

실패 원인을 바탕으로 후보 탐색과 표 확정을 분리했다. 기존 검색기·저장소·모델 런타임을 재사용하며 두 서브그래프를 실제 실행 경로에 연결했다.

**목표 흐름**

원 질문 보존 → A1 조건 정리·원문/보조 검색 → 후보군 → A2 공식 근거 대조·필요한 표 집합 판단 → 자동 채택 또는 사용자 확인 → 확정 A.tables

| 개선 단계 | 적용한 내용 | 결과·제한 |
|---|---|---|
| 1단계: 환경·경계 정리 | `.env` 환경변수 기반 실행, 기존 비교 기록 정리, A1/A2 책임과 내부 계약 정리 | 실제 키 비노출 기준 유지. A.tables 변경 없음 |
| 2단계: A1 질문 조건·검색 | 규칙으로 조건을 정리하고 원문 근거·위치·적용 대상을 기록. 원문 검색을 유지하며 검증된 보조 표현을 별도 활용 | 원문에 없는 명목·실질 등의 조건이나 표 개수를 임의 확정하지 않음 |
| 3단계: A2 공식 근거 대조 | 필수 요구와 후보를 연결하고 충족·충돌·미확인으로 구분. 공식 출처·인용·자료 판본 기록 | 단어 관련성만으로 요청 통계를 제공한다고 판정하지 않음. 메타 부족과 API 미지원도 구분 |
| 4단계: 표 집합·사용자 확인 | 모든 필수 요구와 추가 표의 필요성 검사. shadow/auto 분리, 확인 답변 저장·재판단·기존 확정 경로 연결 | 일반 질문은 기본 사용자 확정. 제한된 공식 명칭 요구만 auto 기능 시험 |

사전은 79건을 일괄 승인하지 않았다. 공식 문자열로 확인한 10건을 별도 실험 판본으로 구성했고, 사람의 의미 검수가 완료된 것처럼 표시하지 않았다.

A2에서는 한 표의 복수 계열, 실제 다중 표, 대안·중복 표, 일부 요구만 충족하는 경우를 별도 기능 시험했다. 사용자 답변은 원문과 분리해 저장하고, 후보가 유지되면 A2에서 재판단하며 검색 요구가 바뀔 때만 A1을 다시 실행하도록 했다.

## 5. 선택적 질문 해석 모델 연결 — 5단계

모델이 항상 최종 표를 고르는 대신, 규칙·사전으로 해결되지 않는 질문 해석을 보완하는 역할부터 독립적으로 실험했다.

`QueryInterpreter`와 기존 provider·호출 예산·캐시를 재사용하고, HCX-007로 허용된 7건을 실행했다. 모델 출력의 인용과 원문 위치, 조건 변경을 검증한 뒤 유효한 결과만 보조 검색에 반영하도록 했다.

| 항목 | 실제 결과 |
|---|---:|
| 요청 / 재시도 | 7회 / 0회 |
| 입력 / 출력 토큰 | 4,519 / 1,514 |
| 유효 해석 적용 | 0/7 |
| 실패 처리 | 원문 인용·위치 검증 실패 → 원문 검색으로 복귀 |
| EvidenceJudge | 실제 호출하지 않음 |

응답을 받은 사실과 해석이 정상 적용된 사실을 구분했다. 적용 성공이 없었으므로 모델을 기본 활성화하지 않았다. 이 7건은 앞의 **기존 자동 선택 7건과 다른 역할의 실험**이며, 서로 다른 입력·출력을 사용해 토큰이나 품질을 단순 비교할 수 없다.

## 6. 기존22로 기능별 통합 평가 — 6단계

규칙 구조화, 실험 사전, 공식 근거 대조, 표 집합 판단의 효과를 구분하기 위해 여섯 설정을 비교했다. 모델은 5단계 결과에 따라 off로 유지했고, 이 단계의 실제 모델 호출은 0회였다.

| 비교 설정 | 확인하려던 효과 | 기존22 결과 |
|---|---|---|
| baseline | 기존 검색 기준 | Top5 22/22, Top1 11/22 |
| rules | 규칙 조건 정리 | 정답 포함·순위 유지 |
| dictionary_experiment | 출처 확인 사전 추가 | 일부 후보 추가, 정답 순위 개선 없음 |
| evidence | 공식 근거 대조 | 근거·충돌·미확인 기록, 정답 순위 유지 |
| shadow | 표 집합 판단만 기록 | 사용자 확정 유지 |
| auto | 제한된 자동 채택 실행 | 자동 채택 0/22 |

자동 채택이 0건인 주된 이유는 현재 정책이 일반 질문 전체의 의미를 공식 근거로 확인하지 못했기 때문이다. 모든 질문 자체가 모호하다거나 검색에 실패했다는 뜻은 아니다. 현재 A2 근거 대조 결과는 표시 순위를 직접 개선하는 데까지 연결된 상태도 아니다.

실제 사용자 답변을 대신 입력해 성공을 만들지 않았다. 미확정 사례의 최종 표 집합 정확도와 사용자 확인 후 성공률은 미확인으로 남겼다. 후속 개선 7·8단계는 진행하지 않고 결과 정리로 전환했다.

**이 단계 이후 기본 구성**

`baseline/legacy 검색 · mapping=approved · 규칙 조건 정리 · 공식 근거 대조 · shadow · 모델 off`

구현·기록·복구 경로는 갖췄지만, 기존22에서 검색 순위나 일반 자연어 자동 선택 정확도가 개선됐다고 판단할 근거는 확보하지 못했다.

## 7. 저장소 정리와 B 구현 통합

실행에 필요한 코드·현재 문서와 과거 실험·보관 자료를 구분했다. 실행 저장소에는 현재 A1/A2와 의존 기능을 남기고, 연결 여부를 검토한 뒤 오래된 자료와 사용하지 않는 구현을 정리했다.

이후 전달받은 `claview_B_검증_기간증강_20261002.zip`을 B 기준으로 통합했다. ZIP에 함께 들어 있던 이전 A가 현재 A1/A2를 덮어쓰지 않도록 파일 책임을 분리했다.

| 구분 | 현재 담당 |
|---|---|
| A1/A2 | `a1_*.py`, `a2_*.py`, `a_discovery.py` |
| A 그래프 | `a_graphs.py` |
| 기존 A 모델 선택 경로 | `a_stages.py` |
| B 조회 조건 | `stages.py` |
| B 그래프·전체 파이프라인 | `graphs.py` |
| A/B 공통 의존성 | `services.py` |

A 쪽에서는 원 질문·확정 A.tables 인계를 유지하고 B의 확인 대기를 저장·표시하도록 연결했다. 확인 대기를 일반 실패와 구분하며 재시작 시 같은 안내를 재사용한다. 확인 없이 조회로 진행하거나 retry를 동의로 처리하지 않는다.

B의 기간·항목 선택 기능 자체는 전달받은 구현을 사용했다. B22 모의 재생 결과는 조건 일치14건·기간 확인 대기8건이다. 이 수치는 실제 B 모델 정확도나 전체 조회 성공률이 아니다. **기간 확인 답변 후 B를 재개하는 기능은 아직 없다.**

B의 반기 메타 지원 반영으로 분기 질문에서 반기 전용 후보 1개가 제외돼 후보 총수는 246→245가 됐다. 기존22의 정답 순위는 모두 유지됐다.

## 현재 완료 범위와 다음 작업

| 완료·확인한 범위 | 남은 범위 |
|---|---|
| 공식 자료 기반 후보 검색, A1/A2 연결 | 첫 후보 정답률 개선 |
| 원문·조건·보조 검색 분리 | 일반 자연어 의미 해석과 공식 근거 연결 보완 |
| 사용자 확정·저장·재시작·B 재시도 | 일반 자연어의 필요한 표 집합 자동 채택 |
| 제한된 자동 채택·다중 표·모호성 기능 시험 | 검수된 다중 표 골든셋을 통한 성능 평가 |
| 실제 HCX 호출과 실패 시 원문 복귀 | 원문 근거 검증을 통과하는 모델 해석과 효과 검증 |
| B 코드 통합·모의 인계·확인 대기 보존 | B 확인 답변 후 재개, 실제 모델 선택·통계 데이터 조회 검증 |

다음 연결 검증은 명시 기간 질문부터 A에서 표를 확정하고 B의 조회 조건·실제 데이터를 대조하는 순서가 적절하다. A 개선은 첫 후보 오답 원인, 질문 해석 검증, 필요한 표 집합 판단을 각각 분리해 비교한다. 임베딩·리랭커·JEV는 남은 실패 유형을 기준으로 이후 실험하며 현재 효과가 확인된 기능으로 소개하지 않는다.

## 평가 자료 사용 원칙

- 기존22를 현재 평가 기준으로 사용하되 모두 단일 표 정답이라는 한계를 유지한다.
- 임의 추가한 A48건과 B 기간 시험13건은 기능 시험 자료이며 실제 성능 지표에 합산하지 않는다.
- 이후 별도 증강·정답 검수를 마친 자료를 평가에 추가한다.
- 검색 후보 포함, 최종 표 확정, 사용자 확인 완료, B 조회 성공을 서로 다른 지표로 보고한다.
