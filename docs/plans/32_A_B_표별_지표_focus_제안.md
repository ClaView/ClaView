# 32. A→B 표 목록에 표별 지표(`focus`) 추가 제안

> 2026-10-27: 모듈 구조(`modules/`·`pipeline/`)로 옮기면서 본문의 파일 경로를 지금 위치로 고쳤다. 3절의 실제 시험 결과는 작업 당시(옛 구조)의 결과다.


- 상태: 제안(A 담당 협의 전). B 쪽 수신 코드와 시험은 하위 호환으로 반영됨.
- 작성일: 2026-10-26
- 관련: [A→B 표 목록 계약](../contracts/A_to_B_표목록.md), [31. B·C 고도화](31_B_C_고도화_복수표_이중축.md), [다중표·이중 축 시험 가이드](../guides/다중표_이중축_시험_가이드.md)

## 1. 제안 요약

- A가 B에 표를 넘길 때 표마다 "이 표를 고른 이유가 된 질문의 지표"를 선택 필드 `focus`로 함께 넘긴다.
- 예: 질문이 "경상수지와 실질 GDP 성장률"이면 국제수지 표에 `focus: "경상수지"`, 주요지표 표에 `focus: "실질 GDP 성장률"`.
- 필드는 선택이다. 없으면 B는 지금과 똑같이 동작한다.

## 2. 문제

- 지금 B는 원질문과 표 목록(`org_id`, `table_id`, `table_name`)만 받는다. 표마다 B 호출이 한 번씩 일어나고 각 호출이 질문 전체를 본다.
- 지표가 둘인 질문에서 B의 모델(HCX)이 각 표에서 두 지표를 모두 채우려 한다. 그 표에 없는 지표는 이름이 비슷한 다른 항목으로 대신 고르거나 같은 행을 반복한다.
- 실제 HCX 시험(골든셋 v3, 표 2개·지표 2개 질문 5건)에서 관찰한 예:
  - 대출금리 표에서 "정기예금 금리" 몫으로 "예·적금담보대출"을, 수신금리 표에서 "주택담보대출 금리" 몫으로 "주택부금"을 선택.
  - 국제수지 표에서 "GDP 성장률" 몫으로 본원소득수지를, GDP 표에서 "경상수지" 몫으로 명목 원화표시 GDP를 선택.
  - 같은 행을 두 번 돌려주어 `duplicate_selection`으로 B가 중단.
- 영향: 계열이 의도보다 늘고, 단위가 세 가지가 되면 이중 축을 그리지 못하고 선그래프로 내려간다(CV-BC-01 실측).

## 3. 근거: 실험 결과

같은 5건·같은 HCX 모델로 네 가지 조건을 비교함. `focus`는 시험 도구가 골든 통계표의 `indicator`(질문에 나온 지표 문구)를 넘긴 값임. "규칙"은 통계표가 여럿일 때 B 프롬프트에 붙는 규칙(지표를 가장 알맞은 표에서만 고르고 비슷한 항목으로 대신하지 않음)임.

| 사례 | ① `focus` 없음, 규칙 있음 | ② `focus`+규칙(감싸개 방식) | ③ `focus`+규칙(실제 필드) | ④ `focus`만(규칙 끔) |
|---|---|---|---|---|
| CV-BC-01 경상수지 · 실질 GDP 성장률 | 추가 2개 | 통과 | 추가 1개(GDP 디플레이터) | 추가 1개(명목 원화표시) |
| CV-BC-02 계절조정 경상수지 · 실질 GDP 성장률 | 추가 2개 | 불일치(GDP 변형 차이, 추가 1개) | 불일치(GDP 변형 차이, 추가 1개) | 불일치(GDP 변형 차이) |
| CV-BC-03 신용카드 이용금액(두 통계표) | 추가 1개 | 통과 | 통과 | 추가 1개(개인 이용금액) |
| CV-BC-04 가계신용 · 순대외금융자산 | 추가 2개 | 통과 | 통과 | 통과 |
| CV-BC-05 주택담보대출 금리 · 정기예금 금리 | 추가 3개 | 추가 1개(주택부금) | 추가 1개(주택부금) | 추가 1개(주택부금) |
| 골든과 일치한 건수 | 0 | 3 | 2 | 1 |

- 표의 "추가 N개"는 골든 계열을 모두 포함하고 B가 N개를 더 고른 경우임. 기준 실행(①)에서 `focus` 없이는 추가 행이 매번 이름이 비슷한 다른 표 몫의 항목이었음(예: 대출금리 표에서 "정기예금" 몫으로 "예·적금담보대출", 수신금리 표에서 "주택담보대출" 몫으로 "주택부금").
- `focus`를 주면 추가 계열이 사례당 0~1개로 줄었음. 규칙은 CV-BC-03에서만 차이를 냈음(규칙이 있으면 통과, 없으면 "개인 이용금액"이 추가됨). 규칙을 빼서 좋아진 사례는 없었음. 따라서 규칙은 유지함.
- CV-BC-02의 불일치는 질문 모호성(전년동기비·전기비)이며 골든을 모델이 일관되게 고른 "실질 계절조정 전기비"로 바꿔 정리함. 변경 뒤 재실행은 하지 않았음.
- CV-BC-05의 주택부금은 `focus`·규칙과 무관하게 남았음(네 번 모두).
- HCX 출력은 실행마다 조금씩 달라(②와 ③의 CV-BC-01) 한 번의 결과로 결론 내리지 않음. 사례당 실행 횟수가 적으므로 효과의 크기보다 방향을 근거로 삼음.
- 추가 계열 하나로 단위가 세 종류가 되면(CV-BC-01) 이중 축을 그리지 못하고 계열마다 카드가 나뉨. 과다 선택이 화면까지 영향을 줌.

## 4. 변경 내용

### 4.1 계약

`a_result.tables[]` 항목에 선택 필드를 하나 추가한다.

```text
{"org_id", "table_id", "table_name", "focus"?: <문자열>}
```

- `focus`: 질문의 지표 문구. 비어 있지 않은 문자열이며 100자 이내.
- 한 표가 요구 여럿을 맡으면 지표를 ` / `로 이어 한 값으로 둔다(예: "경상수지 / 서비스수지").
- 이 외의 필드는 기존처럼 허용하지 않는다. `focus`가 없는 요청은 기존과 같다.

### 4.2 A 쪽 작업

- 표를 B로 넘기는 payload의 `selections[].tables[]` 항목에 `focus`를 싣는다. 근거: A의 요구에는 질문 속 지표 문구가 이미 있다(`analysis.interpretation.requirements[].quote`, `.indicator`).
- 같은 표가 여러 요구에 걸리면 `to_table_request`가 지표를 합치므로(4.3) A는 요구별 값을 그대로 싣는다.
- 모듈 구조에서 화면 경로(`pipeline/claview_pipeline/staged.py`)는 A 포트가 아니라 A 서비스(`modules/a/claview_a_api/service.py`의 `select`/`answer`)가 만든 표 목록을 B 서비스(`BService.resolve`)에 넘긴다. 이 표 목록과 공용 계약 `TableRef`(`common/claview_common/contracts/a.py`)는 지금 세 필드만 담으므로, 화면 경로에서 `focus`가 B까지 가려면 두 곳도 함께 바꿔야 한다(계약 변경 규칙: 계약·fixtures·쓰는 모듈 시험을 함께). 포트(`b_port.py`)는 CLI·골든 22 평가가 쓰는 옛 경로다.

### 4.3 B 쪽 반영(완료, 하위 호환)

- `pipeline/claview_pipeline/b_port.py`: 표 항목에 `focus`가 있으면 요청에 싣고, 같은 표가 여러 요구에서 오면 지표를 중복 없이 합친다. `check_table_request`는 `focus`가 문자열이 아니거나 비어 있으면 `table_focus`로 막는다.
- `modules/b/claview_b/stages.py`: `focus`가 있는 표의 호출에만 입력 `table_focus`와 시스템 프롬프트 한 문장을 더한다. 모델이 보는 표 목록(`selected_tables`)은 이전과 같은 세 필드를 유지한다. `focus`가 유효하지 않으면 `invalid_a_result`.
- `focus`가 없는 호출의 입력과 프롬프트는 이전과 글자 하나 다르지 않다(시험으로 고정).

## 5. 위험과 미결 사항

- `focus`가 질문과 어긋나게 들어오면(A의 지표 해석 오류) B가 그 표에서 잘못된 지표를 고를 수 있다. B는 `focus`를 정답으로 신뢰하므로 A의 지표 문구 정확도가 중요하다.
- A는 관계로 묶인 요구만 B에 한 번에 보내고 독립 요구는 요구별로 호출한다(`b_connection.connect`). 독립 요구마다 표 1개와 질문 전체로 호출될 때도 같은 현상이 나는지는 이번 시험으로 확인하지 못했다. `focus`는 이 경우에도 도움이 될 것으로 보이나 별도 확인이 필요하다.
- 시험은 표 2개·지표 2개 질문 5건이다. 표 3개 이상, 한 표에서 지표 여러 개를 고르는 질문은 아직 시험하지 않았다.
- B 프롬프트의 "통계표가 여럿일 때" 규칙은 `focus`와 겹치지만, 규칙을 끈 비교(3절 ④)에서 CV-BC-03이 다시 나빠져 유지했다. `focus`가 안정적으로 오면 다시 비교한다.
- `focus`를 주어도 사례당 0~1개의 추가 계열이 남는다(CV-BC-05의 주택부금 등). `focus`와 이름이 겹치지 않는 행을 B가 거르는 방안은 정당한 행을 지울 위험이 있어 적용하지 않았다. A가 `focus`를 실제로 넘기기 시작한 뒤 필요성을 다시 본다.

## 6. 합의가 필요한 항목(A 담당)

1. 필드 이름과 형식(`focus`, 문자열, 100자 이내, 여러 지표는 ` / `).
2. 값의 출처(요구의 `indicator.name` 또는 `quote` 중 무엇을 쓸지).
3. 관계 없는 독립 요구를 B에 따로 보내는 현재 방식 유지 여부.
4. 계약 판본(`TABLE_LIST_CONTRACT`) 갱신 시점. B 쪽은 선택 필드라 먼저 반영되어도 호환된다.

## 7. 확인 방법

- B 자동 시험: `modules/b/tests/b_part/test_b_hierarchy.py`(`focus` 전달·무시·거절), `pipeline/tests/test_table_focus.py`(포트 요청 형식·합치기·검사).
- 골든셋 v3 시험: `python -B -X utf8 pipeline/scripts/golden_replay.py check --mode hcx --allow-external --hcx-retries 2 --table-focus`(PYTHONPATH는 [시험 가이드](../guides/다중표_이중축_시험_가이드.md) 3-2절). 시험 도구는 골든 표의 `indicator`를 `focus`로 넘긴다. 이 옵션 없이 돌린 결과와 비교한다. `--no-multi-table-prompt`는 B의 "통계표가 여럿일 때" 규칙을 끄고 실행한다. 모델 입력은 `pipeline/scripts/golden_inspect.py --request`로 확인한다([시험 가이드 3-6](../guides/다중표_이중축_시험_가이드.md)).
- A가 실제로 `focus`를 넘기기 시작하면 같은 5건과 표 3개 이상 질문을 A 실제 경로로 확인한다.
