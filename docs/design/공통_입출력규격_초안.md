# 공통 입출력 규격 초안

- 관리: 팀 공동 / 정리일: 2026-09-23
- 상태: 2026-09-23 노션 공통 규격과 골든셋 초안을 대조한 논리 계약 초안. 실행용 모델·JSON Schema·MCP 도구 명세는 아직 구현하지 않았습니다.
- 기준: [README 처리 원칙](../../README.md), [연결 구조](처리흐름과_연결구조.md), [조회 검증](../guides/KOSIS_조회조건과_검증절차.md)
- 아래 필드·상태 이름은 제안입니다. 기존 문서의 v1 표기를 새 저장소의 확정 계약 버전으로 승계하지 않습니다.

## 1. 공통으로 지킬 내용

- 원 질문부터 결과까지 요청 식별자로 추적합니다.
- 현재 상태는 갱신하되, 이전 선택·도구 실행·오류 이력은 별도로 보존합니다.
- 원자료 DT 문자열·결측 표시와 해석한 숫자, 가공값을 구분합니다.
- 한 표의 여러 계열과 여러 표를 모두 표현할 수 있도록 계열별 선택을 관리합니다.
- 실제 요청 조건·출처·가공 기록을 결과와 평가에 연결합니다.
- 조건 확인·부분 결과·실패도 명시적으로 표현합니다.

## 2. 단계별 정보 묶음

| 묶음 | 최소 정보 후보 | 채우는 주체 |
| --- | --- | --- |
| 요청 | request_id, 원 질문, 조건 버전, 대화 참조 | 에이전트 진입 |
| 해석 | 지표·대상·기간·주기·비교 의도, 확정/미확정 조건, 적용 기본값 | 에이전트 |
| 검색 | 후보 목록, 순위, 점수와 산정 방식, 일치 근거, 메타 버전 | 검색 |
| 확인 질문 | 질문 ID, 필요한 조건, 실제 후보에 연결된 선택지, 사용자 답변 | 에이전트 |
| 조회 계획 | selections 배열, 계열 ID, 기관·표·항목·분류 코드, 기간·주기 | 에이전트·조회 검증 |
| 조회 결과 | 실제 요청 조건, 원 응답 참조, 계열별 관측값·상태, 조회 시각 | 통계 조회 |
| 가공 결과 | 입력 계열·관측값 참조, 규칙·설정·출력·단위·제외 내역 | 정합·계산 |
| 표시·설명 | 표/차트 참조, 설명, 출처, 경고, 가능한 다음 행동 | 시각화·에이전트 |
| 추적·오류 | 단계별 결과·오류 코드·재시도 가능 여부·측정값 | 각 기능 |

계열 ID는 표 ID만으로 만들지 않습니다. 같은 표의 다른 항목·분류·기준을 구분해야 합니다. 기간을 포함한 요청 식별과 통계 계열 식별의 세부 방식은 구현 시 정합니다.

### 2.1 노션 초안과의 대응

아래는 이름 변환과 보완 방향이며 실행용 스키마가 아닙니다. 필드 이름은 최소 모델을 구현할 때 하나로 확정합니다.

| 노션의 필드 | 이 문서의 대응 | 보완 이유 |
| --- | --- | --- |
| query_id | request_id | 요청 연결 키라는 역할은 동일. 두 이름을 중복 필수로 두지 않음 |
| raw_query, interpreted | 원 질문·해석·조건 버전 | 후속 답변과 해석 변경을 원 질문 덮어쓰기 없이 기록 |
| candidates[].tblId | 후보의 기관·표 ID와 선택 조건 | 표 적중만으로 세부 계열 선택 완료를 판단하지 않음 |
| selection | selections 배열 | 단일 표 복수 계열과 여러 표 비교를 모두 표현 |
| data[].raw, value | 원 관측값·해석값·가공값 | 원 DT 문자열 보존과 숫자 변환·계산을 분리 |
| status, messages | 단계별 상태·최종 상태·안내 | 검색 성공 뒤 조회 실패처럼 서로 다른 결과를 보존 |
| provenance | 계열·관측값·가공 결과에 연결된 근거 | 여러 표의 출처가 섞이거나 일부 근거가 유실되는 것을 방지 |

### 2.2 요청 상태와 실행 기록

한 요청에는 현재 상태 요약과 단계별 실행 기록을 둡니다. 모든 기능이 거대한 객체 하나를 직접 수정하기보다 필요한 입력을 받고 결과를 반환하고, 에이전트가 기록을 연결하는 방식을 제안합니다.

- 요청 연결: `request_id`, 대화 턴 식별, `condition_revision`.
- 단계 기록: 단계·호출 식별자, 입력/출력 참조, 조건 버전, 상태·오류, 실행 시각, 사용한 메타·매핑·색인 버전.
- 재시도: 같은 조건의 재시도는 시도 기록을 추가하고, 조건이 바뀌면 새 조건 버전을 부여.
- 평가 연결: 평가 실행 ID·사례 ID를 요청 기록과 연결. 일반 사용자 요청에 골든셋 ID를 요구하지 않음.

최종 출력에는 현재 조건 버전의 결과만 사용합니다. 이전 결과를 재사용하려면 선택 조건·자료 버전의 호환성을 확인하고 재사용 여부를 기록합니다. 전체 실행 기록이나 내부 오류 원문을 사용자·외부 MCP 클라이언트에 그대로 노출하지 않습니다.

## 3. 조회 계획 예시

### 검색 자료에서 받을 정보와 변환 경계

| 확보한 JSON 필드 | 공통 규격에 연결할 정보 | 자동 변환하지 않을 부분 |
| --- | --- | --- |
| doc_id, org_id, table_id | 검색 후보·근거 문서 식별 | 표 ID만으로 계열 ID를 확정하지 않음 |
| official_observations, provenance | 관찰 근거·원문·확인일 | 화면의 period_display와 일부 분류명을 전체 조회 조건으로 사용하지 않음 |
| team_search_document, selection_axes | 후보 설명과 확인할 조건 후보 | 팀 설명을 공식 원문·검수된 정의로 표시하지 않음 |
| mapping_id, relation, condition, scope | 적용한 표현·규칙·문맥·검수 상태 | scope/source의 표를 무조건 조회 대상 표로 선택하지 않음 |
| api_binding | 실제 메타 코드와 연결할 자리 | 현재 null인 항목·분류 코드를 LLM으로 만들어 채우지 않음 |
| readiness | 자료 준비 상태 | table_search=true를 검색 실행 성공으로 해석하지 않음 |

현재 상세 문서 16건의 항목·분류 코드는 비어 있고 API 검증은 false입니다. 이 자료에서 후보·관찰 근거까지 연결할 수 있지만, 유효한 `selections`를 자동으로 만들 수 있는 상태는 아닙니다. 실제 코드·조합·주기별 기간 확인을 거쳐야 합니다.

검색 후보의 근거에는 문서·매핑 ID와 버전, 의미 검수 상태를 남깁니다. 원본 파일의 `schema_version: 1.0`은 자료 형식 버전이며 공통 입출력 계약 확정 버전이 아닙니다. 상세 내용은 [검색 문서 연결 순서](../guides/검색문서_구성과_색인준비.md#7-받은-문서를-검색조회에-연결하는-순서)를 참조합니다.

### 복수 계열 조회 계획

다음은 과거 조회 조건을 이용한 **형식 예시**입니다. 현재 API 유효성·수치 조회 성공을 뜻하지 않으며 아래 JSON 자체가 KOSIS 요청 본문도 아닙니다. 어댑터가 실제 API 파라미터로 변환합니다.

```json
{
  "request_id": "example-001",
  "condition_revision": 1,
  "selections": [
    {
      "series_id": "household-new",
      "org_id": "301",
      "table_id": "DT_121Y006",
      "item_ids": ["13103134553999"],
      "classifications": {"1": ["13102134553ACC_ITEM.BECBLA03"]},
      "period": {"frequency": "M", "start": "202308", "end": "202607"}
    },
    {
      "series_id": "household-stock",
      "org_id": "301",
      "table_id": "DT_121Y015",
      "item_ids": ["13103134612999"],
      "classifications": {"1": ["13102134612ACC_ITEM.BECBLB0202"]},
      "period": {"frequency": "M", "start": "202308", "end": "202607"}
    }
  ]
}
```

조회 전에 ITEM 코드, 분류 축·선택값, 코드 조합, 주기별 수록기간을 확인합니다. 코드가 각각 존재해도 모든 조합이 유효하다는 뜻은 아닙니다. 부모·합계 항목도 확인 없이 금지하지 않습니다. 다중 코드 조회의 묶음 처리 방식은 실제 API 제약을 확인한 뒤 정합니다.

예시의 기간은 과거 조회 조건입니다. 골든셋 CV-G004는 2024년을 요청하므로 이 예시를 그대로 복사하면 기간이 맞지 않습니다. CV-G002는 주택담보대출이므로 가계대출 분류 코드도 재사용하지 않습니다.

초기 논리 계획에서는 선택 1건을 특정 항목·분류 조합의 계열 1개로 관리하는 안을 우선 검토합니다. 위 코드 배열은 각 1개 값입니다. 여러 값을 묶어 호출하도록 확장하면 반환된 조합마다 별도 계열 ID를 붙여야 하며, 하나의 series_id 아래 여러 계열을 섞지 않습니다.

## 4. 원값·가공값 보존

| 구분 | 보존할 내용 |
| --- | --- |
| 원 관측값 | 계열 식별, 시점·주기, 원 DT 문자열, 원 단위, 응답 행 참조 |
| 해석값 | 숫자로 해석한 값, 결측·특수 기호·파싱 상태 |
| 가공값 | 계산 결과, 출력 단위·정밀도, 변환 ID |
| 변환 기록 | 입력 관측값 참조 목록, 수식·규칙·설정, 제외·보간·정렬 내역 |

한 가공값이 여러 원 관측값에서 나올 수 있습니다. 전년동월비처럼 두 시점을 쓰는 계산을 한 개의 raw/value 쌍으로만 표현하지 않습니다.

원 DT 문자열의 정확한 보존과 숫자 동등성은 다른 검사입니다. 표시용 반올림은 원값을 덮어쓰지 않습니다. 큰 자료는 참조로 전달하되 소비자가 실제로 접근할 방법·유효 기간·버전을 정합니다. 외부 클라이언트에 로컬 절대경로만 반환하지 않습니다.

## 5. 결과·오류 구분안

| 상태 후보 | 판정 조건 | 주의 |
| --- | --- | --- |
| ok | 해당 단계의 필수 조건 충족 | 도구 성공과 전체 과업 성공을 구분 |
| needs_clarification | 의미·대상 등 선택에 필요한 정보 부족 | 후보에 근거한 질문을 제공 |
| not_found | 현재 검색에서 적절한 후보를 찾지 못함 | 범위 밖의 증거로 사용하지 않음 |
| out_of_scope | 요청 대상이 지원 범위 밖임을 확인 | 판정 근거와 가능한 대안을 기록 |
| no_data | 메타로 요청 기간의 자료 미수록을 확인하거나, 유효 조회 결과에서 자료 없음을 확인 | 범위 밖·검색 미적중·원인 미확인 빈 응답과 구분. 메타 확인만으로 판정했다면 실제 조회를 수행했다고 기록하지 않음 |
| error | 통신·파싱·검증·가공·시각화 등의 실패 | 단계·원인·재시도 가능 여부를 함께 기록 |
| partial | 요청 일부만 유효하게 완료 | 성공·실패 계열과 빠진 요구사항 표시 |

위 상태값과 도구·에이전트 간 매핑은 합의 대상입니다. 검색 후보를 잘 반환한 도구의 ok와 최종 과업의 ok는 같은 판정이 아닙니다.

기본값 정책, 검색 점수 임계값, 최대 확인 횟수는 아직 정하지 않았습니다. 신규취급액/잔액 등 의미가 바뀌는 조건을 임의 선택하지 않습니다. API 오류와 MCP 전송 계층 오류도 구분해 기록합니다.

### 5.1 판정에 필요한 근거

- 검색 후보가 없거나 점수가 낮음: 검색·색인 상태와 범위를 확인합니다. 그것만으로 `out_of_scope`를 반환하지 않습니다.
- 의미가 다른 후보가 남음: 확인할 조건과 후보 근거를 담아 `needs_clarification`을 반환합니다. 후보 검색은 계속할 수 있지만 수치 조회 조건을 임의 확정하지 않습니다.
- 빈 배열·API의 자료 없음 응답: 요청 코드·조합·기간·응답 의미를 확인합니다. 유효 요청과 자료 부재가 확인될 때 `no_data`로 처리하며, 원인 미확인 응답은 진단 정보를 남깁니다.
- 파싱·인증·입력 오류: 원인과 재시도 가능 여부를 구분합니다. 모든 오류를 일시 장애로 설명하거나 반복 호출하지 않습니다.
- 일부 계열만 성공: 계열별 상태·누락 요구사항을 남깁니다. 부분 제공 허용 정책에 따라 안내하며 요청 전체를 `ok`로 올리지 않습니다.

`stage`, `reason_code`, `retryable` 같은 보조 필드로 원인을 구분하는 안을 검토합니다. 구체적 이름·코드 목록은 미확정이며, 내부 진단과 사용자 안내는 분리합니다.

### 5.2 조건 확인 정보

확인 질문에는 어떤 조건이 비었는지, 각 선택지가 어떤 후보·통계 기준에 연결되는지 남깁니다. 사용자가 자유롭게 답했을 때도 원래 질문의 명시 조건과 합쳐 다시 검증합니다.

| 정보 | 필요한 이유 |
| --- | --- |
| 질문 ID·조건 버전 | 이전 질문의 답을 새 조건에 잘못 적용하지 않기 위해 |
| 미확정 조건·후보별 차이 | 실제 메타 근거로 질문하고 관련 없는 선택지를 만들지 않기 위해 |
| 제안 기본값과 근거, 적용 여부 | 단순 제안과 실제 적용을 구분하기 위해 |
| 사용자 답변·변경된 조건 | 무엇이 확정·수정됐는지 추적하기 위해 |

기간 기본값을 채택하면 '최근'의 기준 시점과 반환 가능 기간도 표시합니다. 월 주기를 지원하는지 확인하지 않고 최근 36개월을 일괄 적용하지 않습니다. 기본값의 적절성은 API 호출 성공만으로 검증되지 않으며 사용 목적과 팀 정책 검토가 필요합니다.

## 6. 근거에 포함할 정보

- 기관·표 ID와 명칭, 선택 항목·분류의 코드와 표시명.
- 실제 키 없는 요청 파라미터, 요청한 기간과 반환된 기간·주기.
- 계열별 단위·통계 기준과 메타 버전.
- 조회 시각과 원 응답 식별자, KOSIS 원표 링크.
- 적용되는 주석·경고·미확인 사항.
- 가공 시 입력 근거와 변환 규칙·설정·손실.
- 수집·조회 시각과 공표·개정·기준 적용 시점은 구분. 모르는 값은 미확인으로 표시.

실제 요청 파라미터는 재현에 필요한 기록입니다. 키를 제거하되 코드를 임의로 생략하지 않습니다. 조회 시각을 데이터의 공표·최신 갱신 시각으로 설명하지 않습니다.

근거는 단계에 맞게 요구합니다. 검색 후보에는 검색 문서·메타 근거를, 실제 자료에는 요청·응답 근거를, 가공값에는 입력과 계산 기록을 붙입니다. 조회하지 않은 확인 질문이나 범위 밖 안내에 조회 시각·수치 출처를 만들어 넣지 않습니다. 단위·기준이 미확인인 자료는 확인된 숫자처럼 비교·가공에 넘기지 않고 미확인 상태와 제한을 전달합니다.

## 7. 평가와 연결

| 평가 | 실행에서 읽을 내용 | 비교할 정답·근거 |
| --- | --- | --- |
| 후보 검색 | 계열별 후보·순위 | 허용 정답 표·계열 집합 |
| 조건 선택 | selections와 적용 기본값 | 기대 코드·통계 기준·기간·주기 |
| 확인 질문 | 질문·선택지·응답 후 조건 버전 | 필요한 확인 조건과 허용 선택 |
| 수치·가공 | 원 관측값·계산 결과·변환 입력 | 고정 원본과 검수한 계산 결과 |
| 표시·설명 | 표·차트 자료·설명·출처·경고 | 필수 항목과 근거 일치 기준 |
| 전체 과업 | 최종 상태와 단계별 필수 결과 | 유형별 성공 조건 |

## 8. 계약을 확정하는 순서

1. 정상 단일·복수 계열, 모호 질의, 조회 오류 사례를 종이상으로 연결합니다.
2. 메타·조회 담당자가 실제 코드·필드·예외를 확인합니다.
3. 평가 담당자가 필요한 판정 근거가 빠지지 않았는지 확인합니다.
4. 합의한 최소 모델을 `src/schemas.py`에 구현합니다.
5. `tests/contracts/`의 예시·검사와 문서를 함께 갱신합니다.

실행 모델을 기준으로 관리하고, 별도 JSON Schema가 필요하면 생성하거나 동기화 검사를 둡니다. 변경 결정은 [설계 검토 기록](설계결정과_검토사항.md)에 남깁니다.

다음 구현에 앞서 최소한 다음을 합의합니다.

- 연결 키·조건 버전과 단계별 상태를 어디에서 관리할지.
- 복수 계열 선택과 원 관측값·가공 입력 참조를 어떻게 표현할지.
- 조건 확인·검색 미적중·자료 없음·오류·부분 결과를 어떻게 구별할지.
- 출력 유형별로 어떤 근거가 필수인지, 검수 대기 정보를 어떻게 표시할지.

Top-k, 점수 임계값, 기본 기간, 재시도 횟수는 논리 계약과 분리한 정책값으로 관리할 수 있습니다. 아직 합의하지 않은 값을 계약 예시만으로 고정하지 않습니다.
