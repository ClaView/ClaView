# 결정 기록

레포를 팀에 넘기는 시점(2026-10-26)에 멘토가 정한 기본 결정이다. "담당"은 다시 판단할 권한이 있는 사람이다. 바꾸면 이 표를 고치고 PR 설명에 이유를 적는다.

상태: **확정**(그대로 진행) · **기본값**(현행 유지, 담당이 바꿀 수 있음) · **과제**(담당이 처리할 일로 배정)

## 협업·운영

| # | 결정 | 상태 | 담당 | 내용 |
|---|---|---|---|---|
| O1 | 원격 레포 | 확정 | 멘토 | 레포는 압축 파일(Git 이력 포함)로 전달한다. 원격(GitHub)은 받는 쪽이 만든다. 절차: [팀 작업 가이드](../guides/팀_작업_가이드.md) 1절 |
| O2 | 코드 오너 | 과제 | 멘토 | `.github/CODEOWNERS`의 `@claview/...` 자리 표시를 실제 GitHub 계정으로 바꾼다 |
| O3 | `main` 보호 | 확정 | 멘토 | PR 필수, CI 통과, 코드 오너 승인 1명. 원격 생성 직후 설정 |
| O4 | `pipeline/` 담당 | 기본값 | 멘토 | 별도 취합 담당을 두지 않고 멘토가 맡는다. 연결 코드 변경은 A·B·C 중 관련 담당이 PR을 올리고 멘토가 리뷰한다 |
| O5 | 배포 형태 | 확정 | 멘토 | 팀원 PC마다 Docker Compose로 띄운다(로컬 단일 사용자). 공용 서버 배포는 하지 않는다. pipeline은 한 번에 한 질문만 처리한다 |
| O6 | 실제 호출 시험 | 확정 | 멘토 | 기본은 `CLAVIEW_MODE=synthetic`. `live`는 멘토 승인 뒤, 한 번에 골든 3문항 이하, HCX 호출 10회 이하로 한다. 결과(호출 수·지연·실패 코드)는 PR이나 이슈에 남긴다 |

| # | 결정 | 상태 | 담당 | 내용 |
|---|---|---|---|---|
| D1 | A 패키지 규칙 완화 | 확정(구현은 과제) | A | (가)안: `claview_a`가 `claview_common.{settings, periods, catalog, llm}`과 `httpx`를 import할 수 있게 한다. `claview_common.api`·`testing`, 다른 모듈, 옛 `claview` 패키지는 계속 막는다. `test_boundary`와 `_guard` 수정은 A 담당 첫 과제 |
| D2 | LLM 호출 정책 | 기본값 | A·B | 인터페이스(`LLMRequest`·`LLMReply`·`LLMError`·`CallPolicy`)만 통일하고 재시도·간격·429 처리는 각 모듈의 현재 값을 정책으로 그대로 넘긴다 |
| D3 | 카탈로그 공통 모델 2단계 | 기본값(보류) | A·B | 1단계(파일 읽기 공통화)까지만 한다. 2단계는 B 골든 비교 뒤 결정 |
| D4 | 공용 기간 해석기 | 기본값(보류) | B | B는 현재 `stages.py`의 기간 해석을 유지한다. `period_core` 도입은 B 기간 골든 비교를 붙인 PR로만 |
| P1 | 설정·경로 공통화 | 확정, 적용함 | 멘토 | `claview_common.settings`에 `Paths`·`Secret`·`usable_key`. B API·C·pipeline의 경로와 키 읽기를 한 곳으로(2026-10-26). B 자체 명령(`claview_b/cli.py`, 숨김 키 입력 포함)과 A는 아직 각자 읽는다(A는 D1 구현 뒤) |
| P2 | 기간 기본 함수 공통화 | 확정, 적용함 | 멘토 | `claview_common.periods`. B `metadata`, C `c_renderer`가 사용(2026-10-26) |

## 서비스 동작

| # | 결정 | 상태 | 담당 | 내용 |
|---|---|---|---|---|
| S1 | A가 표를 확정하지 못했을 때(`assume`) | 기본값 | A·C | 현행 유지: 1순위 표로 진행하고, 화면의 통계표 단계에 "A가 확정하지 못하고 1순위로 진행"과 다른 후보를 보여 준다. 후보 카드로 묻게 바꾸려면 A 담당이 `question_route` 정책을 바꾸는 PR을 올린다 |
| S2 | C가 하던 B 결과 사후 보정 3종 | 과제 | B | 공표 증감률 기간 보존, 지정 항목 보완, 날짜 표기 정규화(`research/c/legacy_web/legacy_old_ab/`). B 담당이 골든 22로 필요성을 확인해 B에 넣거나 버린다. C로 되돌리지 않는다 |
| S3 | 표 ID를 박아 둔 C 규칙 | 과제 | C | M2 합산 검증(`composition.py`), 지수 증감률(`c_analysis.calculate_rates`). 동작은 유지하고 표 ID·항목 코드를 `modules/c/claview_c/rules/*.json`으로 옮긴다 |
| S4 | 조회 조건 편집 화면 | 기본값(보류) | C | 되살리지 않는다. B가 조건을 확정하지 못하면 이유 코드를 보여 주고 질문을 다시 쓰게 한다 |
| S5 | `claview` 명령·골든 평가의 예전 경로 | 과제 | 멘토 | 서비스 경로(service.py)로 통일하고 `pipeline/claview_pipeline/{session,b_port}.py`를 정리한다. 평가 지표가 같은지 확인 |
| S6 | 모듈별 평가 러너 | 과제 | 각 담당 | `make eval-a/b/c`: 자기 모듈 API를 fixtures로 호출해 지표·지연·호출 수 리포트와 기준선 비교. 설계안 2.5절 |
