# 팀 작업 가이드 (A·B·C 담당 3명 + 멘토)

이 레포 하나에서 세 명이 각자 자기 모듈만 고치고, GitHub PR로 합친다. 압축 파일로 코드를 주고받지 않는다.

## 0. 한 장 요약

```text
화면(frontend) ─/api─▶ pipeline ──코드 호출──▶ A service ─▶ B service ─▶ (KOSIS 조회) ─▶ C service
                                                │              │                        │
                         같은 함수를 HTTP로 ─▶ module-a     module-b                 module-c   ← 각자 시험·평가용
```

| 담당 | 고치는 폴더 | 내 모듈의 입구 | 혼자 시험할 때 입력 |
|---|---|---|---|
| A (질문 해석·표 선택) | `modules/a/` | `claview_a_api/service.py` → `POST /a/select` | `common/fixtures/a_request/` |
| B (항목·기간 선택, 조회) | `modules/b/` | `claview_b_api/service.py` → `POST /b/resolve`, `/b/run` | `common/fixtures/b_request/` (정답 표라서 A 없이 됨) |
| C (차트·표, 화면) | `modules/c/`, `frontend/` | `claview_c_api/service.py` → `POST /c/present` | `common/fixtures/data_result_saved/` (실제 KOSIS 값) |
| 멘토 | `pipeline/`, `common/`, Docker 파일 | `pipeline/claview_pipeline/staged.py` | 골든 22문항 |

규칙 세 가지만 기억한다.

1. **내 폴더만 고친다.** 다른 모듈이 바뀌어야 하면 이슈로 요청한다.
2. **모듈끼리 주고받는 모양은 `common/claview_common/contracts`가 기준이다.** 바꾸려면 세 명 모두 리뷰한다.
3. **`main`에 직접 올리지 않는다.** 브랜치 → PR → 시험 통과 → 리뷰 → 머지.

## 1. 처음 받았을 때 (멘토가 한 번)

압축 파일에는 Git 이력(`.git`)이 들어 있다. 압축을 풀면 그대로 Git 레포다.

- 압축은 Windows 탐색기(압축 풀기), PowerShell `Expand-Archive`, 7-Zip으로 푼다. **Git Bash의 `unzip`은 한글 파일 이름을 깨뜨린다**(풀고 나서 `git status`에 삭제된 파일이 보이면 이 경우다).

```bash
git log --oneline | head          # 이력 확인
git status                        # 깨끗해야 한다
```

GitHub에 원격 레포를 만들고 올린다(웹에서 빈 레포를 만든 경우).

```bash
git remote add origin https://github.com/<조직>/claview.git
git push -u origin main
```

`gh` 명령을 쓰면 만들기와 올리기를 한 번에 한다: `gh repo create <조직>/claview --private --source . --push`

올린 뒤 GitHub에서 할 일:

- [ ] `.github/CODEOWNERS`의 `@claview/part-a` 등을 실제 계정(예: `@kim-a`)으로 바꿔 PR로 올린다.
- [ ] Settings → Branches → `main` 보호: Require a pull request, Require approvals 1, Require review from Code Owners, Require status checks(ci).
- [ ] 세 명을 Collaborator(Write)로 초대한다.
- [ ] Issues 라벨: `module:a`, `module:b`, `module:c`, `pipeline`, `frontend`, `contract`.

## 2. 멘티 첫날 (각자 한 번)

필요한 것: Git, Docker Desktop, Python 3.12(로컬 시험용), 편집기.

```bash
git clone https://github.com/<조직>/claview.git
cd claview
cp .env.example .env               # PowerShell: Copy-Item .env.example .env
docker compose up -d --build --wait
docker compose ps                  # 5개 서비스 (healthy)
```

- 화면: http://localhost:10300/ 에서 예시 질문을 하나 실행해 본다(합성 모드라 값은 1로 나온다. 정상이다).
- API 문서: http://localhost:10311/docs (A), http://localhost:10312/docs (B), http://localhost:10313/docs (C), http://localhost:10301/docs (pipeline)
- 끝낼 때: `docker compose down`

로컬 Python 환경(시험을 Docker 밖에서 빠르게 돌릴 때):

```powershell
py -3.12 -m venv .venv
.venv\Scripts\python -m pip install -r requirements-dev.txt
$env:PYTHONHASHSEED = "0"
$env:PYTHONPATH = "common;modules/a;modules/b;modules/c;pipeline"    # Windows는 ; 로 구분
```

macOS/Linux/Git Bash는 `export PYTHONPATH=common:modules/a:modules/b:modules/c:pipeline`(`:`로 구분), 또는 `make test`.

## 3. 매일 작업 흐름

```bash
git switch main && git pull                       # 1. 최신 받기
git switch -c b/period-notice                     # 2. 브랜치: a/… b/… c/… fe/… pipe/… common/…
docker compose -f docker-compose.yaml -f docker-compose.local.yaml up --build   # 3. 저장하면 자동 재시작
#   4. 코드 수정 → 내 모듈 API로 확인 → 내 시험 실행 (4절)
git add -p && git commit -m "B: 기간 안내 문구에 기준일 표시"                   # 5. 작게 자주
git push -u origin b/period-notice                # 6. GitHub에서 PR 생성 (템플릿 채우기)
```

- PR은 한 가지 목적만 담는다. 템플릿의 "확인" 칸에 돌린 시험과 평가 결과(바꾸기 전과 후)를 적는다.
- 리뷰어는 CODEOWNERS가 자동 지정한다. 지적은 같은 브랜치에 커밋을 더해 고친다.
- 머지 뒤 브랜치는 지운다. 다음 작업은 다시 1번부터.
- 충돌이 나면 `git switch main && git pull && git switch <내 브랜치> && git merge main`으로 내 브랜치에서 풀고 다시 push한다. 남의 폴더 충돌은 그 담당과 상의한다.

## 4. 담당별 개발·시험

모든 시험은 **묶음마다 따로** 돌린다(같은 프로세스에 섞으면 가드가 막는다). 명령은 레포 루트에서, 2절의 PYTHONPATH를 설정한 뒤 실행한다.

API를 직접 불러 볼 때는 각 모듈의 `/docs` 화면(Try it out)이 가장 쉽다. 아래 PowerShell 예시는 요청은 정확히 보내지만, Windows PowerShell 5.1은 응답의 한글을 깨진 글자로 보여 준다(값은 정상). 한글 응답을 그대로 보려면 PowerShell 7(`pwsh`)이나 `/docs`를 쓴다.

### A 담당

```powershell
.venv\Scripts\python -B -X utf8 -m pytest modules/a/tests -q -p no:cacheprovider       # A 본체 (약 2~3분)
.venv\Scripts\python -B -X utf8 -m pytest modules/a/tests_api -q -p no:cacheprovider   # A API
Invoke-RestMethod -Method Post -Uri http://localhost:10311/a/select -ContentType "application/json; charset=utf-8" `
  -Body (Get-Content common/fixtures/a_request/CV-AB-12.json -Raw -Encoding utf8)
```

- `claview_a`(본체)는 표준 라이브러리와 langgraph만 import하고, 패키지 안에서는 상대 import만 쓴다. `modules/a/tests/test_boundary.py`가 이를 검사한다. 웹·공통 코드는 `claview_a_api`에서 쓴다(규칙 완화는 [결정 기록](../design/결정_기록.md) D1, A 첫 과제).
- 첫 요청은 카탈로그 적재로 약 8초 걸린다.
- 결과 지표: 골든 22문항 표 일치 17/22(현재 기준선). 바꾼 뒤 이 숫자를 PR에 적는다.

### B 담당

```powershell
.venv\Scripts\python -B -X utf8 -m pytest modules/b/tests -q -p no:cacheprovider
.venv\Scripts\python -B -X utf8 -m pytest modules/b/tests_api -q -p no:cacheprovider
Invoke-RestMethod -Method Post -Uri http://localhost:10312/b/run -ContentType "application/json; charset=utf-8" `
  -Body (Get-Content common/fixtures/b_request/CV-AB-04.json -Raw -Encoding utf8)
```

- `b_request` 샘플은 골든 정답 표를 쓰므로 A 결과와 상관없이 B만 잰다.
- 합성 모드의 B 모델은 "첫 항목·첫 값"을 고르는 가짜다. 선택 정확도를 보려면 재생(골든 B 답) 또는 승인된 실제 호출이 필요하다.
- 기간 계산(`periods_between` 등)은 `claview_common.periods`를 쓴다. B 함수 이름은 그대로 두었다.

### C 담당

```powershell
.venv\Scripts\python -B -X utf8 -m pytest modules/c/tests -q -p no:cacheprovider
.venv\Scripts\python -B -X utf8 frontend/build/ui_build.py         # 화면 다시 만들기 → frontend/dist/
docker compose up -d --build frontend                            # 화면 컨테이너만 새로
```

- 차트 로직(`modules/c/claview_c`)은 서버·조회가 없는 순수 함수다. 입력은 `data_result`, 출력은 차트 자료.
- 화면 JS·CSS는 `frontend/src/`, 화면 틀은 `frontend/src/template/`. 화면은 `/api/*`(pipeline)만 부른다.
- 실제 값으로 보고 싶으면 `common/fixtures/data_result_saved/`(저장된 실제 KOSIS 결과 4건)를 `/c/present`에 넣는다.

### 모두 (PR 전에)

```powershell
.venv\Scripts\ruff check .
.venv\Scripts\lint-imports            # 모듈 경계 규칙 (pyproject.toml)
```

## 5. 다른 모듈에 영향을 줄 때

| 상황 | 할 일 |
|---|---|
| 다른 모듈 결과가 이상하다 | 그 모듈 라벨로 이슈를 연다. 재현 입력(fixtures 파일 이름 또는 질문)과 기대 결과를 적는다. 내 모듈에서 고쳐 덮지 않는다 |
| 주고받는 모양을 바꿔야 한다 | `common/claview_common/contracts` 수정 → `pipeline/scripts/build_fixtures.py`로 샘플 재생성 → 영향 받는 시험 수정을 **한 PR**로. A·B·C 모두 리뷰 |
| 라이브러리가 필요하다 | 루트 `requirements.txt`에 버전 고정(`==`)으로 추가하는 PR. 모든 서비스 이미지에 들어가므로 이유를 적는다 |
| 실제 OpenAI·KOSIS 호출이 필요하다 | 멘토 승인 뒤 `.env`의 `CLAVIEW_MODE=live`와 키. 한 번에 골든 3문항 이하, 모델 호출 10회 이하. 결과를 PR·이슈에 기록 |

| B | S2: 예전 C의 B 결과 보정 3종(`research/c/legacy_web/legacy_old_ab/`)이 필요한지 골든 22로 확인 → B에 넣거나 폐기 | PR 또는 폐기 근거 이슈 |
| B | P3: 카탈로그·원메타 읽기를 `claview_common.catalog`로(설계 4.4) | 349표 전부 `MetadataStore.get()` 결과 동일 |
| C | S3: M2 합산·지수 증감률의 표 ID·항목 코드를 `modules/c/claview_c/rules/*.json`으로 | C 시험·골든 22 화면 결과 동일 |
| 모두 | S6: 내 모듈 평가 러너(`make eval-a/b/c`) — fixtures로 내 API를 불러 지표·지연·호출 수 리포트 | 기준선 파일 `eval/baselines/<모듈>.json` 커밋 |

## 7. 자주 겪는 문제

| 증상 | 원인·해결 |
|---|---|
| `ModuleNotFoundError: claview_…` | PYTHONPATH 미설정. Windows는 `;`, macOS/Linux는 `:` 구분 |
| 시험을 한 번에 돌리면 `boundary`·`network` 오류 | 묶음별로 따로 실행(4절). A 가드는 같은 프로세스의 다른 모듈을 막는다 |
| Docker Desktop이 "unexpected error"로 멈춤 | Docker Desktop 종료 → `%LOCALAPPDATA%\Docker\run\userAnalyticsOtlpHttp.sock` 삭제 → 다시 실행. "Reset to factory defaults"는 누르지 않는다 |
| 포트 충돌(10300 등) | `.env`에서 `FRONTEND_PORT` 등 바꾸기 |
| 화면이 "서버에 연결하지 못했습니다" | `docker compose ps`로 pipeline이 healthy인지, 화면 주소가 http://localhost:10300/ 인지 확인 |
| 커밋할 때 CRLF 경고 | 무시해도 된다(`.gitattributes`가 줄바꿈을 맞춘다) |
| 키를 실수로 커밋했다 | 즉시 멘토에게 알리고 키를 재발급한다. 이력에서 지우는 것만으로는 안전하지 않다 |
