## 2. 준비

팀 저장소는 팀이 만든 GitHub 레포를 기준으로 한다. 받은 뒤 브랜치·로컬 변경을 확인한다.

```sh
git status --short --branch
```

다른 위치에서 쓰던 `.venv`는 복사하지 않고 이 폴더에서 새로 만든다(압축본에 들어 있는 `.venv`도 쓰지 않는다).

## 3. 설치

Windows PowerShell:

```powershell
py -3.12 -m venv .venv
.venv\Scripts\python -m pip install -r requirements-dev.txt
```

Linux/macOS:

```sh
python3.12 -m venv .venv
.venv/bin/python -m pip install -r requirements-dev.txt
```

- 최초 설치에는 패키지 다운로드가 필요하다. 설치 중 네트워크 사용과 시험 중 API 호출은 별개다.
- 의존성을 바꾸지 않았다면 `requirements*.txt`를 새로 만들지 않는다.

## 4. 기본 확인

묶음마다 **별도 pytest 프로세스**로 돌린다(README 3절). Linux/macOS/CI는 `make test`, `make lint`.

```powershell
$env:PYTHONHASHSEED = "0"
$env:PYTHONPATH = "modules/a"
.venv\Scripts\python -B -X utf8 -m pytest modules/a/tests -q -p no:cacheprovider
$env:PYTHONPATH = "common;modules/b"
.venv\Scripts\python -B -X utf8 -m pytest modules/b/tests -q -p no:cacheprovider
$env:PYTHONPATH = "common;modules/c"
.venv\Scripts\python -B -X utf8 -m pytest modules/c/tests -q -p no:cacheprovider
$env:PYTHONPATH = "common;modules/a;modules/b;modules/c;pipeline"
.venv\Scripts\python -B -X utf8 -m pytest pipeline/tests -q -p no:cacheprovider
.venv\Scripts\python -B -X utf8 -m pytest common/tests modules/a/tests_api pipeline/tests_api -q -p no:cacheprovider
.venv\Scripts\ruff check common modules/a/claview_a_api modules/b/claview_b_api modules/c/claview_c_api pipeline/claview_pipeline/api.py
.venv\Scripts\lint-imports
```

| 검사 | 통과 기준 |
| --- | --- |
| Python | 3.12 계열 |
| 시험 묶음 | 실패 0(레포 밖 자료가 없어 skip되는 시험은 사유 확인) |
| 네트워크 차단 | 시험 중 일반 Python TCP 연결이 막힘(B: `block_network`, A: A 가드, API 시험: 루프백만 허용) |
| Ruff | `make lint` 범위의 코드 검사 오류 없음 |
| 모듈 경계 | `lint-imports` 규칙 모두 지킴(모듈 본체끼리 import 금지 등) |

연결 차단은 pytest 실행 중 일반적인 Python TCP 연결을 막는 장치다. 별도 프로세스·UDP·네이티브 라이브러리까지 막는 보안 격리는 아니다. 기본 시험에는 실제 API 호출 코드를 넣지 않는다.

이 검사는 환경만 확인한다. KOSIS 조회, NCP 모델 접근, 데이터 정확성의 검증 완료를 뜻하지 않는다.

## 5. API 키와 환경변수

기본 설치·시험에는 `.env`와 API 키가 필요하지 않다(기본 `CLAVIEW_MODE=synthetic`).

API 기능이나 Docker를 쓸 때만 `.env.example`을 복사한다. 이미 있는 `.env`는 덮어쓰지 않는다.

PowerShell:

```powershell
if (-not (Test-Path -LiteralPath .env)) {
    Copy-Item -LiteralPath .env.example -Destination .env
}
```

Linux/macOS:

```sh
test -e .env || cp .env.example .env
```

- 키는 편집기에서 입력하고 문서·채팅·명령줄 인자·로그에 남기지 않는다.
- Docker Compose는 `.env`를 읽는다. 로컬 Python 실행은 `claview_common.settings`가 환경변수를 읽으므로, 필요하면 셸 환경변수로 넣는다.
- `git check-ignore .env`로 제외 여부를 확인하고 PR에 실제 키가 없는지 검사한다.

## 6. 의존성 변경

1. 사용할 기능·추가 이유·영향 범위를 공유한다.
2. 실제 필요한 의존성만 `requirements.txt`(런타임) 또는 `requirements-dev.txt`(개발 도구)에 버전을 고정해 추가한다.
3. Dockerfile·실행 안내·시험이 맞는지 함께 확인한다(AGENTS.md).
4. 기본 검사와 관련 기능 시험을 실행한다.
5. PR에 변경 이유·검증 결과를 남긴다. 병합 뒤 팀원은 `pip install -r requirements-dev.txt`로 맞춘다.

Python 변경, 핵심 프레임워크 도입, 주요 버전 업그레이드는 작업 전 팀과 합의한다. 브랜치·리뷰·병합 규칙은 [CONTRIBUTING](../../CONTRIBUTING.md)과 [팀 작업 가이드](팀_작업_가이드.md).

## 8. 문제 해결

| 증상 | 확인할 것 |
| --- | --- |
| `ModuleNotFoundError: claview_*` | 저장소 루트에서 실행했는지, 그 묶음의 `PYTHONPATH`(Makefile)를 줬는지 확인 |
| 여러 묶음을 한 번에 돌리면 import 거부 | A 가드 때문이다. 묶음마다 별도 pytest 프로세스로 돌린다 |
| Python 버전 불일치 | `.venv`를 3.12로 만들었는지 확인 |
| 테스트 중 Network access is forbidden | 실제 연결 대신 모의 응답 사용. 차단을 해제해 기본 검사를 통과시키지 않음 |
| `lint-imports` 실패 | 모듈 본체끼리 import했는지 확인. 잇는 일은 `pipeline/`에서, 서비스 흐름은 `claview_*_api`를 통해서만 |
