# 검색 문서 구성과 색인 준비

- 관리: 검색 담당 / 메타정보·용어 매핑 담당 공동 검수
- 정리일: 2026-09-23
- 상태: 기본 검색 문서 349건·상세 16건·매핑 76건·개발 질문 48건을 검토용 JSON으로 반영했습니다. 의미 승인·조회 코드 연결·색인·검색 성능 검증은 미완료입니다.
- 관련: [메타정보 검수](메타정보_관리와_검수.md), [용어 매핑](용어_매핑_작성과_검수.md), [NCP 활용 방향](../design/NCP_모델분석과_적용방향.md)

## 1. 목적과 연결

```text
검수한 목록·메타정보 + 용어 매핑
→ 검색 문서 생성
→ 키워드·임베딩 색인
→ 질문에 맞는 후보 회수
→ 실제 메타정보와 조회 조건 검증
```

검색 문서는 질문과 후보를 연결하기 위한 파생 자료입니다. 실제 API 응답이나 조회 계획을 대신하지 않습니다. 통계 수치를 임베딩 문서에서 찾아 원자료처럼 답하지 않습니다.

### 확보한 입력과 검수 범위

| 입력 | 확인한 내용 | 남은 작업 |
| --- | --- | --- |
| [기본 검색 문서 349건](../../data/samples/search-review/검색문서_기본349건.json) | 기존 목록 CSV와 표 ID 집합·표명 일치. 2026-09-16 보관 목록 기반 | 경로·현행/구계열의 공식 메타 대조, 최신 목록 재수집 |
| [상세 검색 문서 16건](../../data/samples/search-review/검색문서_상세16건.json) | 14개 분야, 관찰 정보와 팀 설명 분리, 기본 목록 참조 확인 | 화면 관찰을 실제 메타 코드·주기별 기간과 연결 |
| [용어 매핑 76건](../../data/mappings/review/검색용_의미매핑_초안.json) | 의미 별칭 14·관련 개념 31·조건 보존 23·표기 정규화 8 | 관계 의미·적용 범위·실제 코드 검수 |
| [개발 질문 48건](../../eval/cases/review/검색평가_초안_48건.json) | 명확·모호·오연결 방지 각 16, 모두 미실행 | 기대 행동 검수, 고정 후속 답변·정답 조건 보완 |

이 파일들은 받은 자료의 JSON 값과 배열 순서를 유지한 고정 스냅샷입니다. 파일명·인코딩·줄바꿈만 공유 기준에 맞췄습니다. 기본 349건은 현재 전체 API 범위의 재조사 결과가 아니며, 상세 16건은 349건과 별개의 16개 표를 추가한 것이 아닙니다. 같은 표 ID에 상세 설명을 붙인 자료입니다.

검수 기록과 원본 파일명은 [검색 자료 이관·검수 기록](../research/검색자료_이관과_검수.md)에 있습니다. `table_search: true`는 작성자가 표 검색용으로 준비했다는 표시이며 검색 실행 성공을 뜻하지 않습니다. 모든 상세 문서의 `api_execution`은 false이고 항목·분류 코드는 비어 있습니다.

## 2. 문서에 포함할 내용

| 영역 | 내용 |
| --- | --- |
| 식별·경로 | 문서 ID, 기관·표 ID, 표명, 목록 경로 |
| 선택 조건 | 항목·분류 명칭, 계층, 유효한 연결 코드 |
| 통계 의미 | 대상·통계 기준·단위·정의·주석 |
| 조회 가능 범위 | 지원 주기와 주기별 수록기간 |
| 표현 연결 | 검수 상태를 확인한 별칭·관련 개념·구별 조건 |
| 추적 정보 | 원본 메타 버전, 매핑 버전, 문서 생성 버전·시각 |

검색용 텍스트와 프로그램이 사용할 식별 정보를 나눠 보관합니다. 코드가 긴 경우 텍스트에 모두 나열하기보다 구조화 필드에 보존하는 방식을 비교합니다. 후보를 찾은 뒤 코드로 원본 메타를 다시 확인할 수 있어야 합니다.

형식 예시:

```text
기관·표 ID / 문서 ID / 원본 버전
목록 경로 > 표명
선택한 항목·분류의 명칭과 통계 기준
단위·지원 주기·수록기간
정의·주석·구별 조건
관련 표현과 관계 유형
연결 코드·원문 참조
```

예시의 항목은 필드 후보이며 공통 입출력 계약의 확정 스키마가 아닙니다.

## 3. 문서 단위를 정하는 방법

| 단위 후보 | 장점 | 확인할 위험 |
| --- | --- | --- |
| 표 단위 | 전체 목록을 관리하고 넓은 질문의 후보를 찾기 쉬움 | 항목이 많은 표에서 세부 의미가 묻히거나 입력이 길어짐 |
| 항목·분류 묶음 단위 | 구별 조건을 상세하게 검색하기 쉬움 | 조각만으로 표 맥락·단위를 이해하기 어려울 수 있음 |
| 표 요약 + 상세 문서 | 표 탐색 후 필요한 상세 후보를 볼 수 있음 | 문서 간 연결·중복 후보 처리가 필요 |

처음부터 모든 항목·분류의 조합을 만들지 않습니다. 의미가 있는 묶음과 실제 조회 가능한 조건을 확인한 뒤 분할합니다. 분할 기준과 최종 문서 단위는 대표 사례의 입력량·검색 결과를 보고 정합니다.

길이 제한으로 문서 뒷부분을 무조건 자르지 않습니다. 식별자·기준·단위가 빠지지 않도록 분할하고, 모든 상세 문서를 원래 표와 연결합니다.

## 4. 생성·저장·갱신

| 자료 | 위치 | 관리 방식 |
| --- | --- | --- |
| 목록·메타 확보 현황 | `data/catalog/` | 원본 참조·수집·검수 버전 기록. 현황 요약을 상세 메타로 사용하지 않음 |
| 상세 메타·원 응답 | `data/raw/` 또는 팀 공용 보관소 | 기본 Git 제외. 원본 식별자·확보 방법을 연결하고 대표 메타만 `data/samples/`에 공유 |
| 기준 매핑 | `data/mappings/` | 관계 유형·근거·승인 상태 기록 |
| 대표 검색 문서 | `data/samples/` | 작고 검토 가능한 예시만 공유 |
| 초기 검색 문서 고정 스냅샷 | `data/samples/search-review/` | 기본 349·상세 16건의 검토용 기준 입력. 전체 생성 문서의 상시 보관소가 아님 |
| 전체 생성 문서 | `data/processed/` | 기본 Git 제외, 입력과 생성 방법으로 재현 |
| 검색 색인 | `data/indexes/` | Git 제외, 재생성 조건 기록 |
| 생성·색인 실행 진입점 | `scripts/` | 공통 로직은 구현할 때 `src/search.py`에 배치 |

색인 생성 기록에는 입력 파일 버전·생성 코드·분할 설정·임베딩 모델·문서 수·실패 수를 남깁니다. 제외 문서와 사유도 기록해 전체 대상 중 어디까지 검색 가능한지 확인합니다.

메타·매핑 변경으로 영향받는 문서를 다시 생성합니다. 임베딩 모델을 바꾸면 기존 벡터와 섞지 않고 해당 색인을 다시 만듭니다. 문서 ID와 원본 버전의 연결을 유지합니다.

## 5. 초기 검증 순서

1. 구조가 다른 대표 표와 명확·모호한 질문을 준비합니다.
2. 키워드 검색을 기준선으로 만들고 놓치는 후보를 기록합니다.
3. 같은 입력 자료와 질문에서 문서 단위·별칭 반영 효과를 비교합니다.
4. 임베딩·하이브리드 검색 등 후보 방법을 하나씩 추가해 비교합니다.
5. 정답 표뿐 아니라 필요한 항목·분류 후보가 연결되는지 확인합니다.
6. 후보를 원본 메타와 대조하고 조회 조건 검증 단계로 넘깁니다.

| 확인 항목 | 기록할 내용 |
| --- | --- |
| 표 후보 회수 | 정답 표가 상위 k개에 포함되는지, 복수 표 질문은 필요한 표를 얼마나 찾았는지 |
| 상세 후보 | 항목·분류·통계 기준이 질문에 맞는지 |
| 의미 혼동 | 관련 개념을 동의어로 처리하거나 기준이 다른 계열을 섞었는지 |
| 입력·비용 | 문서 수·토큰량·생성/질의 호출량·응답 시간 |
| 예외 | 후보 없음, 근거 부족, 색인 누락, 메타 변경 |

지표의 분모·k·목표치는 [평가 계획](../design/골든셋과_평가계획.md)에서 합의합니다. 검색 점수가 낮다는 이유만으로 범위 밖이라고 확정하지 않습니다. 인용 문서의 순서를 API가 제공한 관련도 순위로 가정하지 않습니다.

## 6. 인계 완료 기준

- 대표 문서에서 원본 메타·매핑과 연결 코드를 찾을 수 있습니다.
- 생성 규칙과 버전, 누락·실패 문서를 설명할 수 있습니다.
- 같은 입력으로 문서를 다시 만들 수 있는 실행 방법이 있습니다.
- 검색 후보를 조회 계획 검증 단계로 전달할 필드가 정리되어 있습니다.
- 성능 결과에는 질문셋·정답 근거·검수 범위가 함께 기록됩니다.

현재는 검토용 문서 파일을 확보하고 참조 구조를 검사한 단계입니다. 원본 메타 연결·승인·문서 재생성 코드·색인·검색 평가 결과는 아직 없습니다.

## 7. 받은 문서를 검색·조회에 연결하는 순서

1. 기본 문서와 상세 문서는 기관·표 ID로 연결합니다. 둘을 색인에 함께 넣더라도 같은 표를 두 번 찾았다는 이유로 표 적중 수를 늘리지 않습니다.
2. `official_observations`는 작성자의 화면 관찰 기록, `team_search_document`는 검색용 설명으로 구분합니다. `period_display`와 표시된 일부 분류값을 전체 조회 가능 조건으로 변환하지 않습니다.
3. `scope.table_ids`는 매핑의 적용 문맥일 수 있습니다. `source_table_ids`도 근거 표이지 항상 최종 조회 대상이 아닙니다. 예를 들어 M004의 소비자심리지수는 경제심리지수와 다른 지표를 찾도록 설명하므로 scope의 표를 정답으로 강제하면 안 됩니다.
4. `alias` 중 `normalization_only: true` 8건은 표기 처리로 분리합니다. 관련 개념은 후보 확장에, `criterion`은 명시 조건 보존에 사용하도록 검토합니다. 승인 전에는 실험 입력으로 사용한 버전·행을 명시하고 서비스 사전에 자동 반영하지 않습니다.
5. 후보 근거로 `doc_id`, `mapping_id`, 원문·확인일·검수 상태를 전달합니다. 실제 조회는 원본 메타에서 코드를 확인한 뒤 공통 규격의 `selections`로 구성합니다.
6. 개발 질문의 확인 질문 예시는 그대로 재생하지 않습니다. Q01-A의 ‘경기 심리’는 지표부터 모호한데 예시 질문은 경제심리지수 안의 원계열/순환변동치만 묻습니다. 지표 후보를 먼저 확인하도록 검토해야 합니다.
7. [평가 계획](../design/골든셋과_평가계획.md)에 따라 키워드 기준선부터 측정합니다. 역방향 순위·직접 유사도는 용어 후보 검토 방법의 비교안이며, 실제 검색 성능과 별도로 검증합니다.
