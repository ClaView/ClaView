# Docker 기본 화면으로 실제 조회하기

기본 화면은 `frontend → pipeline → A → B → KOSIS 조회 → C`로 실행한다. pipeline이 같은 프로세스에서 각 모듈의 service를 부르며, module-a/b/c 컨테이너의 HTTP API를 거쳐 연결하는 것은 아니다. 별도 골든 실행기 없이 화면에서 입력·되묻기·답 적용·결과 확인을 할 수 있다.

## 1. 설정과 실행

저장소 루트에서 `.env.example`을 `.env`로 복사한다. 이미 `.env`가 있으면 덮어쓰지 않고 필요한 항목만 수정한다. Docker와 일반 배포의 기본값은 `CLAVIEW_MODE=live`다. 키가 없으면 준비 상태가 false이고 실제 요청을 실행할 수 없다. 합성 결과로 자동 대체하지 않는다. 개발·시험에서 외부 호출 없이 동작을 볼 때만 `CLAVIEW_MODE=synthetic`을 명시한다.

실제 조회를 사용할 때 `.env`의 다음 세 항목을 설정한다. 실제 키 값은 문서·채팅·실행 명령 인자에 넣지 않는다.

```dotenv
CLAVIEW_MODE=live
OPENAI_API_KEY=<발급받은 키를 .env에서만 입력>
KOSIS_API_KEY=<발급받은 키를 .env에서만 입력>
```

일반 화면 실행에는 `CLAVIEW_A_LIVE_APPROVAL`이 필요하지 않다. 평가용 승인 경로를 사용 중이었다면 일반 실행용 환경과 구분한다. 승인 경로를 명시한 채 유효하지 않은 승인으로 실행하면 거절되며, 일반 실행으로 자동 대체하지 않는다.

```bash
docker compose up -d --build --force-recreate --wait
docker compose ps
```

브라우저에서 `http://localhost:10300/`을 연다. `.env` 변경은 이미 실행 중인 프로세스에 반영되지 않으므로 컨테이너를 재생성해야 한다. Docker 기본 설정은 한 pipeline 프로세스로 실행한다.

화면의 준비 상태 또는 `http://localhost:10301/api/info`에서 다음을 확인한다.

일반 운영 화면에는 모드 이름을 붙이지 않고 준비 상태만 보인다. 명시적으로 켠 합성 시험에는 `테스트용 · 합성 데이터`를 표시한다. 저장된 결과 불러오기는 모드 전환이 아니며, 내부 기록에는 자료 출처를 계속 보존한다.

| 항목 | 의미 |
|---|---|
| `claview_mode` | `live` 또는 `synthetic` |
| `a_ready` | A 실행에 필요한 설정이 준비됨 |
| `model_ready` | B 모델 실행에 필요한 설정이 준비됨 |
| `kosis_ready` | KOSIS 조회에 필요한 설정이 준비됨 |
| `ready` | 전체 실행에 필요한 준비 상태 |
| `a_unavailable_reason` | A가 준비되지 않은 경우의 고정 사유 코드 |

준비 표시는 외부 인증 시험이 아니다. 실제 API에서 인증·한도 오류가 반환될 수 있다. 키가 없거나 설정이 잘못되었을 때 합성 데이터로 바꾸어 성공 처리하지 않는다. `/api/info`에는 프로세스용 요청 토큰도 있으므로 응답 전체를 공유하지 않는다.

A 호출에서 401·403이 반환되면 인증 중단 상태도 저장한다. 키를 바꾸거나 컨테이너를 재시작해도 이 상태와 사용한 호출 칸을 자동 초기화하지 않는다. 현재 자동 해제 화면은 없으므로, 인증 오류를 해결한 뒤 운영자가 중단 상태를 별도로 확인해야 한다. 기록 volume 전체를 삭제해 해결하지 않는다.

## 2. 화면에서 확인할 순서

1. 기간·주기·대상이 명확한 질문을 입력한다. A가 확정한 표·조건이 B 선택과 조회까지 이어지는지 본다.
2. 기간이나 기준이 빠진 질문에서 되묻기 카드가 나오면 필요한 조건만 답한다. 답 적용은 기존 선택·조건을 보존하며 A 모델을 새로 부르지 않는다.
3. 결과에서 계열 이름·단위·요청 기간·실제 조회 기간·미수록 안내를 확인한다. A 조건 확정과 전체 조회 완료를 구분한다.
4. 계산을 요청한 경우 원자료와 파생값, 계산 완료 여부를 따로 확인한다. 원자료를 받았다는 이유만으로 요청 계산이 끝난 것은 아니다.
5. 저장된 실제 기록을 불러와 결과를 확인한다. 이는 합성 모드가 아니며 새 외부 호출도 하지 않는다. 같은 질문을 다시 보내 모델을 재호출하는 것과 구분한다.

서비스의 기준일은 새 질문을 시작한 날로 정하고, 되묻기 답을 적용하거나 기록을 불러올 때 같은 실행의 기준일을 유지한다. 고정 기준일로 비교하는 골든 평가는 별도 실행 범위다.

기존 A 정책은 유지한다. 첫 판단은 1회, 필요한 복구는 공유하는 최대 1회이며, 되묻기는 사용자만 정할 조건을 받는다. 기본 화면의 A·B·KOSIS 전체 사용량에 골든 평가의 문항 목록·금액 상한이 자동 적용되지는 않는다. 대량 확인을 요청할 때는 대상과 호출·비용 범위를 별도로 정한다.

## 3. 기록 보존

기본 compose는 다음 named volume을 사용한다. 두 서비스가 같은 A 기록 기반 경로를 보므로 A HTTP와 화면을 바꾸어 호출해도 별개의 기본 원장으로 갈라지지 않는다.

| volume | 컨테이너 경로 | 용도 |
|---|---|---|
| `claview_runs` | `/claview/runs` | A 실행 기록과 pipeline 저장 결과 |
| `claview_a_live` | `/root/.claview/a_live` | 명시적 평가 승인 실행의 원장·사용량 기록 |

compose가 `CLAVIEW_A_RUN_ROOT=/claview/runs/a_service`를 설정한다. 일반 실행의 A 기록은 그 아래 `live/`와 `synthetic/`으로 나뉜다. pipeline 결과는 `/claview/runs/pipeline/live/` 또는 `/claview/runs/pipeline/synthetic/`에 저장하며 결과·목록의 `claview_mode`로도 구분한다. 합성 확인이 실제 호출 칸을 쓰거나 실제 기록으로 오인되지 않도록 분리한다. 명시적 평가 승인 경로는 승인에 기록된 경로·원장 조건을 그대로 검사한다.

```bash
docker compose down
docker compose up -d --wait
```

위 중지·재기동은 volume을 유지한다. **`docker compose down -v`는 volume과 그 안의 실행 기록·원장을 삭제하므로 기록을 유지할 때 사용하지 않는다.** 프로젝트 이름을 바꾸면 다른 이름의 volume이 만들어질 수 있다. 예전 기록을 찾지 못한다고 원장을 초기화하거나 질문을 다시 실호출하지 않는다.

개발용 `docker-compose.local.yaml`은 `/claview/runs`를 저장소의 `./runs`로 바인드 마운트한다. 기본 compose의 named volume과 보관 위치가 다르다. 기본 실행과 개발용 실행을 번갈아 쓸 때 각각의 기록 위치를 먼저 확인한다. 이 개발용 파일은 소스 마운트·자동 재시작만 바꾸므로 합성 확인을 원하면 `CLAVIEW_MODE=synthetic`도 명시한다. CI Docker 스모크와 `docker-compose.eval.yaml`의 오프라인 평가 실행은 합성 모드를 명시해 실제 호출을 하지 않는다.

## 4. 합성 확인과 평가 실행

- 합성 확인: 개발·시험 목적으로 `.env`를 `CLAVIEW_MODE=synthetic`으로 명시하고 컨테이너를 재생성한다. A·B 판단과 조회 값이 합성임을 화면에서 확인한다. 모델 해석 정확도나 실제 수치 검증으로 보고하지 않는다.
- 일반 실사용: 기본 모드인 `live`에서 두 키를 서버 환경에 설정하고 화면에서 실행한다. 평가 승인 JSON은 요구하지 않는다. 키가 없으면 준비되지 않은 상태이며 합성 모드로 넘어가지 않는다.
- 실제 기록 불러오기: 이전 실제 응답·조회 결과를 표시하는 기능이다. 합성 데이터 생성과 구분하며 새 외부 요청을 보내지 않는다.
- 승인된 평가: `CLAVIEW_A_LIVE_APPROVAL`에 컨테이너에서 접근 가능한 승인 경로를 명시한다. 문항·후보·해시·유효기간·원장 등 승인 조건을 검사하며, 실패할 때 일반 실사용으로 우회하지 않는다. 평가 실행기를 쓰는 경우 그 실행기의 B·KOSIS 한도도 별도로 적용되어야 한다.

이 변경은 실행 경로를 연결하는 작업이다. 실제 모델·KOSIS를 이용한 전체 화면 결과는 별도 실행 기록으로 확인하며, 오프라인 시험 통과를 실호출 완료로 표시하지 않는다.
