# A파트(질문 해석·표 선택)에 요청: B와 유기적으로 잇기 (2026-10-20)

B 재구성(계획 [03 r2](../plans/03_B_재구성_계획_r2.md)) 중 사용자가 정한 네 원칙을 위해 A 쪽에서 해 줄 일이다. 기준 코드는 A 동결 공유본 `share/질문해석_공유_20261020`의 `src/claview_v3`이다. "확인"은 코드·저장 표본에서 본 것, "제안"은 아직 정하지 않은 모양이다.

> 갱신(07:56): 이후 표 선택 스레드와 합의한 모양이 [계획 10절](../plans/03_B_재구성_계획_r2.md)에 있다. 이 문서의 제안 모양과 다르면 10절을 따른다: 대응 행 `{name_id, quote, span, table_id, obj_id, value_id, value_name, role, path, negated}`, 미리보기 `preview_fit(requirement, table)`, 되묻기 `{scope_id, dimension, changes_numbers, options, resume_at}`(`resume_stage` 대신 `resume_at`), 대표값은 A `selection_policy`를 읽음.

## 0. 공통 전제 (확인)

- A와 B는 같은 메타를 읽는다. 원자료 `boK_meta_raw.jsonl` sha256 앞 12자리 `b604e909d40f`, 카탈로그 `search_catalog.json` `0ff158a8717c`(A 출력의 `catalog_version`과 같음).
- 표 선택의 `selections[].signals.facts.tables[표].indicator.occurrences[].value_id`는 B 메타의 항목·분류 값 코드와 같다(원 메타 `OBJ_ID`까지 일치, B 시험 `tests/b_v2/test_adapter_v3.py`).
- B 입력 계약은 요구 단위다: `scope_id = requirement_id`, 표, 조건(고유+공통), 모호 조건 ID, 부정어, 값 언급(`value_mentions`), covers. 변환은 B의 `src/claview/b/adapter_v3.py`가 맡는다. A 출력 모양이 바뀌면 공유본 날짜를 새로 내 달라.

## 1. 후보 표마다 미리 매핑해 보고 고르기

목표: 표 선택의 1·2순위 후보에 B의 코드 매핑(모델 없음)을 먼저 돌려, 계열이 완성되는 표만 남긴다. 하나만 완성되면 묻지 않고 확정, 하나도 안 되면 B 전에 표 부적합.

B가 줄 것(제안): `preview_fit(scope, table) -> {fit: ok | partial | no, fixed_axes, open_axes, series_estimate, period: {applied, source}, reasons[]}`. 메타만 읽고 모델·KOSIS 호출 0.

A가 할 일:
1. 1·2순위 후보를 확정 전에 미리보기에 넘길 자리. 지금 `alternatives`는 표 ID 목록뿐이다(확인). 2순위 후보도 `org_id`, `table_name`, `covers`, 그리고 `signals.facts.tables`의 occurrences가 있어야 미리보기가 돈다. 저장 표본 8개에서는 대안 표의 facts가 모두 들어 있었다(확인). 그러나 그것이 보장인지는 코드에서 확인하지 못했으니 "1·2순위는 facts를 항상 남긴다"를 보장해 달라. 또 `alternatives`가 빈 선택(표본 2건: confirm인데 대안 0, facts에는 표 16개)은 2순위 후보가 무엇인지 정해 줄 필드가 없다. 2순위를 명시하는 칸(예: `ranked_candidates[:2]`)이 필요하다.
2. 미리보기 결과를 결정 규칙에 넣기(제안): 완성 표가 하나 → `auto`(되묻지 않음), 둘 이상 → 지금 규칙, 없음 → `no_table` + 사유 `preview_no_fit`. 결정은 A의 `select/decision.py`·검증(V2) 쪽에서 한다.
3. 의존 방향(제안): A가 B 모듈을 직접 import하지 않고, 그래프 설정(`configurable["fit_preview"]`)으로 함수를 받는다. 없으면 지금처럼 동작한다(미리보기 끔).
4. 완료 판정: 같은 질문 표본에서 미리보기 켬/끔의 결정 상태(auto/confirm/no_table) 개수 비교, 외부 호출 0.

## 2. 이름 → 값 대응표 한 벌

목표: 해석이 찾은 이름을 "어느 표, 어느 축, 어느 값 코드"까지 한 번에 묶어 두고, 표 선택은 이걸로 표를 고르고 B는 이걸로 축을 고정한다.

지금(확인): 해석의 `terms[]`는 `obj_id`까지만 있고 값 코드가 없다. 값 코드는 표 선택 단계의 occurrences에서 처음 나온다. B는 그 사본을 받는다.

A가 할 일:
1. 대응표 행(제안): `{name, fragment_id, requirement_id, table_id, obj_id, value_id, method(exact/...), role(target/series_name/indicator), parents[], polarity(+/-)}`. 부정어(`judgement.negated`)·기준 조건 polarity로 `-`를 표시한다(occurrence에는 지금 polarity가 없다, 확인).
2. 만드는 곳: 해석(terms)이 카탈로그 층에서 값 코드까지 붙이거나, 표 선택 직후 한 번 만든다. 어느 쪽이든 한 곳에서 만들고 이후 단계는 읽기만.
3. 출력 위치(제안): `analysis.value_index[]`(또는 상태 최상위). B 어댑터는 이것이 있으면 이걸, 없으면 지금처럼 occurrences를 쓴다.
4. 완료 판정: 저장 표본에서 B가 고정한 축 값이 대응표 행과 1:1로 대조된다.

## 3. 조건은 한 칸

목표: 기간·주기·기준은 해석이 한 번 읽고, 표 선택은 그 값으로 표를 거르고, B는 구간만 계산한다(r2 반영).

지금(확인): 표 선택의 `select/evidence.py resolve_period`는 '최근 N년'만 날짜로 풀고 최근 N개월·분기·반기는 풀지 않는다. B는 표 최신 시점 기준으로 모든 단위를 푼다. 같은 질문에서 A의 covers와 B의 실제 조회 구간이 다를 수 있다.

A가 할 일:
1. 기간 적합 판정에 B의 공유 해석기(제안: `resolve_period(conditions, table) -> {frequency, applied, source, assumptions}`)를 쓰거나, 최소한 같은 규칙으로 맞춘다. 주기를 말하지 않으면 '말 → 기간 단위 → 단일 주기 → 가장 긴 주기', 기간을 말하지 않으면 최근 구간 가정(사용자 결정 ①②).
2. 모든 기간·주기·기준 조건이 요구의 `condition_ids`/`shared_condition_ids`에 들어가고, 정하지 못한 것은 `ambiguous_condition_ids`로만 가게 한다(지금 그렇게 동작, 확인. 바뀌지 않게 유지).
3. 완료 판정: 저장 표본에서 A covers의 기간과 B `period.applied`가 같은 표·같은 조건에서 일치.

## 4. 되묻기는 한 군데에서

목표: A와 B가 각자 묻지 않고 "묻는 재료"만 내고, 라우터가 숫자가 달라지는 차원 하나만 골라 한 번 묻는다. 답은 그 값을 처음 쓴 단계부터 다시 돈다.

지금(확인): A는 `selection_route.questions[]`(한 차례 최대 3개, 선택지 최대 5개, `effect_kind`)로 재료를 낸다. router 변형에는 `ask_user` 노드가 있다. B는 `ask`(series_count/unit/condition)와 `resume_at`만 낸다.

A가 할 일(제안, 라우터 담당과 함께):
1. 질문 재료 공통 모양: `{dimension, options[], changes_numbers: bool, resume_stage: interpret | select | B_context | B_select, requirement_ids}`. `changes_numbers`는 선택지에 따라 조회될 계열·수치가 달라지는지(예: 같은 값을 주는 family 표 사이 선택은 false).
2. A 안에서 사용자에게 직접 묻는 경로는 라우터로 옮기고, A는 재료만 낸다.
3. 답 적용 지점: 표 답은 select부터, 해석 답은 interpret부터. 기간·주기는 묻지 않지만(가정·기록), 사용자가 대안 주기·기간으로 바꾸면 B_context부터.

## 5. B 쪽 일정(참고)

B 2단계: 공유 기간·주기 해석기 → 3단계: `preview_fit` + 1·2순위 후보 받기 → 4단계: 대응표(먼저 B 쪽 사본) → 5단계: 질문 재료 계약. A가 1·3번을 붙이려면 B 2·3단계 함수가 먼저 있어야 한다.
