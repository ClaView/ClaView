## 1. 제공 리소스는 무엇인가?

| 구분 | 제공 리소스 | 입력 → 출력 | ClaView에서 맡길 수 있는 일 |
| --- | --- | --- | --- |
| 대화·생성 모델 5종 | HCX-DASH-001/002, HCX-003/005/007 | 지시·질문·근거 → 문장 또는 지원 기능의 구조화 결과 | 질문 해석, 후보 차이 설명, 되묻기, 결과 설명 |
| 임베딩 2계열 | Embedding v1/v2 | 텍스트 → 숫자 벡터 | 질문과 메타 문서의 의미 유사도 검색 |
| 검색 문서 기반 응답 도구 | Re-ranking Model | 질문·검색된 문서 → 답변·인용·재검색 제안 | 근거 기반 응답 보조 후보 |
| 검색 도구 연계 응답 모델 | RAG Reasoning Model | 질문·도구 정의/실행 결과 → 도구 호출 제안 또는 근거 답변 | 검색 도구 선택과 결과 기반 설명 후보 |

대화 모델 5종은 검색 전용 모델이 아닙니다. 검색 후보를 해석하는 데 활용할 수 있지만, 메타 수집·색인·검색·KOSIS 조회는 애플리케이션에서 구현합니다.

임베딩 v1에는 `clir-emb-dolphin`과 `clir-sts-dolphin`이라는 세부 선택지가 있습니다. 현재 v1 시험은 전자만 수행했습니다. 따라서 '제공 리소스 9종'과 '모든 세부 모델·기능을 시험했다'는 서로 다른 말입니다.

공식 역할: [대화 모델](https://guide.ncloud-docs.com/docs/clovastudio-model), [임베딩 v1](https://api.ncloud-docs.com/docs/clovastudio-embedding), [임베딩 v2](https://api.ncloud-docs.com/docs/clovastudio-embeddingv2), [리랭커](https://api.ncloud-docs.com/docs/clovastudio-reranker), [RAG Reasoning](https://api.ncloud-docs.com/docs/clovastudio-ragreasoning).

## 2. RAG 방식과 RAG Reasoning API의 차이

**RAG는 검색한 외부 근거를 모델 입력에 제공하는 구현 방식입니다. RAG Reasoning은 그 방식에 활용할 수 있는 NCP의 특정 API입니다.**

ClaView의 메타데이터 RAG는 다음과 같이 구성할 수 있습니다. 아래는 설계안이며 구현 완료를 의미하지 않습니다.

```text
준비: KOSIS 목록·메타 → 검수·검색 문서 → 키워드 색인 / 임베딩 색인
                                                    ↓
질문 → 조건 해석 → 후보 검색 → 근거를 받은 모델의 조건 확인·설명
                                      ↓
                         코드로 메타·조회 조건 검증
                                      ↓
                         KOSIS 수치 조회 → 가공·결과
```

| 방식 | 검색을 실행하는 주체 | 생성·판단 담당 | 선택 시 확인할 것 |
| --- | --- | --- | --- |
| 자체 RAG | 팀의 검색 코드 | 선택한 HCX 대화 모델 | 검색 후보와 확인 질문 정책을 직접 제어 |
| RAG Reasoning 활용 | API가 제안한 도구를 팀 코드가 검증·실행 | RAG Reasoning API | 도구 결과 재전달·인용·오류 처리가 요구에 맞는지 |

두 방식 모두 자체 메타 저장소와 검색 기능이 필요합니다. RAG Reasoning API가 KOSIS를 자동 수집하거나 벡터 DB·MCP 서버를 대신 제공하지는 않습니다. 서로 다른 단계에 두 방식을 병행할 수도 있지만 처음부터 중복 도입할 필요는 없습니다.

메타데이터 RAG를 사용해도 원자료 수치는 KOSIS API에서 얻습니다. 관련 계열을 검색했다는 사실만으로 수치·기간·통계 기준이 검증되는 것은 아닙니다. 공통 흐름과 책임은 [아키텍처 초안](../architecture/처리흐름과_기능별_책임.md)을 따릅니다.

## 3. 공식 사양 중 선택에 영향을 주는 차이

### 대화 모델

| 모델 | API | 컨텍스트 / 별도 입력 상한 | 출력 상한 | 도구 호출 | 구조화 출력 |
| --- | --- | --- | --- | --- | --- |
| DASH-001 | v1 | 4,096 / 3,500 | 4,096 | 미지원 | 미지원 |
| HCX-003 | v1 | 8,192 / 7,600 | 4,096 | 미지원 | 미지원 |
| DASH-002 | v3 | 32,000 | 4,096 | 지원 | 미지원 |
| HCX-005 | v3 | 128,000 | 4,096 | 지원 | 미지원 |
| HCX-007 | v3 | 128,000 | 32,768 | 지원 | 지원 |

컨텍스트는 입력+출력 합계입니다. 각 최대값을 동시에 사용할 수 있다는 뜻이 아닙니다. HCX-005는 이미지 입력, 007은 추론도 지원하지만 현재 과업의 필수 기능은 아닙니다. 007 추론 출력 예산에는 추론 토큰이 포함됩니다.

출처: [공식 모델표](https://guide.ncloud-docs.com/docs/clovastudio-model), [v1 제한](https://api.ncloud-docs.com/docs/clovastudio-chatcompletions), [v3 제한](https://api.ncloud-docs.com/docs/clovastudio-chatcompletionsv3), [007 추론](https://api.ncloud-docs.com/docs/clovastudio-chatcompletionsv3-thinking).

### 임베딩·응답 도구

- 임베딩 v1: 입력 최대 500토큰. v2: 최대 8,192토큰. 둘 다 1,024차원입니다.
- 모델 변경 시 기존 벡터와 혼합하지 않고 같은 문서 버전을 다시 임베딩합니다.
- NCP 리랭커의 공개 출력은 답변·인용·재검색 제안입니다. 인용 순서를 문서별 관련도 순위로 간주하지 않습니다.
- RAG Reasoning은 검색 도구와 결과를 주고받는 구현이 필요합니다. 첫 도구 제안 성공은 최종 답변 성공이 아닙니다.

정확한 경로·필드·지원 조합은 [API 가이드](NCP_API_활용가이드.md)에서 확인합니다.

## 4. 모델은 언제 결정하는가?

최종 선택은 해당 기능의 구현·평가 시점에 합니다. 다만 구현을 시작할 임시 기준선까지 미룰 필요는 없습니다. 다음 표는 기존 마일스톤에 연결한 **선정 시점 제안**이며 일정 확정본은 아닙니다.

| 시점 | 결정·확인할 것 | 판단 자료 |
| --- | --- | --- |
| 1주차: 데이터·환경 준비 | 리소스 역할·접근·입출력 파악, 비교 후보·시험 예산 제안 | 공식 사양, 현재 호출 결과, 검수할 메타·질문 |
| 2주차: 자연어 검색 | 검색 문서 단위, 임베딩과 대화 모델의 1차 선택 | 키워드 기준선, Recall@k, 조건 확인 정확성, 토큰량 |
| 3주차: 조회·MCP | 도구 호출이 필요하면 지원 모델·인자 검증 방식 결정 | 유효 코드 선택, 도구 실행·결과 재전달 시험 |
| 4주차: 전체 연결 | 설명 모델·RAG Reasoning 도입 여부를 통합 흐름에서 확인 | 대화 상태, 근거 충실성, 전체 지연·실패 복구 |
| 5~6주차: 평가·개선 | 오류가 큰 단계만 후보 재비교하고 변경·유지 결정 | 같은 평가셋, 회귀 시험, 품질·비용·시간 |
| 7주차: 정리 | 최종 설정·한계·재현 방법 기록 | 고정 버전과 최종 평가 결과 |

임베딩은 색인 구축 전 1차 선택이 필요합니다. 이후 변경할 수 있지만 재색인 비용이 발생하므로 모델·문서 버전을 함께 저장합니다. 출력 스키마·도구 계약은 특정 모델에 종속시키지 않는 방향으로 검토합니다.

현재 제안은 대화 DASH-002/005 비교, 임베딩 v2 초기 후보입니다. 성능 우위나 채택 확정이 아니라 [실측 결과](../evaluation/NCP_초기호출_검증결과.md)를 바탕으로 한 시작점입니다.

## 5. 선택 전에 준비할 근거

| 준비 내용 | 확인 방법 |
| --- | --- |
| 공통 입력 | 메타 담당의 검수 스냅샷 + 매핑 담당의 일상어·후보·구별 조건 |
| 기대 행동 | 정상·모호·불가 질문의 정답 조건을 팀 공동 검수 |
| 입력량 | 전체 축약 목록 / 상위 5·10·20개 후보 / 선택 표 상세 메타를 구분 |
| 대화 비교 | 같은 질문·후보·프롬프트·출력 예산으로 모델만 변경 |
| 검색 비교 | 같은 정답 질의·문서 집합, 키워드 기준선과 임베딩 비교 |
| 비용·시간 | 전체 호출 수·입출력 토큰·재시도·관측 지연 포함 |

개발용 6~10개 질문으로 시작할 수 있으나 최종 평가셋과는 분리합니다. 입력 한도 안에 들어간다는 사실과 정답을 잘 찾는다는 사실도 구분합니다.

입력량은 문자 수 추정이 아니라 해당 모델의 공식 토큰 계산기로 확인합니다. 지침·질문·이력·도구 정의·출력 스키마도 포함하고 출력 예산과 안전 여유를 남깁니다. 현재 시험 CLI에는 전체 메타 토큰 분석 기능이 없습니다. [공식 v3 토큰 계산기](https://api.ncloud-docs.com/docs/clovastudio-tokenizerhcxv3)

지표·분모·판정 양식은 [골든셋과 평가계획](../evaluation/골든셋과_평가계획.md), 채택·보류 기록은 [설계결정](../decisions/설계결정과_검토사항.md)에서 관리합니다. NCP 모델별 실측값은 이 문서에 중복 기재하지 않습니다.
