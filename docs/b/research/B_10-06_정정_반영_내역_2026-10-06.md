## 6. 상대기간 flow 변경 (2026-10-06, 팀 결정)

| 구분 | 내용 |
|---|---|
| 기존 | 상대기간 질의에서 표의 최신 수록 시점이 현재 시점(as_of)보다 앞서면 B가 안내 메시지를 전달하고 `status="needs_confirmation"`으로 멈춤. 조회 단계로 진입하지 않음 |
| 변경 | 같은 경우에 `needs_confirmation` 상태를 안내로 저장하고 조회 단계까지 진행함. 이용자에게 진행 여부를 묻지 않고 조회 가능한 기간만 안내함 |

### 6-1. 동작

- B(`BSteps.context`)는 `resolve_relative_period`의 결과가 `needs_confirmation`이면 종료하지 않고, 해석된 기간(`resolved_period`)을 그대로 선택·검증 단계에 사용함. 표별 안내를 `period_notices`에 모음.
- B 결과는 status `ok`이며 `result.selections`와 함께 `result.period_notices`를 가짐. 안내가 없는 질의는 `period_notices` 키 자체가 없음(기존 결과 형태 유지).
- 안내 항목: `table`, `status`(`needs_confirmation`), `code`(`period_requires_confirmation`), `requested_as_of_period`, `resolved_period`, `message`.
- 안내 문구는 질문형이 아닌 안내문으로 변경함(예: "…표의 최신 수록 시점은 202608입니다. 조회 가능한 기간으로 자료를 조회합니다. / 조회 기간: 202309 ~ 202608"). 문구는 세 경우로 구분함: 작년 기간 일부 미수록, 최신 수록 시점이 요청 시점보다 앞섬, 표의 수록 시작 시점이 요청 시작보다 늦음.

### 6-2. 저장·응답 경로

| 위치 | 내용 |
|---|---|
| `candidate_store` (B 시도 기록) | B 결과가 `ok`이므로 시도 상태는 `succeeded`. 저장된 결과에 `period_notices`(status `needs_confirmation`)가 포함되어 재시작·`retry_b`에서도 재사용됨(모델 재호출 없음) |
| `fetch_data` | `b_result.period_notices`를 조회 결과(`data_result.period_notices`)로 전달함. 조회 요청 기간은 해석된 기간임 |
| 파이프라인 응답 | `response.notices`로 안내를 노출함. `response.confirmation`은 더 이상 기간 안내에 쓰이지 않음 |
| `stages.py` `resolve_relative_period` | 반환 형태는 유지함(status `needs_confirmation`, code `period_requires_confirmation`). 호출부의 처리만 변경됨 |
