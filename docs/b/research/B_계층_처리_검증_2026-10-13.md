[B 계층 처리 설계](../design/B_계층_처리_설계.md)의 구현 경과와 실제 모델(HCX-007) 확인 결과를 기록함. 확인된 결과, 해석, 미확인 사항을 구분해 적음. 1~6장은 2026-10-12 기준이고, 2026-10-13의 골든 22건 전체 실행과 기간·이름 보정은 7장에, 2026-10-15~16의 요청 한도 확인과 모델 전달 표 축소는 8장에 적음. 4장·5장·6장의 일부 서술은 7장과 8장으로 갱신되었음.

### 3.2 해석

- 12/12 중 모델의 `expand` 지정이 의도와 맞은 것은 09뿐임(그것도 `[참고]` 제외가 필요했음). 08·10·13은 모델이 원하는 확장을 하지 않았고 코드 규칙이 바로잡았음.
- 5장의 보정 규칙은 앞선 회차의 실패 4건(08, 09, 10, 13)을 보고 만든 것임. 12/12는 이 4건에 맞춘 뒤의 결과이며, 다른 질문에서의 일반화 증거가 아님. 골든에서 `expand`가 필요한 질문은 이 4건뿐임.
- 모델은 같은 입력에서도 회차마다 다르게 답한 적이 있음(CV-AB-10: 한 회차에서 `SUM`에 `children`, 이후 3회는 전부 `none`). 한 번의 통과를 안정적이라고 보지 않음.
- 프롬프트로 "이름으로 말한 하위는 각각 선택하라"고 요구해도 모델이 따르지 않았음(05번은 회차 4, 13번은 회차 7의 3회). 그래서 같은 내용을 코드 규칙으로 처리함.
- 분해 표현이 없는 질문에 `expand` 스키마를 주면 관련 없는 필드에도 영향이 있었음(17번의 종료월이 빈 값, 05번의 하위 확장). 분해 표현이 있을 때만 주는 구조로 바꾼 뒤 05번이 3/3으로 돌아옴.

## 4. 요청 크기와 HTTP 429

- 약 131,000자 요청(DT_301Y013)에서 HTTP 429가 반복됨. 약 110,000자 요청(DT_402Y014)은 정상이었음.
- 실행 간격을 늘리거나 재시도해도 같은 요청에서는 계속 429였고, 후보를 약 30,000자로 줄이자 정상 응답했음. 요청 크기가 원인이라는 증거는 강하지만 서버 쪽 원인을 직접 확인한 것은 아님.
- 한도 120,000자는 정상 구간(110,000)과 실패 구간(131,000) 사이의 추정치임. 정확한 경계는 확인하지 못했음.
- 2026-10-16 갱신: 429의 원인은 문자 수 자체가 아니라 분당 토큰 한도(현재 키 60,000)로 보임(8.1). 요청을 축소하는 방법과 한도의 현재 의미는 8장과 설계 문서 8장을 따름.

### 7.3 재확인 호출·순서 반전·힌트 실험

- 이름이 비슷한 값을 잘못 고르는 질문에서 기본 호출과 "고른 값이 질문과 맞는지 한 번 더 묻는" 호출을 비교함(`scripts/b_part/experiment_value_selection_hcx.py`). 두 방법 모두 틀린 선택을 그대로 반복해 통과하지 못했음. 같은 입력에서 같은 오답이 결정적으로 반복되는 것으로 해석하며, 이를 근거로 이름 규칙을 코드에 둠.
- 후보 순서를 뒤집는 방식과 힌트를 주는 방식은 도구에 준비했으나 실제 모델로 돌리지 않았음. 효과는 미확인임.

### 7.4 해석과 한계

- 통과한 질문 중 12·17·21번은 모델의 선택이 그대로 틀렸고 코드 규칙이 바로잡은 것임. 기간 관련 질문(16·18·19·20번)은 코드가 기간을 계산한 결과임. 모델의 판단이 좋아진 것이 아님.
- 이름 규칙 3가지는 위 실패에서 도출했고, 골든 22건의 정답을 넣어도 바뀌는 값이 없음을 시험으로 확인한 것이 검증의 전부임. 다른 질문에서의 효과와 오탐은 확인하지 못함. 넓은 규칙(이름이 한쪽 방향으로라도 겹치면 교체)은 골든 05·17번을 바꿔 채택하지 않았음.
- 마지막 전체 실행은 질문당 1회이고, 같은 입력에서도 코드·문맥이 바뀌면 답이 달라진 사례가 있음. 안정성은 확인하지 못함.
- 04번에서 `resolved_period`를 보여주면 항목을 과다 선택하는 이유는 확인하지 못함. 보여주지 않는 쪽이 맞았다는 비교 결과만 있음.
- 가지치기 없이 약 131,000자로 보낸 04번이 429였다는 것은 요청 크기가 원인이라는 근거를 보강하지만 서버 쪽 원인을 직접 확인한 것은 아님. `max_b_context_chars=120000`은 계속 추정치임.
- 항목 경로를 압축해 보내면 04번 약 63,000자, 16번 약 113,000자, 18번 약 186,000자로 줄어든다고 추정했으나 모델에 보내는 형식이 전 질문에서 바뀌므로 구현하지 않았음(18번은 압축해도 한도를 넘음).

### 8.3 해석

- CV-AB-03은 저장 형식 표에서는 어느 프롬프트로도 통과했고, 축소한 표에서 `is_leaf`를 false에만 쓸 때 새 프롬프트에서만 실패했음. `is_leaf`를 모든 값에 쓰거나 `path`를 이름 목록으로 되살리면 통과함. 표 형식과 프롬프트 문구의 조합이 영향을 준 것으로 보이며, 둘 중 하나만이 원인이라고 단정하지 못함.
- `under`는 필요함(빼면 다른 가지를 고름). 다만 `under`만으로는 충분하지 않았음.
- 채택한 수정: `model_table`이 `is_leaf`를 모든 값에 쓰도록 함. 이에 맞춰 `expand` 프롬프트의 `is_leaf` 문장도 원래 문구("is_leaf가 true인 값에는 쓰지 않는다")로 되돌렸으나, 되돌린 뒤의 조합은 아직 모델로 확인하지 않았음(8.5).
- 변형당 1회, `temperature=0` 실행이라 반복해도 독립 표본이 아님(03번 3회가 모두 같은 오답이었음).
- 회차 5의 22/22는 질문당 1회 결과임. `expand`가 쓰인 5건(07, 08, 09, 10, 13) 중 07·10·13에서는 모델이 최하위 값에 `expand`를 붙여 코드가 `none`으로 낮췄고(`expand_on_leaf` 3건), 08은 `children`을 `leaves`로 올렸고(1건), 10은 미사용 보정이 작동함(1건). 통과가 코드 보정에 기대는 정도는 이전 결과와 같은 성격이며, 10-13 실행의 같은 수치는 이 기록에 없어 증감은 비교하지 않았음.
- 회차 7(프롬프트 문구 정리 후)도 22/22이고 질문당 1회임. `expand` 관련 수치는 회차 5와 거의 같음(최하위 값에 `expand`를 붙여 코드가 낮춘 질문 3건: 07, 10, 13, 승격 1건: 08). 달라진 점은 미사용 보정이 0건으로 줄었고(회차 5는 10번에서 1건), CV-AB-10에서 모델이 두 축 모두 `children`으로 답했다는 것임(회차 5는 `SUM` 축을 `none`으로 답함). 최종 계열 8개는 같음. 같은 질문에서도 문구가 바뀌면 모델의 `expand` 지정이 달라지며, 통과는 코드 보정에 기대는 부분이 있다는 점은 이전과 같음.
- 회차 6: 가지치기 없이 보내면 04번은 서비스·본원소득·이전소득 수지를 빼고 하위 5개(110000, 120000, 210000, 310000, 410000)를 골랐고, 05번은 정답 5개에 하위 13개를 더해 18행을 냈음. 요청 자체는 정상 처리됨(429 없음). 가지치기를 적용하면 둘 다 통과하므로, 가지치기는 요청 크기 대응이면서 후보를 줄여 과선택을 막는 효과도 있는 것으로 추정함. 이 효과만 분리한 실험은 아님. 그래서 가지치기 기준(저장 형식 크기 120,000자)은 바꾸지 않았음.
