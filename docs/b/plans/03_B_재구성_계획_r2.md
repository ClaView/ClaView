## 1. 바꿀 것의 모양 (계약 먼저)
### 1.1 B 입력 (새 A → B)
`BRequest = {question, as_of, scopes:[{scope_id, tables:[{org_id, table_id, table_name}], decision: auto|confirm, hints}], skipped:[{scope_id, reason}], route, relations, table_group_hint, source}` (구현: `src/claview/b/contract.py`)
- scope_id = 새 A의 requirement_id. 표는 Selection.tables 중 status가 auto/confirm인 것만. no_table 요구는 B에 오지 않고 unresolved로 남는다.
- hints(모두 선택 칸, 없으면 지금처럼 원문에서 읽음): text, indicator·targets·breakdown 이름, conditions(고유+공통, {id, kind, quote, value, attrs}: period PeriodAttrs, frequency 코드, basis, unit, exclude, calc), ambiguous_condition_ids(적용하지 않음), value_mentions({table_id, obj_id, value_id, name, method, role, relation, parents}), covers, a_period_request(대조용).
- value_mentions의 출처: claview_v3 최종 상태에는 evidence 문서의 MatchedItemRow가 없고(요약만 남음) `selections[].signals.facts.tables[표].indicator.occurrences[]`가 있다. value_id는 B 메타 코드와 같다(확인). occurrence에는 polarity가 없어서, '긍정' 판정은 M4에서 조건의 polarity와 `judgement.negated`로 따로 한다(확인된 제약).
- 어댑터 `to_b_request(state)`(claview_v3 최종 상태) 하나만 새 A 모양을 안다. selection_route는 {kind, confirm, partial, reasons, requirement_ids}만 기록하고, proceed가 아닐 때 B를 부를지는 라우터가 정한다.

### 1.2 B 출력 (요구 단위)
`BScopeResult = {scope_id, status: ok | ask | unresolved | table_unsuitable, series[], period, frequency, assumptions[], decided, notices[], issues[], ask?}`
- period = {source: question_a | question_rule | assumed_recent | user, requested, applied, notice?}
- frequency = {source: question_a | question_rule | period_unit | table_single | assumed_longest | user, chosen, alternatives[]}
- decided = 축마다 code | model | expand (어떻게 정해졌는지)
- issues[] = {code, kind, retryable, resume_at} — kind: input | condition | model | validation | data. resume_at: A_reselect | ask_user | B_context | B_select | fetch
- ask = {kind: series_count | unit | condition, message, options[]} — 주기·기간은 묻지 않는다(9절 결정 1·2)
- assumptions[] = {dimension: period | frequency, value, rule} — B가 가정한 값(9절 결정 3)
- ask는 되묻기 재료만 만들고, 묻는 일은 라우터가 한다.
- 호환: series마다 scope_id를 붙이고, `fetch_selections`가 ok scope의 series를 지금 fetch가 받는 평평한 `selections` 모양(scope_id 제거)으로 바꾼다. 계열→scope 대응은 `series_scopes`.

## 10. 단계별 모양 (클라우드 r2·표 선택 스레드 합의, 2026-10-20 07:56 코디네이터 전달)

구현은 단계마다 사용자가 진행을 승인한 뒤에 한다. 2단계는 승인 대기.

| 단계 | 내용 | 함수·모양 |
|---|---|---|
| 2 | 공유 기간·주기 해석기, A 조건으로 구간 계산·가정 기록, 표 부적합 분리(M2·M3·M7) | `resolve_period_for_table(conditions, table_meta, as_of) -> {frequency, applied, source, assumptions}` |
| 3 | 어댑터가 확정 표 + 첫 대안 묶음을 넘김, 후보마다 코드 매핑(모델·외부 호출 0), 저장 표본으로 되묻기 감소 세기 | `preview_fit(requirement, table) -> {fit: ok \| partial \| no, reasons, series_estimate, fixed_axes, open_axes, assumptions}` |
| 4 | 이름 → 표·축·값 코드 대응 행 | `{name_id, quote, span, table_id, obj_id, value_id, value_name, role, path, negated}` |
| 5 | 되묻기 재료 | `ask = {scope_id, dimension, changes_numbers, options, resume_at}`, `resume_at`에 `A_next_alternative` 추가 |

조건 칸 모양: `{value, source: question | catalog | default | user, confirmed, applied}`. `applied`는 B가 채운다. (1절 계약의 period/frequency 기록과 맞추는 일은 2단계에서 한다. 지금 계약의 source 값 `question_a`·`assumed_recent` 등을 이 네 값과 어떻게 대응시킬지 2단계 계획에 적는다.)

대표값: B에 새 규칙을 만들지 않고 새 A의 `selection_policy`(대표값 / 전부) 파일을 읽는다(표 선택 스레드와 합의).

카탈로그 전체 메타 오류(`duplicate_catalog_id` 등)의 `resume_at`: 사용자 확인 전까지 지금(`A_reselect`) 그대로 둔다. 제안은 "실패로 끝냄"(재개 지점 없음).

A 쪽 요청은 [A파트_요청_B연결_20261020.md](../handoff/A파트_요청_B연결_20261020.md)에 있다. 위 합의와 다른 곳(대응 행 필드 이름, 미리보기 반환 필드, `resume_stage`/`resume_at` 이름)은 합의 쪽을 따른다.

## 9. 결정 (최종: 2026-10-20 07:41 사용자 '맞춰 계속')

처음(같은 날) 권장안 7개를 모두 승인했다가, 공유 폴더의 r2 계획과 아래 결정에 맞추기로 바꿨다. 이 파일은 그 결정을 따른다. 공유 폴더 r2 원문은 이 PC에서 읽지 못해 결정 목록 기준으로 맞췄다.

1. 주기를 말하지 않으면 되묻지 않는다. 순서: 질문의 주기 말 → 기간의 단위("최근 3분기"면 분기) → 표 주기가 하나면 그것 → 여럿이면 가장 긴 주기를 쓰고 나머지는 대안 주기로 안내.
2. 기간을 말하지 않으면 되묻지 않고 그 주기 기준 최근 구간을 가정한다(예: 연 10·분기 5·월 3년; 숫자는 M3 구현 때 확정해 보고).
3. 가정한 값은 결과 `assumptions[{dimension, value, rule}]`에 남긴다. 기간 출처 `assumed_recent`, 주기 출처 `assumed_longest`이면 assumptions에 그 항목이 있어야 한다(계약 검사).
4. 계열 30개 상한은 scope(요구) 단위로 센다.
5. A의 이름 힌트는 모델 문맥에 넣지 않는다. 코드 고정과 대조에만 쓴다.
6. 조회가 partial이면 받은 계열과 결측 안내를 C로 넘긴다.
7. 모델: HCX 기본 + OpenAI 어댑터 자리. 실호출은 승인 뒤.
8. 입력 계약: 요구 단위(안 A, 지금의 새 A → `adapter_v3`)와 질문 단위(안 B, 보류 가능성 큼 → `adapter_question`) 둘 다 어댑터로 받고, B 안은 scope 단위 하나로 돈다.
9. 작업 폴더: `claview-b-1020`에서 구현한 뒤 확인받고 claview에 병합.
10. 작업 방식(10/20 16:04): 관찰 전용 경로 없이 바로 바꾸고, Codex 검수는 계약·관문 규칙 묶음 끝에 1회.

이 결정으로 바뀐 곳: 1.2절의 ask는 frequency·period를 묻지 않는다(ask.kind = series_count | unit | condition). M3는 '되묻기'가 아니라 '가정 + assumptions 기록'으로 구현한다.
