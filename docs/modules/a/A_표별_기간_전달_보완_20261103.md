# A 표별 기간 전달 보완

2026-11-03 · `4ad800d` 통합 작업본에서 구현·오프라인 확인

## 바뀐 동작

서로 다른 표가 각기 다른 단일 기간을 맡을 때, A가 기간 차이만으로 전달을 일괄 차단하던 동작을 보완했다. 예를 들어 두 표의 요청 연도가 각각 2023년과 2024년이면 A는 두 기간을 그대로 준비하고, 파이프라인이 연결된 B의 수신 능력을 확인한 뒤 전달한다.

**옮긴 것은 `period_differs_between_requests` 한 가지뿐이다.** A의 선택·조건 검증이나 다른 차단을 전부 B에 맡기는 변경이 아니다. 정책·모델 지시문·출력 계약·A/B 기간 계약도 바꾸지 않았다.

## 구조와 경계

1. [A view.py](../../../modules/a/claview_a_api/view.py)의 표 간 기간 일괄 차단을 제거했다. 통계별 표·기간·주기·focus·사용자 답은 그대로 보존하고 표별 `period_condition`을 준비한다.
2. [파이프라인 screen.py](../../../pipeline/claview_pipeline/screen.py)가 수신부를 확인한다. 다음 두 조건을 **모두** 충족해야 서로 다른 기간을 넘긴다.
   - B가 `accepts_period_context=True`를 명시한다.
   - 전달할 모든 요청에 준비된 `period_condition`이 있다. 이는 `accepts_period_condition=True`인 B 경로에서만 붙는다.
3. 파이프라인은 원래 `view.handoff.ready`에 있던 요청들의 기간을 `frozenset`으로 비교한다. 준비 실패나 사용자 답 미지원으로 일부 요청이 먼저 제외돼도, 남은 요청 하나가 구형 B 차단을 우회하지 못한다.
4. 지원 B에는 기존 [staged.py](../../../pipeline/claview_pipeline/staged.py)의 묶음별 호출과 `period_context`로 다른 표의 기간 문구를 함께 전달한다. 표별 해석·사용자 답 우선순위·B 결과 검증은 기존 경로를 사용한다.

| 상황 | 처리 |
|---|---|
| 다른 표·다른 단일 기간, 조건과 문맥 모두 지원 | 기간을 합치거나 줄이지 않고 묶음별 전달 |
| 구형 B 또는 `period_context` 미지원 | `period_differs_between_requests`로 차단 |
| 기간 조건 준비 실패가 있어 안전한 전달이 불가능 | 차단; 준비 안 된 조건을 버리고 진행하지 않음 |
| 사용자 답 요청을 구형 B가 못 받아 일부 제외 | 제외 전의 기간 차이를 검사해 남은 요청의 우회 전달도 차단 |
| 같은 표를 사용하는 통계의 조건 충돌 | 기존 `same_table_conditions_differ` 유지 |
| 떨어진 여러 구간 | 기존 `disjoint_period_not_in_b_contract` 유지 |
| 판본별 표 분할 | 기존 `edition_period_split` 유지 |
| B가 사용자 답을 적용하지 않음 | 기존 사용자 답 보존 검사와 조회 중단 유지 |

지원 B가 기간 조건을 받는 것과 실제 모델 요청에 그 값을 잘 반영하는 것은 다른 문제다. 이번 실측에서 발견한 **B의 사용자 답 기간 미노출**은 이 변경으로 해결되지 않으며 [B·C 보완 요청](B_C_연결_실측_보완요청_20261103.md)의 B-1에 따로 남겼다.

- 파이프라인 API 14건 통과.

위 수치는 Docker/서비스 변경을 포함한 통합 작업본이다. 이번 A 보완만 최신 main에 분리한 PR 작업본에서도 A API 195건, 파이프라인 246건, 파이프라인 API 4건이 모두 통과했다. 두 작업본 모두 묶음별 별도 프로세스로 실행했고 외부 연결 차단을 유지했다. 분리 작업본에는 Docker/서비스 신규 시험이 없어 건수가 다르다.

추가·수정한 직접 검증은 다음을 포함한다.

- 서로 다른 표에 확정한 기간·주기와 답의 적용 통계·출처 보존.
- 실제 A 송신부 → 파이프라인 묶음별 호출 → 실제 BService 경로에서 표별 기간 분리. 기존 시험의 A 차단 우회용 monkeypatch는 제거했다.
- 조건 미지원·문맥 미지원·준비 실패 수신부에 대한 차단.
- 사용자 답 요청이 먼저 제외되면서 남은 요청 수가 하나가 되는 조합. 실제 답 적용·재개 경로에서 B·KOSIS 전송 0을 확인했다.
- 같은 표 조건 충돌·불연속 기간·판본 분할과 사용자 답 보호의 기존 회귀.

## 저장 12문항 재생

새 모델 호출 없이 기존 실측 응답을 사용했다. 비교 증거의 `exact_request_matches`는 **기존 저장 HTTP 요청 50건의 JSON이 일치**했다는 뜻이다. 파일 해시 일치나 모델 정확도 향상으로 바꾸어 표현하지 않는다.

| 구분 | 결과 |
|---|---|
| 기존 저장 요청 대응 | A 14 + B 13 + KOSIS 23 = 50건 모두 요청 JSON 일치 |
| 원자료 보존 | 비교 대상 기존 파일 64개 불변 |
| 외부 전송 | 0회 |
| 결과 불변 | 11문항, 비교 필드 변화 없음 |
| 결과 변경 | `FN-TWO-PERIODS` 1문항: `unsupported → ok` |

변경 문항은 최초 실측에서 A가 막았으므로 실제 B/KOSIS 응답이 없었다. 따라서 **A는 저장 실제 응답**, **B 모델 응답 2개와 KOSIS 응답 2개는 새 합성 자료**, **BService·C는 제품 코드**로 확인했다. KOSIS 합성 값은 모두 1이다. 이 결과는 조건 전달과 연결 경로의 정상 동작을 보여 주며, B 모델 선택 품질이나 실제 수치가 맞는지는 보여 주지 않는다.

기존 실측에서 미해결이었던 기간 답 문항과 전년동월비 계산 문항은 그대로다. 이번 변경으로 이 두 건까지 해결했다고 보고하지 않는다.

제품 프론트엔드에서 저장 기록을 불러와 7개 상태를 확인했다. 콘솔 경고·오류와 외부 호출은 모두 0이었다.
