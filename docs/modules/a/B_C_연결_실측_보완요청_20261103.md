# B·C 연결 실측 결과와 보완 요청

2026-11-03 · 최초 실측 기준 `4ad800d` · A 전달 보완 후 오프라인 결과 반영

## 요약

기준일 `2026-10-29`로 12문항을 실제 A → B → KOSIS → C 경로에서 확인했다. 골든 일부와 기능 점검 문항을 섞은 개발 확인이며, 독립 평가나 골든 전체 통과 결과는 아니다. 질문·기대값은 호출 전에 고정했다.

- A가 최종 확정한 **표·기간·주기**는 12문항 모두 기대와 같았다. 이것은 모든 focus 조건까지 엄격 기준으로 통과했다는 뜻은 아니다.
- 제한 재선택 1건과 재검색 1건은 기존 복구 1회 안에서 해결됐고, 정상 focus·기간·주기·계산·분류 조건을 보존했다.
- 실제 조회된 **23계열, 428개 값**은 KOSIS 원응답 → C 전달값 → 화면 전달값까지 일치했다. 통계 수치 자체를 외부 독립 원천과 대조한 것은 아니다.
- 실행 상태는 `ok` 10건, `unresolved` 1건, `unsupported` 1건이었다. 기능 충족은 **9건(부분 수록 조회 1건 포함), 미충족 2건, 사전 고지한 연결 한계 1건**으로 구분했다. `ok` 중 한 건은 요청 계산을 하지 못했다.
- 실제 호출은 A 첫 판단 12회·복구 2회, B 모델 13회, KOSIS 23회다. 이번 문서 작성 과정에서는 추가 호출을 하지 않았다.

보완 순서는 **B 사용자 답 전달 → B 비교 기준 구간 → C 계산 지원**을 권한다. **조회 완료와 계산 미완료의 표시 구분은 C 계산 지원을 기다리지 않고 병행**할 수 있다. A의 서로 다른 표 기간 차단 완화는 별도로 구현·오프라인 확인을 마쳤으며, 최초 실측과 아래에서 구분한다.

## 이미 합의한 처리 원칙

1. 사용자 되묻기 답으로 확정한 기간·주기는 해당 필드의 최우선 조건이다. 원문에 없다는 이유로 다시 묻거나 임의 기본값으로 대체하지 않는다.
2. 그 밖의 A 기간은 B가 참고하고, B의 표별 해석·수록 정보로 조회 범위를 결정한다. 차이는 기록하며 사용자 답을 적용하지 못한 경우와 구분한다.
3. 요청 범위·조회 범위·미수록 범위·계산용 앞선 구간은 서로 구분한다. 원자료 값을 보존하고 파생값은 계산한 경우에만 계산 결과로 표시한다.
4. A의 복구는 기존 1회를 유지한다. 이번 B·C 보완 때문에 A 호출을 추가하거나 정상 조건을 완화하지 않는다.

## B-1. 사용자 기간 답을 계열 선택 모델에도 제공

**담당: B. A 송신부는 이번 사례에서 정상이다.**

### 재현과 원인

기능 문항 `FN-PERIOD-ASK`는 기간이 없는 M2 월별 질문이다. A가 기간을 물었고 사전 답 **`2024년 월별`**을 적용했다. A는 다음 내용을 B에 정확히 보냈다.

```json
{
  "frequency": "M",
  "frequency_source": "question",
  "period": [{"start": "2024-01", "end": "2024-12"}],
  "period_source": "user_answer",
  "period_phrase": "2024년 월별"
}
```

실제 요청에는 적용 통계와 답 원문을 담은 `answers`도 있었다. 위 예시는 핵심 조건만 발췌한 것이며 완전한 B 요청 예시는 아니다.

B 내부 기간 계획 이후 모델 요청에는 **기간이 없는 원질문**, `period_policy: "explicit_only"`, **`resolved_period: null`**이 들어갔다. 모델은 `{"selections": []}`를 반환했고 B는 `conditions_incomplete`로 종료했다. KOSIS는 호출하지 않았다.

확인 위치:

- [stages.py](../../../modules/b/claview_b/stages.py)의 `BSteps.context`: `plan["period"]`를 계산한 뒤 `plan["show"]`가 참일 때만 `resolved_period`를 모델에 보여 준다. 기준 버전 2502~2505행에서 사용자 답 기간도 숨긴다.
- 같은 함수의 모델 입력 작성: `selected_tables`에서 `period_condition`을 제거하며, `resolved_period`에는 위의 표시용 값만 넣는다(2530~2536행).
- `canonicalize_selections`: 선택이 비면 기간 덮어쓰기 전에 `conditions_incomplete`로 거절한다(2396~2398행).

따라서 “B가 A 값을 못 받았다”가 아니라 **받은 확정 기간이 계열 선택 모델 요청에는 보이지 않았다**는 문제다. 모델의 빈 응답만 바꾸려 하기보다 입력부터 보완해야 한다.

### 요청 범위

- 사용자 답으로 확정된 기간·주기를 B의 계열 선택 요청을 만들기 전에 반영한다. 가능하면 기존 `resolved_period`를 활용하고, 코드가 확정한 값을 모델이 임의 재해석하지 않도록 한다.
- 필드별 출처를 보존한다. 기간만 답했으면 주기까지 사용자 답으로 바꾸지 않는다.
- 모델이 계열을 반환한 뒤에도 코드의 확정 기간 검증·적용은 유지한다.
- 원질문에 기간을 임의 덧붙이거나, 해당 M2 문항만 예외 처리하지 않는다.

### 완료 기준

1. 실제 `BService`를 가짜 모델 전송기로 실행해, 모델에 보내기 직전 입력에 확정 기간이 들어 있음을 확인한다.
2. 기간만 답한 경우·주기만 답한 경우·둘 다 답한 경우를 구분하고, 원질문의 다른 통계 기간이 혼입되지 않음을 확인한다.
3. 현재 실측의 빈 응답은 실패 원자료로 그대로 보존한다. 올바른 가짜 계열 응답을 사용한 연결 시험에서는 사용자 확정 범위가 조회 파라미터까지 유지돼야 한다.
4. 사용자 답을 적용할 수 없으면 그 사유를 반환한다. 기간 누락으로 다시 분류하거나 조용히 다른 범위로 바꾸지 않는다.

입력 보완과 오프라인 시험 통과는 실제 모델이 새 요청에서 계열을 잘 고른다는 증거와 구분한다. 실제 모델 재확인이 필요하면 별도 승인 범위에서 진행한다.

## B-2. 전년동월비 계산에 필요한 기준 구간 보존

**담당: B. 요청 범위와 계산용 추가 구간을 구분한다.**

### 재현과 원인

`FN-YOY-M2`에서 A는 **전년 동월 대비 증감률** 계산 문구를 보존했다. 요청 표시 기간은 2024년이다. 사전 기대는 2023년 비교값과 2024년 현재값을 조회하고, 2024년의 증감률을 계산하는 것이다.

그러나 실제 B와 KOSIS 요청은 **2024-01~2024-12만** 포함했다. B의 `YEAR_OVER_YEAR`와 `detect_baseline_extension`은 “전년 동월 대비”를 인식하지 않아 추가 기간을 0으로 계산했다. 이 한계는 실호출 전에 코드로 확인했으며 실제 응답에서도 나타났다.

위치는 [stages.py](../../../modules/b/claview_b/stages.py)의 `YEAR_OVER_YEAR`, `detect_baseline_extension`, 명시 기간·사용자 확정 기간의 계산용 확장 처리다(기준 버전 64행, 859~868행, 936~944행, 989~992행).

### 요청 범위와 완료 기준

- 지원하는 비교 표현을 같은 의미로 처리하고, 이 문항·표 ID만 겨냥한 예외를 넣지 않는다.
- 필요한 전년 동월 기준값을 추가 조회하되 **사용자 요청/표시 기간 2024년은 유지**한다.
- 기준 구간은 `calculation_extra`에 목적과 함께 표시한다. 연속 2023~2024 조회 또는 분리 조회 중 기존 계약에 맞는 방식을 사용한다.
- 수록 부족·기준값 결측을 요청 기간 변경이나 0으로 대체하지 않는다.
- 기간 계산 직접 시험, 실제 `BService` 연결 시험, 기존 비교 기간 회귀를 확인한다. 사용자 답 우선순위와 표별 문맥 분리도 유지한다.

## C-1. 직접 계산과 공표값 표시 구분

**담당: C. 계산 지원 범위는 C에서 명확히 한다.**

같은 `FN-YOY-M2`의 C 결과는 `calculation: null`이고 화면에 전달된 단위는 `%`가 아니라 원자료의 **십억원**이었다. [c_analysis.py](../../../modules/c/claview_c/c_analysis.py)의 `calculate_rates`는 지수 단위 및 특정 지수 사례만 지원하므로, B에서 2023년 자료를 추가해도 M2 증감률 계산이 자동으로 해결되지는 않는다.

- 계산을 지원한다면 원응답으로 `(현재값 / 전년동월값 - 1) × 100`을 계산하고 원자료와 파생 결과를 분리한다.
- 계산 기준값의 결측·0 및 부분 계산을 명시한다. 유효하지 않은 값을 0%로 채우지 않는다.
- KOSIS가 이미 증감률을 공표하는 계열은 “공표값 표시”로 구분하며, C가 직접 계산했다고 보고하지 않는다.
- 지원하지 않는 동안은 **요청 계산 미완료**가 명확한 결과로 남아야 한다. 원자료 조회 완료를 전체 요청 충족으로 바꾸지 않는다.

완료 기준은 계산식·단위·표시 기간·현재값/기준값 연결에 대한 직접 시험과, 저장된 실제 원자료를 사용한 재생 대조다. 현재 기록에는 비교 구간이 없으므로 임의 값을 보충해 실제 계산 검증으로 보고하지 않는다. 필요한 별도 합성 기준값은 합성 시험임을 표시한다.

## 연결·화면-1. 조회 완료와 계산 미완료를 분리

**담당: 파이프라인·화면 담당, C와 결과 표현 협의.**

`FN-YOY-M2`는 상위 실행 상태와 C outcome이 `ok`였다. 화면 전달값에는 “C에서 별도 증감 계산이나 최대 변화 시점 판정을 하지는 않습니다”라는 일반 경고가 있지만, 계산 미완료를 나타내는 별도 상태는 없었다.

- 원자료 조회 상태와 요청 계산 충족 상태를 분리한다. 사용자가 계산을 요청했고 계산하지 않았다면 **“원자료 조회 완료 · 요청 계산 미완료”**가 요약과 저장 기록에도 남아야 한다.
- 이번처럼 원자료를 제대로 조회한 사실은 유지한다. 조회 실패로 바꾸거나 실제로 하지 않은 계산 완료를 표시하지 않는다.
- 필요한 계약 필드가 기존에 없다면 C·파이프라인·화면 간 최소 형태를 합의한다. A의 기간·focus 계약 변경과 묶지 않는다.
- 실제 화면과 저장 결과 불러오기에서 같은 상태가 유지되는지 확인한다. 불러오기로 추가 조회를 하지 않는다.

## A의 별도 보완: 구현·오프라인 확인 완료

`4ad800d`의 최초 실측 후, 서로 다른 표의 단일 기간이 다르다는 이유로 A가 전달 전체를 막던 `period_differs_between_requests`를 보완했다. **이 차단 하나만** A의 일괄 차단에서 파이프라인의 수신 능력 검사로 옮겼다. 모든 A 차단을 B로 넘긴 것이 아니다.

[view.py](../../../modules/a/claview_a_api/view.py)는 검증된 표별 기간을 보존해 송신 요청을 준비한다. 파이프라인은 B가 `accepts_period_context=True`를 밝히고, 보낼 모든 요청에 준비된 `period_condition`이 있을 때만 서로 다른 기간을 전달한다. 구형 B·기간 조건 준비 실패·문맥 미지원이면 기존처럼 막는다. 사용자 답 요청이 먼저 제외돼 남은 요청이 하나가 되더라도, **제외 전 `handoff.ready` 전체의 기간**을 비교해 구형 B 보호를 유지한다.

다음 보호는 별개로 유지한다.

- 같은 표에 서로 다른 조건을 합칠 때의 `same_table_conditions_differ`
- 현 계약이 지원하지 않는 불연속 기간
- 사용자 답을 B가 적용하지 못했을 때의 중단
- 판본별 분할 등 이번 범위 밖의 연결 제한

최초 실측의 `FN-TWO-PERIODS`는 옛 차단으로 B·KOSIS를 호출하지 않았다. 보완 후에는 **저장 A 응답 + 실제 BService/C 코드 + 합성 B 응답 2개·합성 KOSIS 응답 2개(값 1)**로 정상 전달·조회·화면 자료 생성까지 확인했다. 이는 새 경로의 오프라인 확인이며 실제 B 모델·수치 검증으로 세지 않는다.

저장 12문항 재생에서 기존 HTTP 요청 50건의 JSON이 모두 일치했다. 다른 11문항은 비교 필드가 그대로이고 `FN-TWO-PERIODS`만 `unsupported → ok`로 바뀌었다. A API 206건, 파이프라인 256건, 파이프라인 API 14건과 Ruff·import 경계 9개 검사가 통과했다.

제품 프론트엔드에서 저장 기록의 7개 상태를 불러와 확인했다. 표별 2023/2024년 차트 2개, 미래 요청·조회·미수록 범위, 되묻기 대기와 답 적용 후 상태가 유지됐다. 콘솔 경고·오류와 외부 호출은 0이었다. 브라우저는 `records/load`만 사용했으며 새 질문·답 전송은 하지 않았다. 답 적용은 저장 응답 재생에서 확인했다. 전년동월비 문항의 원자료 차트와 상위 `ok`·계산 미완료 구분 문제는 기존대로 남았다. 세부 내용은 [A 표별 기간 전달 보완](A_표별_기간_전달_보완_20261103.md)에 있다.

## focus 근거 생략은 별도 기록

GV4-06의 focus에는 백만달러, GV4-19와 BOK-NEW-19에는 2020=100 문구가 없었다. 엄격한 focus 문구 보존 기준의 생략 사실은 그대로 남긴다. 이번 실제 선택 메타·B 결과·KOSIS 응답·화면 단위는 해당 조건을 충족했다.

따라서 **focus에 명시됨 / 선택 메타가 보장함 / 실제 조회 결과가 충족함**을 구분한다. 이번에 단위가 올바르게 나왔다는 이유로 모든 생략을 자동 허용하거나, A의 송신 코드가 조건을 삭제했다고 결론 내리지 않는다. 새 근거·기준값 필드가 필요하면 별도 계약으로 협의한다.

## 별도 서비스 PR의 범위

일반 Docker 실행의 기본 실호출 경로, **서버 복원**을 통한 완료·확인 대기 기록 불러오기, 호출 횟수의 `HCX` 표시를 **B 모델**로 바꾸는 작업은 [서비스 PR #46](https://github.com/ClaView/ClaView/pull/46)에 담았다. 원기록의 집계 키는 보존하고 화면 표시만 바꾼다. 옛 `/sample` 메뉴 제거도 이 서비스 화면 정리에 포함된다. PR 생성과 main 반영은 구분하며, 병합 전에는 서비스 PR 브랜치의 변경이다.

- 일반 실행은 키 등 실행 설정이 준비됐을 때 A → B → KOSIS → C를 사용하며, 설정 부족을 합성 결과로 자동 대체하지 않는다.
- 서버 복원은 보관된 결과를 불러오며 그 자체로 새 모델·KOSIS 호출을 만들지 않는다. 대기 기록의 답을 사용자가 제출하면 후속 실행을 시작한다.
- 이번 문서의 최초 실측 결과는 기준 버전에 그대로 귀속한다. 서버를 켜거나 저장 기록을 다시 표시하는 일을 새 실측 성공으로 세지 않는다.
- 이 서비스 PR은 B 모델 입력의 확정 기간, 비교 구간 계산, C 계산 지원·완료 상태를 고치는 작업이 아니다. 아래 B·C 수락 시험은 별도로 필요하다.

## 진행과 회신 요청

1. B는 B-1·B-2를 구분해 수정 위치, 모델 전송 직전 입력, 조회 파라미터와 오프라인 확인 결과를 회신한다. 표별로 나눠 호출하는 **실제 파이프라인 경로**도 수락 시험에 포함한다.
2. C는 M2 같은 원자료 비교 계산 지원 여부와 미지원/부분 계산일 때 반환할 상태를 회신한다. 연결·화면 담당은 그 상태를 요약·차트·저장 복원에 어떻게 표시할지 함께 맞춘다.
3. A 전달 보완 PR과 별도 서비스 PR의 반영 여부를 구분해 확인한다. B·C 보완은 해당 후보에 합쳐 사용자 답 우선순위, 서로 다른 표의 기간 분리, 요청/조회/계산 범위 보존을 다시 확인한다.
4. 먼저 저장된 실패 응답과 가짜 전송으로 수정 전 재현·수정 후 검증을 하고, 기존 B·C/파이프라인 회귀와 실제 프론트엔드 재확인을 수행한다. 현재 저장 자료에 없는 비교값을 합성으로 보충했다면 그 결과는 합성 검증으로 분리한다.
5. 회신에는 항목별 **해결 / 미지원 유지 / 추가 계약 필요**, 검증한 커밋, 시험·재생 결과와 남은 제한을 적는다. 추가 실호출이 필요하면 문항·횟수·비용을 별도로 정하며, 최초 원응답과 기대값은 수정하지 않는다.

이 문서는 작업 전달용이며 추가 실호출·push·병합 승인이 아니다. 개인 실행 경로, 키, 질문 전문, 원자료 파일은 포함하지 않았다.
