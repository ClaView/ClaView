# A 최근 기간 코드 수정 내역과 B 연결 후속 작업

A는 최근 N기간을 표·주기의 최신 수록 시점 기준으로 계산하도록 바꿨다. 되묻기 답은 원문과 확정값을 함께 보존한다. B에서 이 답을 우선 적용하는 수신부와 파이프라인 연결은 후속 작업이다.

최근 기간 정책 변경은 PR #32로 병합됐다. 아래 B 현황은 PR #34가 포함된 main `6067254` 기준으로 갱신했다. 이어진 A 기간 경계·복합 기간 보완은 [2026-11-03 문서](A_기간경계_종료일있는최근기간_20261103.md), 새 송신 형식과 미지원 보호는 [공용 계약·A 송신부 문서](../../contracts/A_B_기간조건_공용모델과_A송신부.md)를 따른다.

## 이번 A 수정

- 최근 N년·반기·분기·개월은 해당 표·주기의 최신 수록 시점을 포함한 연속 N기간이다. 월별 표의 끝이 2026-08이면 최근 3년은 2023-09~2026-08이다.
- 모델은 기간의 의미·수량·단위를 내고 코드가 날짜를 계산한다. 최근 6개월을 분기별로 요청하는 것처럼 정확히 환산 가능한 범위도 처리한다. 불완전한 분기를 임의로 늘려 확정하지 않는다. 2026-11-03 보완에서는 명시 월 범위와 직접 입력 답도 확장하지 않도록 처리한다.
- 되묻기 선택지에도 실제 표·주기로 계산한 범위를 표시한다. 주기가 미정이면 주기별 날짜를 구분하고, 사용자 답 적용 뒤에도 원래 명시된 시작·끝과 다른 통계의 조건을 보존한다.
- 기간을 말하지 않으면 묻고, 조용한 기본 기간을 넣지 않는다. 기존 한 번의 복구 한도도 유지한다.

PR #32의 정책 변경은 **최근 N기간**에 한정했다. 올해·작년·지난달 같은 달력 상대 표현, 명시 날짜, 열린 기간의 기준을 일괄 변경하지 않았다. 상대 표현 전체가 B와 일치한다는 의미는 아니다. B의 기준일·표 범위·주기·질문·결과 예시로 남은 차이를 별도로 확인한다.

## 코드 변경 위치와 확인 결과

이 절은 PR #32의 구현·검증 기록이다. 비교 기준은 main `8133b3e`, 실행 코드 검수 후보는 `8bf5556`이었다. 당시 변경은 `modules/a`와 `docs/modules/a`에 한정했으며 B·C·파이프라인 수신부는 변경하지 않았다. 이후 보완의 범위와 결과는 위 연결 문서에 따로 기록한다.

| 위치 | 바뀐 동작 |
|---|---|
| `periods/period_policy.json`, `policy.py` | 최근 N기간용 `recent_anchor_rule=data_latest`를 추가했다. 달력 표현용 `anchor_rule=as_of_calendar`는 유지한다. |
| `periods/resolver.py`, `periods/__init__.py` | 표·주기의 최신 수록 시점에서 연속 기간을 계산한다. 같은 통계의 후보 판본끼리는 기준점을 맞춰, 공표가 끝난 옛 판이 자기 끝에서 계산한 범위로 선택되지 않게 한다. |
| `check.py`, `answers.py` | 선택지의 주기별 범위, 명시 시작·끝, 동시 제출한 기간·주기 답을 검사한다. 기간 답 이후 가능한 주기를 갱신하고 원답·출처를 보존한다. |
| `data/prompt_tl.md`, `data/period_presets.json` | 최근 기간의 의미 설명과 선택지 안내를 최신 수록 기준에 맞췄다. 모델 출력 계약은 유지했다. |

검수에서 발견한 정확 환산 거절과 부분 종료일 답 거절 두 건을 수정했다. 신규 반례 28건은 수정 전 14 실패·14 통과에서 수정 후 모두 통과했다. A 본체 333, 판단 1,464, API 160, legacy 4,008, 공용 1,287, 파이프라인 176, 파이프라인 API 4건이 통과했다. 평가 자료 미연결 등으로 건너뛴 시험은 별도로 기록했다.

저장 실제 응답 40건, 옛 상대기간 응답 4건, 합성 6건, 별도 BOK08 응답 1건을 구분해 재생했다. 최초 정책 변경에서는 상대기간 날짜가 바뀌었고, 검수 보완 전후 51건 결과는 같았다. 실제 프론트엔드 26단계도 확인했다. 새 모델·B·KOSIS 호출은 0이며, 새 지시문 모델 정확도나 전체 조회 완료를 측정한 것은 아니다.

## 되묻기 결과에서 A가 보장하는 값

다음은 기간·주기가 결정되어 A의 송신 준비가 완료된 요청에 대한 보장이다. 기간의 일부 경계나 주기가 아직 미정이면 확정 요청으로 만들지 않는다. 직접 입력도 같은 검사 경로를 거친다.

| 내용 | 현재 위치와 의미 |
|---|---|
| 적용 대상 | `handoff.ready[].assignments[]`의 `table_id`, `statistics`. 답의 대상 통계와 표를 연결한다. |
| 구조화된 값 | 같은 assignment의 `frequency`, `period[{start,end}]`. 기간은 주기에 맞춰 정규화한 `YYYY-MM` 월 구간이며, 미완성 입력 자체를 확정값으로 보내지 않는다. |
| 기간 출처 | `statistics[].tables[].period_source`. 정상 질문 인용은 `quoted`, 되묻기 확정은 `user_answer`다. |
| 주기 출처 | 같은 표의 `frequency_source`. `question`, `catalog`, `user_answer`를 구분한다. |
| 사용자 답 기록 | `statistics[].answers[]`의 질문 ID·버전, 대상 통계, 선택지 또는 직접 입력, `source`. 기간·주기 답은 `handoff.ready[].period_answers[]`에도 보존한다. |
| 근거와 A의 메타 범위 | 표의 `period_phrase`, `period_hint`, `catalog_range`, `latest_unpublished`. B의 최신 메타와 같다는 보장은 아니다. |

출처는 **기간과 주기를 따로** 판단해야 한다. 기간만 사용자가 답했으면 기간만 최우선 확정값이다. 카탈로그에서 선택된 주기까지 사용자 답으로 승격하지 않는다. 주기만 답한 경우도 같다.

선택지에 단일 `range`가 있으면 그 범위와 적용 결과가 일치하도록 검사한다. 주기별 범위가 다르면 공개 AView의 `range`는 비어 있고 `label`에 주기별 날짜가 표시된다. 내부 `ranges`는 답 상태에서 보존하지만 현재 AView의 별도 구조화 필드는 아니다. 최종 주기 확정 뒤의 assignment를 B 입력으로 사용해야 한다.

`default`는 A 구판 호환 코드·기록에 남아 있다. 현재 `ask_condition` 경로에서 기간 누락을 기본 기간으로 확정하는 용도로 쓰지 않는다. 저장 40문항의 최종 표 75건에서는 `default`가 0건이었으며, 모든 과거 기록에 없다는 뜻은 아니다. 확정 조건 조립 함수와 새 B `period_condition` 계약은 `default`를 거절한다.

## B 요청에 대한 회신

| 요청 | 회신 |
|---|---|
| 출처를 B 입력에 포함 | `handoff.ready[].b_request.tables[].period_condition`에 `period_source`·`frequency_source`를 조립한다. 기존 `assignments`는 그대로이며, 준비한 새 요청의 자동 전송과 B 수신 적용은 아직 연결하지 않았다. |
| 직접 입력도 구조화 | A에서 기간·주기를 확정한 뒤 전달한다. B가 사용자 답의 자연어를 다시 해석하지 않아도 되는 형태를 사용한다. 부분 입력이 남으면 확정 요청을 만들지 않는다. |
| Y·H·Q 월 구간 해석 | Y는 1~12월, H는 1~6월 또는 7~12월, Q는 해당 분기의 3개월로 정확히 표현할 수 있는지 검사한다. 2024-02~05를 Q의 2024-01~06으로 넓히는 기존 동작은 2026-11-03 보완에서 막는다. 사용자가 Q까지 확정했다면 다른 주기로 바꾸지 않는다. 주기 미정이면 정확히 표현하는 지원 주기를 확인하며, 요청 범위와 미공표 구간은 별개로 둔다. |
| 계산용 선행 구간 | 최종 `period`는 사용자 요청 범위인 `requested_months`이며 계산용 선행 구간을 포함하지 않는다. B가 전월·전년 대비 계산을 위해 앞쪽을 더 조회하는 것은 별도 목적·범위로 기록한다. 사용자 표시 범위를 그만큼 늘리지 않는다. |
| B 메타가 더 짧은 경우 | 원래 확정한 요청 범위는 보존하고, 실제 조회 범위를 B 메타와의 교집합으로 정해 미수록 구간을 안내하는 방식으로 연결한다. 사용자 확정값 자체를 덮어쓰거나 전체 범위를 조회한 것처럼 표시하지 않는다. |
| 참고 기간 차이로 인한 중단 | 되묻기 확정이 없는 필드는 B 계산을 우선하며 차이는 기록한다. 다만 불연속 구간·판본 분할·같은 표의 서로 다른 통계 조건을 단일 구간으로 합쳐도 되는지는 별개다. 전달 대상이나 사용자 조건이 유실되지 않도록 차단 사유별로 처리한다. |

`edition_period_split`, `disjoint_period_not_in_b_contract`, `period_differs_between_requests`, `same_table_conditions_differ`를 일괄 삭제하지 않는다. 단순 참고 기간 차이는 비차단으로 바꾸고, 여러 표·통계·구간의 대응이 필요한 경우는 그 대응을 전달하거나 실행 한계를 표시한다. 이것은 A·B 참고값이 다르다는 이유로 중단하는 것과 구별한다.

## B 연결 전에 함께 확인할 차이

사용자 답 우선·그 밖의 정보는 B 우선이라는 방향은 유지한다. 아래 항목은 아직 규칙 정렬이나 연결 시험이 필요한 부분이며, 이 문서가 새 중단 정책을 확정하는 것은 아니다.

| 항목 | 현재 상태와 후속 확인 |
|---|---|
| 달력 표현 | PR #34에서 B의 ‘작년’은 as_of 전년으로 바뀌었다. 기준일이 2026년이고 표에 2025년이 있으면 A·B 모두 2025년이다. 지난달·지난 분기 등도 B 달력 계산이 추가됐다. 다만 B는 전체 미수록 달력 기간을 최신 수록 시점이 속한 기간으로 대체할 수 있고, A는 원래 요청 범위를 보존한다. 사용자 확정값을 대체하지 않는 수신 처리와 안내를 별도로 검증한다. B의 ‘올해’는 표 최신 시점 기준 경로가 유지된다. |
| 최근 N의 표현·주기 | PR #34에서 B의 ‘최근 6개월’/Q 정확 환산, ‘최근 8개 분기’, ‘최근 3개년’ 인식이 추가됐다. A의 최근 N 계산과 같은 표·주기·수록 범위로 대조한다. 수록 기간이 N보다 짧을 때 B는 잘라 안내하고 A는 먼저 보류할 수 있으므로 이 차이는 연결 후속으로 남긴다. |
| 열린 기간·복합 표현 | B는 ‘2020년부터’를 표 최신까지 처리하며 ‘2025년까지 최근 3년’의 명시 끝을 반영한다. A는 열린 요청의 끝을 as_of 기준으로 보존하고, 새 .10 계약에서 종료일과 최근 개수를 함께 계산한다. B는 명시 끝이 표 최신보다 뒤이면 끝을 먼저 줄인 뒤 개수를 거꾸로 세는 경로가 남아 있다. 요청 시작까지 이동하는 PC-18 사례는 공통 예시에서 따로 확인한다. |
| 여러 표의 최근 기간 비교 | 표별 최신이 달라 최근 기간이 다르면 현재 A의 `period_differs_between_requests`가 전달을 보류하는 것을 재현했다. B 수신부 지원 뒤에 단순 참고 기간 차이의 차단을 조정한다. 사용자가 ‘같은 기간’을 명시했거나 답으로 확정한 범위는 그대로 보존하며, 같은 표의 상충 조건·판본 분할·불연속 구간을 함께 해제하지 않는다. |
| 되묻기의 최근 N | 현재 A는 선택지에 제시한 카탈로그 기준 날짜를 `user_answer`로 확정한다. 우선 이 날짜를 보존해 연결한다. B의 더 최신 메타로 재계산하려면 사용자가 선택한 범위가 바뀌므로, 확정 날짜와 상대기간 의도를 구분하는 별도 계약이 필요하다. |

공통 예시표에는 원질문, 기준일, 표·주기, 각 카탈로그 수록 범위, 답 여부·출처, 기대 요청 범위와 조회 범위를 담는다. 기존 달력 예시표는 옛 정책 시험용이므로 새 최근 기간 규칙의 기준표로 그대로 쓰지 않는다.

## 추가로 연결할 필드

`handoff_conditions`와 `prepare_b_request`가 표별 값을 공용 계약의 `period_condition`으로 조립한다. AView의 `b_request`에서 확인할 수 있지만 실제 B 서비스로 자동 전달하지 않는다. 필드 이름·형식과 예시는 [공용 계약·A 송신부 문서](../../contracts/A_B_기간조건_공용모델과_A송신부.md)가 기준이다.

| 정보 | 필요한 이유 |
|---|---|
| `table_id`, 대상 `statistics` 또는 요청 ID | 같은 표라도 서로 다른 통계의 조건을 섞지 않기 위해 필요하다. |
| 확정 `period`, `frequency` | 자연어 재해석 없이 조회 조건을 만든다. 여러 구간을 받지 못하면 단일 범위로 조용히 합치지 않는다. |
| `period_source`, `frequency_source` | 각 필드가 사용자 답인지 참고 정보인지 구별한다. |
| 답의 `question_id`, `question_version`, 대상 통계 | 어느 되묻기를 확정한 값인지 추적한다. 원문·선택값은 설명과 기록에 사용한다. |
| 요청 범위·조회 범위·미수록 구간·계산용 추가 구간 | B 메타 차이와 계산을 설명하고 화면의 완료 여부를 판정한다. 반환 위치를 함께 정한다. |
| 실제 적용 출처와 계약 지원 표시 | B가 A 사용자 답을 썼는지, 자체 계산을 썼는지 기록하고 구버전 B에 새 필드를 보내지 않도록 한다. |

`focus`는 기존 대상 설명으로 유지하며 기간 우선순위의 근거로 사용하지 않는다. `calculations`는 기존 통계별 계산 문구를 사용한다. 신규취급액·원계열 같은 **기준 축 답**은 AView에 있지만 `period_answers`에는 포함되지 않는다. B가 기간·주기 외의 되묻기까지 받는다면 그 답도 별도 범위로 합의해야 한다. `basis`·`evidence` 역시 현재 B 입력으로 연결된 필드가 아니다.

## B와 파이프라인 후속 순서

1. B가 공용 `period_condition` 모델로 수신·검증·적용을 구현하고 `accepts_period_condition=True`를 명시한다. 현재 HTTP는 미지원 서비스에 새 조건이 들어오면 0호출로 거절한다. 이 보호를 지원 구현으로 세지 않는다.
2. B는 `user_answer`인 필드의 확정값을 우선한다. 그 필드의 자연어 재해석은 생략하되 날짜 형식·순서, 표·통계 대응, 주기 지원 여부 검증은 유지한다. 사용자 주기를 다른 주기로 조용히 바꾸지 않는다.
3. 나머지 필드는 B 계산을 사용한다. 단순 참고 기간 차이는 기록하고 진행하되, 위의 달력·표현 해석 차이는 공통 예시로 먼저 확인하고 처리·안내를 맞춘다. 요청·조회·계산용 구간을 분리하여 반환한다.
4. 수신 지원이 확인된 뒤 `period_answer_contract_pending` 보류와 기존 기간 불일치 중단을 새 우선순위에 맞게 바꾼다. 답을 받지 않는 B에 먼저 보류만 풀지 않는다.
5. 기간만 답한 경우, 주기만 답한 경우, 직접 입력, 표 끝 이후 요청, 다중 통계, 계산용 선행 구간, 미지원 주기, 구버전 B를 오프라인 수락 시험으로 확인한다. 마지막에 실제 프론트엔드에서 답 적용·범위 안내·기록 재개를 확인한다.

이번 A 변경은 저장 응답과 합성 자료로 검사한다. 새로운 모델 해석, B 계열 선택, KOSIS 수치의 정확도는 해당 실호출 검증과 구분한다.

기간 정책과 A 소스 해시가 바뀌었으므로 기존 실호출 승인은 그대로 재사용하지 않는다. 이후 실호출은 연결 상태와 실행 대상을 고정한 새 승인을 받아 진행한다.
