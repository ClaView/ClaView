# C 실행 키 관리 가이드(테스트·배포)

대상 키: HCX(CLOVA Studio) 키 `CLOVASTUDIO_API_KEY`, KOSIS 키 `KOSIS_API_KEY`. 선택 사항으로 `OPENAI_API_KEY`(GPT 비교 경로 `verify_expand_hcx.py --model openai` 전용, C 서버는 사용하지 않음).

## 1. 단계별로 필요한 키

| 단계 | 필요한 키 | 키가 없을 때 |
|---|---|---|
| question·table(A) | 없음(규칙 기반) | 정상 동작 |
| conditions(B) | HCX | `hcx_key_missing`에서 중단. A 결과까지는 화면에 표시 |
| fetch | KOSIS | B까지 실행한 뒤 `kosis_key_missing`에서 중단 |
| chart(C) | 없음 | 정상 동작 |

서비스 흐름 `pipeline/claview_pipeline/staged.py`의 `Pipeline.run(through="A")`는 키 없이, `through="B"`는 HCX 키만으로 단계별 시험이 가능하다.

## 2. 테스트 시(Windows PC)

지금 레포의 화면은 Docker(`frontend` + `pipeline`)로 띄우고, 키는 Git에서 제외된 `.env`에서 읽는다(`CLAVIEW_MODE=live`는 호출 수·비용 승인 뒤에만, [README](../../../README.md) 2절). 아래 입력창 방식은 옛 C 로컬 서버(`research/c/legacy_web/server.py`, 보관본) 기준이며 모듈 구조에서는 실행 확인을 하지 않았다.

```powershell
python -X utf8 research/c/legacy_web/server.py --prompt-keys
```

- 입력창은 글자도 `*`도 표시하지 않으며(`getpass`, 붙여 넣고 Enter를 누르면 다음 입력으로 넘어감) 키는 서버 프로세스 메모리에만 있다. 파일·로그·브라우저 응답에 쓰지 않는다. 시작 시 `HCX key: set | KOSIS key: set`처럼 설정 여부만 출력한다.
- 빈 입력이면 환경변수 값을 쓴다. 환경변수를 쓰는 경우 현재 PowerShell 창에서만 설정한다: `$env:CLOVASTUDIO_API_KEY = "..."`(창을 닫으면 사라짐). 사용자 환경변수로 영구 등록하는 방식은 평문 저장이므로 쓰지 않는다.
- 질문 입력창에 키를 붙여 넣으면 서버가 거절한다(`apiKey=`, `Bearer`, 긴 영숫자 문자열 패턴).
- 실행 기록(`runs/<run_id>/result.json`)은 저장 전에 키 문자열 포함 여부를 검사해 막는다. `runs/`는 Git에 올리지 않는다.
- 팀원 각자 본인 키를 쓴다. 채팅·문서·스크린샷에 키를 남기지 않는다.

## 3. 배포 시 선택지

배포 형태에 따라 달라진다. 현재 코드는 **로컬 단일 사용자 전제**다(127.0.0.1만 허용, 요청마다 토큰, 한 번에 한 질문, 옛 로컬 서버 기준).

### 가. 팀 PC 개별 실행(현재 방식의 확장)

- 각자 본인 키를 사용한다. 키 입력 우선순위는 환경변수 → 저장된 자격 증명 → 입력창이다(`research/c/legacy_web/launcher.py`).
- 자주 쓰면 Windows 자격 증명 관리자에 저장할 수 있다(`research/c/legacy_web/credential_store.py`, 항목 `ClaView/LocalServer/<id>`). Windows 전용이며 해당 계정 로그인 상태에서만 읽힌다. 평문 파일 저장보다 안전하다.
- 코드 변경 없이 가능하다. 키 발급·회수는 개인별로 관리한다.

### 나. 공용 서버(사내망 또는 클라우드)

키를 **서버 한 곳에서만** 보관한다. 사용자에게는 키를 주지 않는다.

| 항목 | 권장 |
|---|---|
| 보관 | 비밀 저장소(예: NAVER Cloud Platform Secret Manager 등 사용하는 클라우드의 비밀 관리 서비스)에 저장하고, 프로세스 시작 시 환경변수로 주입. 저장소·이미지·설정 파일·CI 로그에 값 금지 |
| 분리 | 테스트용과 운영용 키 분리. 운영 키는 운영 계정만 접근 |
| 권한 | 비밀 읽기 권한은 실행 계정 1개에만 부여 |
| 회전 | 정기 교체 주기와 유출 시 즉시 폐기 절차를 문서화. 교체 시 서버 재시작만으로 반영되게 구성 |
| 로그 | 요청 URL에 KOSIS 키가 쿼리로 들어가므로 HTTP 클라이언트 로그를 INFO 이하로 켜지 않는다(`modules/b/claview_b_api/service.py`의 실호출 클라이언트 생성이 httpx 로거를 WARNING으로 고정). 예외 메시지·추적 기록에 키가 남지 않게 점검 |
| 접근 | 로그인(사내 계정 등)과 HTTPS 필수. 현재 서버의 토큰 방식은 로컬 보호용이며 공용 인증을 대신하지 못한다 |
| 한도 | HCX 분당 토큰 한도(TPM 60,000)와 KOSIS 호출 한도는 **서비스 전체가 공유**한다. 요청 큐, 사용자별 속도 제한, 일일 비용 상한 필요 |
| 동시성 | 현재 한 번에 한 질문만 처리. 다수 사용자면 요청별 실행 상태 분리와 작업 큐가 필요 |
| 질문 기록 | 질문·실행 기록 보관 기간과 접근 권한 정책 필요 |

위 항목 중 인증·큐·속도 제한·동시성은 **코드 작업**이 필요하며 이번 범위에 포함하지 않았다.

### 다. 혼합(서버 보관 키 + 사용자 인증)

가의 개인 실행 화면을 유지하되 나의 키 보관·한도 관리를 쓴다. 사용자별 사용량 집계가 가능하다.

## 4. 점검 목록

- [ ] 저장소·zip·이미지에 키 문자열이 없다(`.env` 제외 규칙 유지, `.env.example`은 변수 이름만).
- [ ] 서버 로그·실행 기록에 키가 없다.
- [ ] 키가 노출됐다면 즉시 폐기하고 재발급한다.
- [ ] 운영 키와 테스트 키가 분리되어 있다.
- [ ] 호출 한도·비용 상한이 설정되어 있다.

## 5. 공식 문서(발급·한도·비밀 저장소 확인용)

- CLOVA Studio API 키: https://guide.ncloud-docs.com/docs/clovastudio-apikey
- CLOVA Studio 호출 한도: https://guide.ncloud-docs.com/docs/clovastudio-ratelimiting
- NAVER Cloud Secret Manager: https://guide.ncloud-docs.com/docs/en/secretmanager-use
- KOSIS 인증키 이용 조건은 KOSIS 공유서비스(Open API) 안내 페이지에서 확인한다.

한도 수치와 가격은 변경될 수 있으므로 배포 전에 공식 문서로 다시 확인한다.
