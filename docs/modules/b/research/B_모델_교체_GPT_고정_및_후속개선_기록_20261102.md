# B 선택 모델 교체(HCX → gpt-6.1-terra)와 후속 개선 기록 (2026-11-02)

- 기준: `main` 3bc1730(PR #27 병합).
- 목적: B 모델을 바꾼 근거와 그 뒤의 개선(C 패널 분리, B 단위 보정, B 보강 규칙), 실제 실행 확인 결과, PR #8~#27 목록을 한곳에 남김.
- 이 문서의 실행 결과는 모두 저장된 KOSIS 응답과 실제 모델 호출로 얻은 것이며, 실행 도구와 결과 폴더는 작업 PC의 `Claude outputs/`에 있고 레포에는 없음.

## 1. 요약

- B의 항목·분류값 선택 모델을 `gpt-6.1-terra`(OpenAI Chat Completions)로 고정하고 서비스 경로에서 HCX 사용을 없앰(PR #24). 모델 ID는 코드에 고정하고 환경변수로 바꾸지 않음.
- 같은 입력·프롬프트·스키마로 B 선택 단계만 바꾼 비교에서 GPT가 더 정확했음. 신규 골든셋 20건 통과 HCX 16/20 대 GPT 20/20·20/20(2회), 골든 v4 20건은 둘 다 20/20임.
- HCX는 후처리 규칙이 모델 선택을 바꾼 사례가 v5 7/20, v4 15/20이었으나, GPT는 60건 모두 0건이었음.
- 이어서 C 패널 분리(#23), B 단위 보정(#26), B 보강 규칙(#27)을 병합함.
- 2026-11-02 live 확인: 새 A 화면 경로는 live 모델 호출이 꺼져 있어 화면 전체 흐름은 확인하지 못했고, B만 직접 호출한 결과는 골든 정답과 두 표 모두 일치함.

## 2. 배경: HCX 기준선의 문제

- 신규 골든셋 20건(v5, 표 24개·52계열)을 실제 HCX 답으로 돌렸을 때 B 선택 일치가 11/20, 통과가 8/20이었음(당시 규칙).
- 오류 유형이 반복됨: 질문이 말한 값 대신 비슷한 값 선택, 상위 항목만 고르거나 질문에 없는 상위·형제 항목 추가, 그래프 배치를 지시하는 말("지표별로 그래프를 나눠줘")을 값 세분 요청으로 읽음.
- 이를 바로잡는 후처리 규칙을 계속 추가해야 했으며, 이 규칙은 HCX 답을 보고 만든 것이어서 같은 20건에서의 개선은 독립 검증이 아님.

## 3. 모델 비교(HCX 대 GPT)

같은 입력·프롬프트·스키마를 쓰고 B 선택 단계의 모델만 바꿈. KOSIS 호출은 0회(저장 응답 사용). HCX는 저장된 실제 답을 현재 규칙으로 재평가한 값임.

| 지표 | HCX | GPT |
|---|---|---|
| 신규 골든셋 20건 통과 | 16/20(12·13·15·17번 B 선택 오류) | 20/20, 20/20(2회) |
| 골든 v4 20건 통과(포커스 없음) | 20/20(규칙이 15건의 선택을 고침) | 20/20 |
| 후처리 규칙이 모델 선택을 바꾼 사례 | v5 7/20, v4 15/20 | 0/60 |
| 모델이 고른 행 수(v4) | 209 | 70 |
| 출력 토큰(v4 41회) | 17,040 | 4,233 |
| 응답 시간 합(v4) | 5.3분 | 1.7분 |

- GPT 호출 합계 93회(스모크 2, v5 25회×2, v4 41회), 입력 약 48.5만·출력 약 1.2만 토큰이며 비용은 약 0.5달러로 추정함. 단가는 제3자 자료(입력 $1, 출력 $5, 100만 토큰당) 기준이며 OpenAI 공식 페이지에서 확인하지 못함.
- 해석상 유의점
  - 표본은 골든 세트 20건씩(v5 2회, v4 1회)이며 실제 질문의 다양성을 모두 덮지 않음.
  - GPT는 실행마다 달라질 수 있어 모델 ID를 고정했고, 추론 강도는 기본값임.
  - GPT 통과 결과는 당시 아직 병합되지 않은 규칙·보정이 들어 있는 작업 트리에서 측정했으나, GPT의 선택(항목·분류값·기간)은 후처리 전후가 모든 건에서 같았으므로 선택 결과 자체는 그 규칙에 의존하지 않음.

## 4. 결정과 구현(PR #24)

- 팀 결정(2026-10-30): 기본 모델을 교체하고 HCX는 쓰지 않음, API 키는 A 파트와 같은 방식(팀 `.env`의 `OPENAI_API_KEY`)으로 보관, 모델 ID는 코드에 고정.
- 변경 내용
  - `common/claview_common/settings.py`: `B_MODEL_ID = "gpt-6.1-terra"`, 키 환경변수는 `OPENAI_API_KEY`·`KOSIS_API_KEY`. `hcx_key`·`HCX_MIN_INTERVAL_SEC` 설정 제거.
  - `modules/b/claview_b_api/service.py`: `live_clients`가 OpenAI 모델만 만듦. `CLOVASTUDIO_API_KEY`는 읽지 않음.
  - `pipeline/claview_pipeline/{staged,api,live}.py`: 오류 코드 `hcx_key_missing` → `openai_key_missing`, `hcx_http_*` → `openai_http_*`(화면 문구는 "분석 모델"). `/api/info`에 `model_ready`, `b_model` 추가.
  - `.env.example`: `OPENAI_API_KEY` 하나로 정리.
- 바꾸지 않은 것: `HcxModel` 클래스, B CLI(검색 임베딩이 `CLOVASTUDIO_API_KEY`를 씀), 연구용 스크립트, `research/` 보관본, 프런트 계약 때문에 이름만 남긴 `hcx_ready`와 호출 수 키 `"HCX"`, B 출력 상한 6,144토큰(GPT 최대 출력 468토큰).

## 6. 실제 실행 확인(2026-11-02, Docker live)

- 질문: "2022~2024년 경상수지(계절조정)와 실질 GDP 성장률을 한 그래프에서 이중 축으로 보여줘."(골든 v3 CV-BC-02)
- 화면 경로: synthetic 모드에서는 합성 B가 기간을 자리표시값(`x`)으로 채워, 파이프라인의 A 기간 대조에서 `b_period_differs_from_a`로 멈춤(배선 확인용 모드의 정상 동작). live 모드에서는 새 A 화면 경로가 모델 호출을 꺼 두어 1단계에서 `a_live_disabled`로 멈춤(호출 0회, 호출 한도 검사 연결 전). 화면에서 A부터 C까지 live로 도는 확인은 하지 못함.
- B만 직접 호출(`POST /b/resolve`, 골든의 두 표 `DT_301Y017`, `DT_200Y102` 전달): OpenAI 2회, KOSIS 0회, 응답 5.3초. 결과는 골든 정답과 두 표 모두 일치함.

| 표 | 선택 | 주기·기간 |
|---|---|---|
| `DT_301Y017` 경상수지(계절조정) | 경상수지, 백만달러 | M, 202201~202412 |
| `DT_200Y102` 주요지표(분기지표) | 국내총생산(GDP)(실질 계절조정 전기비), % | Q, 202201~202404 |

- 한계: 질문 1건, 실행 1회이며 KOSIS 조회와 A의 실제 기간은 확인하지 못함.

## 8. 남은 과제

- A 담당: 새 A 화면 경로의 live 모델 호출을 켜는 호출 한도 검사 연결, A와 B의 기간·주기 규칙 정렬([B 기간·주기 처리 현황](../design/B_기간_처리_현황_20261101.md) 10~11절), "~별로/따로 배치" 표현이 `a_selection_unsettled`로 가는지 실제 A 확인.
- B 정리: HCX 코드(`HcxModel`, B CLI, 연구 스크립트, `contracts.py`의 HCX 한도 주석)를 별도 PR로 정리. 단위 보완표의 미확인 표(47개 안팎) 확인 후 추가.
- C: 이름 있는 분류 축("기업규모별로")으로 나누는 요청은 묶음 판정이 자동 순서(단위→통계표→지표)로 돌아가는 한계가 남음.
- 팀 결정 필요: 골든 v3 정답 승인, 멘토 `ci.yml` 수정(CI는 현재 `ruff check .`만 실행).
