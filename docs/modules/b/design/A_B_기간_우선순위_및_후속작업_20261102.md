# A·B 기간 처리 우선순위와 후속 작업 (2026-11-02)

- 기준: `main` 8133b3e(PR #30·#31 병합 후) 코드. 코드와 시험 파일을 읽어 확인했고, 7절의 비교 표만 실제로 실행한 값임.
- 목적: A·B 기간 처리 방향을 정리하고, A에 요청할 사항, B 후속 작업, 팀이 정해야 할 사항을 한곳에 모음.
- 관련 문서: [B 기간·주기 처리 현황](B_기간_처리_현황_20261101.md), [A에서 B로 전달하는 인터페이스](A에서_B로_전달하는_인터페이스.md), [새 A focus와 출처](../../../contracts/A_focus_출처.md), [A 1차 공유 범위](../../a/A_1차_공유_범위_20261102.md).

## 1. 결정된 방향

1. 상대 기간("최근 N년", "올해" 등)은 A가 B와 같은 로직으로 처리하도록 A를 수정할 예정임. 그래도 A와 B의 기간이 다르면 B가 계산한 기간이 우선함.
2. 질문에 기간이 없어 A가 사용자에게 되묻고 확정한 기간·주기는 A의 값이 최우선임. B 로직에 없던 정보이며 사용자가 직접 확정한 값이기 때문임.
3. 위 두 경우를 제외하고 A가 `focus` 등으로 보내는 정보는 참고용임. A와 B의 기간이 다르면 B가 우선함.
4. A와 B의 정보가 다르다는 이유로 중단하지 않음.

## 2. 현재 상태 (8133b3e)

### 2.1 B

- `modules/b`는 PR #28 이후 변경이 없음. B는 A의 기간·주기를 받지 않고 질문 원문에서 표마다 다시 계산함.
- 기간이 없는 질문은 B에서 `conditions_incomplete`로 멈춤. 상대 기간은 표의 최신 수록 시점을 기준으로 계산하고, 표가 뒤처져 있으면 안내(`period_notices`)만 남기고 같은 기간으로 진행함(되묻지 않음).

### 2.2 파이프라인

- `_b_conditions_lost`가 B 결과를 A의 표별 주기·기간과 대조하고, 하나라도 다르면 조회 전에 `b_period_differs_from_a`로 멈춤.
- A의 되묻기 답변(`period_answers`)이 있는 요청은 B에 받는 칸이 없어 B로 보내지 않고 `period_answer_contract_pending`으로 보류함(결과는 partial).
- `accepts_period_answers`는 실제 B에서 항상 거짓임.

### 2.3 A

- `focus`는 기간 정보가 아니라 모델이 원질문을 읽고 쓴 100자 이내 대상 설명임(출처·인용 상태는 `focus_provenance`). B는 이 문자열을 계열 선택 때 모델에 보여 주는 데만 씀.
- 기간이 없거나 주기가 여럿인데 말하지 않은 질문은 기본값을 가정하지 않고 사용자에게 되묻는 정책(`condition_rule: ask_condition`)임. 상대 기간은 as_of가 속한 달력을 기준으로 계산하고, 표 끝 이후 부분은 `latest_unpublished`로 표시한 채 요청 기간 그대로 넘김(정책 ①, 2026-10-30).
- A가 되묻기 결과로 내보내는 정보는 다음과 같음.

| 구분 | 위치 | 내용 | B 전달 |
|---|---|---|---|
| `period_answers` | 요청 | 질문 ID·버전, 선택지 또는 직접 입력 text, 출처 `user_answer` | 보류(B 칸 없음) |
| `assignments`(표별) | 요청 | 표 ID, 주기, 기간 구간(`YYYY-MM`), 적용 통계, `catalog_range`, `latest_unpublished` | 파이프라인 대조에만 사용 |
| `period_source`, `frequency_source`, `period_phrase`, `period_hint` | AView 통계의 표 | 기간·주기 출처(quoted/default/user_answer), 기간 문구, 참고 기간 | 전달 안 함 |
| `handoff_conditions` 결과 | `view.py` 함수 | 위 값을 표별 조건으로 조립 | 호출처 없음(시험만) |

- 시험에서 되묻기로 "최근 5년"을 고르면 주기 `Y`, 기간 `2022-01~2026-12`로 확정되고 출처는 `user_answer`임. 직접 입력 text는 A가 다시 해석해 구조화하므로 B가 text를 해석하지 않아도 되는 구조임.
- `handoff_conditions`는 기간 출처가 `default`이거나 구간이 하나가 아니거나 같은 요청의 통계 값이 서로 다르면 조건을 만들지 않음.

## 3. A 요청 사항

1. **(필수) 출처를 B 전달 정보에 포함**: 표별 `period_source`, `frequency_source`를 `assignments` 또는 B 전달 조건에 넣을 것. B가 "되묻기 확정"과 "질문 인용"을 구별해야 우선순위를 정할 수 있음. 정책(`ask_condition`) 이후에도 `default` 출처가 남는지 함께 알릴 것.
2. **(필수) 확정값의 구조화 보장**: 되묻기로 확정된 요청은 직접 입력한 경우에도 `assignments`에 기간·주기가 항상 구조화되어 있고, 부분 입력(`partial_periods`) 상태로는 보내지 않음을 확인할 것. 확정 범위와 선택지에 보여 준 `range`가 같음도 확인할 것.
3. **(필수) 월 구간을 Y·H·Q 주기에 쓰는 규칙**: 시작·끝이 항상 주기 경계에 맞는지, 걸치는 주기를 모두 포함하는 것으로 B가 읽어야 하는지 명문화할 것. 현재 파이프라인 대조는 걸치는 주기를 모두 포함하는 것으로 읽음.
4. **`period`의 의미**: `period`가 사용자가 보는 표시 범위이고 "전년 대비" 같은 계산 기준 구간을 포함하지 않음을 확인할 것. B가 계산용으로 앞쪽을 늘리는 것에 동의하는지도 회신할 것.
5. **표 끝 이후 구간**: 확정 범위가 표 끝을 넘으면 B가 B 메타 기준으로 표 끝까지 자르고 안내하는 방식에 동의하는지 확인할 것. A 카탈로그 기준일과 B 메타 기준일이 다를 수 있음.
6. **A 쪽 차단 완화**: 되묻기가 없는 요청에서는 A의 기간이 참고용이므로 아래 차단은 풀어도 되는지 확인할 것. B가 단일 시작·끝만 받으므로 되묻기 확정값이 여러 구간인 경우만 계속 막는 것이 맞아 보임.
   - `edition_period_split`, `disjoint_period_not_in_b_contract`, `period_differs_between_requests`, `same_table_conditions_differ`

그 밖에 `calculations`(통계별 계산 문구)는 현재 형태로 충분함.

## 4. B 후속 작업

1. **입력 칸 추가**: 표별 선택 필드 `confirmed_period`(주기, 시작, 끝, 출처, 문구)를 추가함. `focus`와 같은 방식으로 `b_port.py`의 선택 필드(`OPTIONAL_TABLE_FIELDS`)와 요청 검사(`check_table_request`), `stages.py`의 `load` 검사, 공용 계약에 반영함. 이름과 형식은 A와 합의함.
2. **B 기간 처리에 우선순위 반영**: 확정 기간이 있으면 주기 결정·상대 표현·연도 계산·`validate_period`를 건너뛰고 그 값을 씀. 기간이 없는 질문에서 `conditions_incomplete`로 멈추는 현재 동작을 피하기 위해 필요함. 확정 범위가 표 범위를 벗어나면 자르고 안내함(5절 결정 대기).
3. **파이프라인에서 중단 제거**:
   - `screen.py`의 `period_answer_contract_pending` 보류와 `accepts_period_answers` 조건을 없애고 확정 기간을 B로 전달함.
   - `b_period_differs_from_a` 중단을 비차단 기록으로 바꿈. 되묻기가 없으면 B 값으로 진행하고 차이를 기록함. 되묻기가 있으면 B가 A 값을 썼는지 확인만 함.
4. **결과에 근거 표시**: 선택마다 기간의 출처(A 확정/B 계산), 자른 여부, 안내를 결과에 담아 화면 카드에서 확인할 수 있게 함.
5. **B 기간 규칙 품질 개선**: B 값이 우선하게 되므로 현재 한계를 시험과 함께 고침. 대상은 부분 문자열 "월"("월급", "월평균"), "상반기·하반기"가 H로 읽히는 문제, "2024년 1~3월"의 첫 숫자 누락, "2020년부터"가 한 해로만 계산되는 문제, "매년·년도별"이 연간 신호가 아닌 문제임.
6. **A에 기준 시험 자료 제공**: A가 B와 같은 상대기간 로직으로 수정할 수 있도록 B의 상대기간 계산 예시표(기준일, 표 범위, 질문, 결과)를 JSON으로 만듦. A의 `period_calendar_examples_56.json`과 같은 형식으로 함.
7. **시험·문서 갱신**:
   - 기간 불일치 중단을 단언하는 기존 시험(`pipeline/tests/staged/test_screen_54.py` 등)을 바꿈.
   - synthetic B의 기간 `"x"` 때문에 멈추지 않도록 합성 기간을 실제 값으로 바꿈.
   - [B 기간·주기 처리 현황](B_기간_처리_현황_20261101.md)과 인터페이스 문서에 우선순위 원칙을 반영함.

live 확인은 화면의 A live 호출 게이트가 연결된 뒤에 진행함(현재 `a_live_disabled`).

## 5. 정해야 할 것

| 항목 | 내용 | 제안 |
|---|---|---|
| 확정 범위가 표 끝을 넘을 때 | 자르고 안내 / 중단 | 자르고 안내(B의 상대기간 처리와 같음) |
| 확정 주기를 B 표 메타가 지원하지 않을 때 | 이유를 밝히고 중단 / B 주기로 대체하고 안내 | 중단. 사용자가 직접 고른 값을 다른 주기로 바꿔 보이면 안 됨. A가 표를 미리 거르므로 드문 경우임 |
| B 값이 A 값을 덮은 경우 사용자 안내 | 항상 안내 / 기록만 / 범위가 달라진 경우만 안내 | 결과·로그에는 항상 기록하고 화면 안내는 범위가 실제로 달라진 경우만 함 |
| 입력 칸 이름·형식 | `confirmed_period` 구조, 구간 형식 | A 담당자와 먼저 합의. A의 조건 조립 결과(`handoff_conditions`)를 기준으로 삼는 방안이 있음 |

## 6. 진행 순서 (제안)

1. 3절 A 요청 회신 받기, 5절 결정 사항 확정.
2. 입력 칸 형식 합의 후 4절 1~4번 구현(B·파이프라인).
3. 4절 5번(B 기간 규칙 개선)과 6번(예시표 제공)은 병행 가능함.
4. 4절 7번 시험·문서 갱신.
5. A 수정(상대기간 로직 일치)과 A live 게이트 연결 후 live 확인.

## 7. 참고: A·B 상대 기간 계산 비교

월 표(수록 2000-01~2026-08), as_of 2026-10-30에서 같은 질문을 A 해석기와 B 함수로 각각 실행하고 파이프라인의 대조 함수로 비교한 값임. A의 `period`는 미공표 월을 포함한 계산값(`applied`)을 기준으로 함(A 시험 설명에 근거. 전체 파이프라인 실행은 아님).

| 질문 | A | B | 대조 |
|---|---|---|---|
| 2022년 월별 | 202201~202212 | 202201~202212 | 같음 |
| 2022~2024년 월별 | 202201~202412 | 202201~202412 | 같음 |
| 최근 3년 월별 | 202401~202610 | 202309~202608 | 다름 |
| 올해 월별 | 202601~202610 | 202601~202608 | 다름 |

- 상대 표현 차이의 원인: A는 as_of가 속한 달력을 끝으로 보고 표 끝 이후를 미공표 월로 표시한 채 넘김(정책 ①). B는 표의 최신 수록 시점을 끝으로 거꾸로 계산하고 안내만 남김.
- "2020년부터"는 B가 "이후"만 상대 표현으로 읽는 기존 한계, "전월 대비"는 B의 계산용 기간 확장 때문임.
