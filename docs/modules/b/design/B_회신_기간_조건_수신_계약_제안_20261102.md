# A·B 기간 조건 수신 계약 제안 (B 회신, 2026-11-02)

- 대상: A 파트. A가 보낸 질문 4건("B에서는 아래 내용을 확인 부탁드립니다")과 회신 문서(`A_최근기간_수정과_B_되묻기_연결_회신_20261102.md`)에 대한 B의 답임.
- 기준: `main` 8133b3e 코드. A의 후속 수정(`8bf5556`)은 저장소에 없어 문서 내용만 근거로 함. 필드 이름과 형식은 모두 제안이며 합의 전에는 확정이 아님.
- 관련 문서: [A·B 기간 처리 우선순위와 후속 작업](A_B_기간_우선순위_및_후속작업_20261102.md), [B 기간·주기 처리 현황](B_기간_처리_현황_20261101.md).

## 1. 전제

- 방향: 기간·주기 각각 사용자 되묻기 답(`user_answer`)인 필드는 A 값을 우선하고, 나머지는 B 계산을 우선함. A와 B의 값이 다르다는 이유로 중단하지 않음.
- 현재 B 입력에는 A의 기간·주기를 받는 칸이 없음. 표 항목이 받는 키는 `org_id`, `table_id`, `table_name`, 선택 `focus`뿐이며, 그 밖의 키는 요청 검사에서 거절함(`check_table_request`).
- A의 출처(`period_source`, `frequency_source`)는 AView 통계의 표에는 있으나 `handoff.ready[].assignments`에는 없음(A 회신 확인). 조립 함수 `handoff_conditions`는 B 서비스에 연결되어 있지 않음.

## 2. 수신 계약 제안 (질문 1)

### 2.1 입력

표 항목에 선택 필드 `period_condition`을 추가함(`focus`와 같은 방식). A의 `handoff_conditions`가 조립하는 표별 조건을 그대로 받는 형태로 하여 A의 변환 부담을 줄임.

```json
{
  "org_id": "301", "table_id": "DT_...", "table_name": "...", "focus": "...",
  "period_condition": {
    "frequency": "Q",
    "frequency_source": "user_answer",
    "period": [{"start": "2024-01", "end": "2026-12"}],
    "period_source": "user_answer",
    "period_phrase": "최근 3년",
    "latest_unpublished": [{"start": "2026-10", "end": "2026-12"}],
    "answer": {"question_id": "...", "question_version": 3, "statistics": ["s1"]}
  }
}
```

| 필드 | B의 사용 |
|---|---|
| `frequency`, `frequency_source` | 출처가 `user_answer`이면 사용함. 그 외에는 참고로 기록만 하고 B가 주기를 정함 |
| `period`, `period_source` | 출처가 `user_answer`이면 사용함. 그 외에는 참고로 기록만 하고 B가 계산함. 구간은 한 개만 받으며 두 개 이상이면 입력 오류로 거절함 |
| `period_phrase` | 안내 문구와 기록에 사용함 |
| `latest_unpublished` | 참고. B는 자기 메타로 표 끝을 판단함 |
| `answer` | 어느 되묻기를 확정한 값인지 추적하는 기록용 |

- 기간 구간은 A가 주기 경계에 맞게 정규화한 `YYYY-MM` 월 구간임. B는 경계를 검증만 하고 다시 확장하지 않음.
- `frequency`는 출처와 관계없이 항상 보내 주기를 요청함(참고값). 값은 `Y`, `H`, `Q`, `M`임.
- `default` 출처는 받지 않음. 있으면 해당 필드를 참고로만 취급함.
- 같은 표를 여러 통계가 쓰는 경우 A가 조건이 같을 때만 한 요청으로 묶으므로, 표당 `period_condition`은 하나임. 같은 표에서 통계마다 조건이 다른 경우는 A가 차단함(`same_table_conditions_differ`).

### 2.2 B 처리 규칙

| 상황 | 처리 |
|---|---|
| 기간·주기 모두 `user_answer` | A 값을 사용함. 질문 원문에서 기간을 다시 해석하지 않음 |
| 기간만 `user_answer` | 주기는 B가 정함. 월 구간은 걸치는 주기로 환산하고, A의 주기와 다르면 환산 사실을 안내함 |
| 주기만 `user_answer` | 주기는 A 값을 쓰고 기간은 B가 계산함 |
| 둘 다 `user_answer`가 아님 | 기존 동작. A 값은 기록만 하고 다르다는 이유로 중단하지 않음 |
| 확정 기간이 표 범위를 벗어남 | 교집합으로 조회하고 미수록 구간을 안내함. 확정값 자체를 덮어쓰지 않음 |
| 교집합이 없음 | 다른 기간으로 바꾸지 않고 이유를 밝혀 중단함 |
| 사용자가 고른 주기를 표가 지원하지 않음 | 다른 주기로 대체하지 않고 이유를 밝혀 중단함(A가 표를 미리 거르므로 드문 경우) |

- 계산 기준 구간("전년 대비", "전월 대비")은 A의 `period`에 포함되지 않음을 전제로 B가 앞쪽을 더 조회함. 사용자 표시 범위는 그만큼 늘리지 않음.

### 2.3 출력

선택마다 아래를 구분해 반환하고 화면 카드에서 확인할 수 있게 함.

| 항목 | 내용 |
|---|---|
| 요청 범위 | 사용자 또는 질문이 요구한 범위 |
| 조회 범위 | 실제로 KOSIS에 요청한 범위 |
| 미수록 구간 | 표에 없어 조회하지 못한 구간 |
| 계산용 추가 구간 | 비교 계산을 위해 앞쪽에 더한 구간 |
| 적용 출처 | `a_user_answer` 또는 `b_computed`(필드별) |
| 안내 | 환산·교집합·대체 사실 |

### 2.4 지원 표시와 판본

- B 서비스가 `accepts_period_condition`을 노출하고 표 목록 계약 판본(`TABLE_LIST_CONTRACT`)을 올림.
- 파이프라인은 지원하는 B에만 새 필드를 보냄. 구버전 B에 보내면 요청 검사에서 거절되기 때문임.
- 지원 확인 전에는 기존 `period_answer_contract_pending` 보류를 풀지 않음(A 회신의 순서와 같음).

## 3. 우선순위와 달력·최근 N 표현 (질문 2)

- 방향에 동의함. 공통 예시표는 B가 만들어 A에 전달함. 열은 기준일, 표·주기, 수록 범위, 원질문, 답 여부와 출처, 기대 요청 범위, 기대 조회 범위, 안내임.
- 계산 기준은 다음과 같이 맞춤. B 쪽 수정은 B 단독 수정 목록(5절)으로 진행함.

| 표현 | 기준 |
|---|---|
| 작년 | as_of 달력의 닫힌 한 해. 표에 일부 없으면 안내하고 표의 최신 기간 기준으로 산출함. 한 해가 전부 없으면 표의 최신 연도로 대체하고 안내함 |
| 올해 | 표의 최신 시점까지. 표에 없는 부분은 안내함 |
| 최근 N기간 | 표·주기의 최신 수록 시점을 끝으로 거꾸로 N기간(A·B 일치) |

- 현재 B의 불일치 원인(코드 확인): "작년"을 as_of가 아니라 표의 최신 연도 기준으로 계산함(2026-10-02 팀 결정). "최근 8개 분기", "최근 3개년"은 개수 정규식이 "개"와 "개년"을 인식하지 못해 중단함. 분기 표의 "최근 6개월 분기별"은 개월→분기 환산이 없어 중단함. "2025년까지 최근 3년"은 명시한 끝을 읽지 않음. "2020년부터"는 열린 기간으로 읽지 않고 한 해로만 계산함.
- B 값이 틀릴 수 있는 문형이 남아 있는 동안에는 "A와 B가 다르면 B 우선"으로 중단을 풀지 않음. 위 수정과 공통 예시표 확인 이후에 풂.

## 4. 연결 시험 포함 항목 (질문 3, 4)

| 항목 | B의 입장 |
|---|---|
| 여러 표의 최신 시점이 다른 비교 | B는 표마다 그 표의 최신 시점으로 계산하므로 표별 기간이 다를 수 있음. 각 표 항목에 자기 `period_condition`이 있으면 B는 표별로 처리할 수 있으므로 표가 다른 경우의 `period_differs_between_requests`는 풀어도 됨 |
| 같은 표에서 통계마다 기간이 다름, 판본별 분할 | B가 표당 기간을 하나만 받으므로 `same_table_conditions_differ`, `edition_period_split`은 유지가 맞음 |
| 되묻기로 고른 "최근 3년" | A가 선택지에 보여 준 날짜로 확정된 값을 그대로 사용함. B의 최신 메타로 다시 계산하지 않고 교집합만 구해 미수록을 안내함 |
| focus | 기존 참고 정보로 유지함. 기간 우선순위의 근거로 쓰지 않음 |
| 기준 축 답(평잔·말잔 등) | 지금 B가 받을 필요가 없음. A가 그 답으로 표를 선택해 보내고 표 안의 값은 A가 되묻지 않기 때문임. 필요가 생기면 별도 범위로 정함 |

연결 시험 항목: 기간만 답한 경우, 주기만 답한 경우, 직접 입력, 표 끝 이후 요청, 표 범위와 겹치지 않는 요청, 다중 통계, 계산용 선행 구간, B 미지원 주기, 구버전 B, 표별 최신 시점이 다른 비교, 되묻기 "최근 3년".

## 5. B 단독 수정 목록 (계약 합의와 별도 진행)

1. "작년"을 as_of 달력 기준으로 변경함. 표에 일부 없으면 안내하고, 전부 없으면 표의 최신 연도로 대체하고 안내함. 2026-10-02 팀 결정을 뒤집는 것이므로 PR에 이력을 남김.
2. 개수·단위 인식 확장: "N개 분기·반기·년", "N개년", "N분기간". 개월→분기·반기·연 환산은 나누어떨어질 때만 허용함.
3. 상대 표현과 명시 끝 연도의 조합("2025년까지 최근 3년")을 하나의 계산 경로로 처리함.
4. "N년부터"를 열린 기간으로 처리함.
5. 현재 중단하는 "지난달" 등 개수 없는 상대 표현의 처리 방식을 정함.
6. 기존 한계(부분 문자열 "월", "상반기·하반기"가 H로 읽힘, "1~3월"의 첫 숫자 누락, "매년·년도별")를 시험과 함께 고침.
7. 위 변경에 맞춰 기존 시험과 골든 기대값(`test_b_unit.py`, `test_b_period_golden_augmented.py`, `golden_set_v1_period_augmented.json` 등)을 갱신함.

## 6. A에 대한 확인 요청

1. 기간 출처가 `quoted`인 경우에도 `period_condition`을 참고값으로 항상 보내는지. B는 사용하지 않고 기록만 함.
2. 차단 코드 중 `period_differs_between_requests`만 풀고 `same_table_conditions_differ`, `edition_period_split`, `disjoint_period_not_in_b_contract`는 유지하는 안에 동의하는지.
3. 입력 형식(2.1절)이 `handoff_conditions` 결과와 맞는지. 다르면 A의 형식에 B가 맞출 수 있음.

## 7. 진행 순서 (제안)

1. 위 계약안을 A와 합의함. 이름은 달라도 되지만 구조는 맞춤.
2. 계약 문서와 요청·응답 JSON 샘플(`common/fixtures`)을 B 쪽에서 먼저 작성하고 A가 검토함.
3. A 송신부, 파이프라인, B 수신부 순으로 연결함.
4. 공통 예시표로 연결 시험을 하고, 마지막에 화면에서 요청·조회·미수록·계산용 범위 표시를 확인함.
5. A의 live 호출 승인(기간 정책·소스 해시 변경으로 새 승인 필요)이 난 뒤 live 확인을 함.
