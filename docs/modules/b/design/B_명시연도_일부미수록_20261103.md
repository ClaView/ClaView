# 명시 연도 일부 미수록 처리 (2026-11-03)

- 대상: B `claview_b/stages.py`(`explicit_period_detail`, `plan_table_period`의 안내 분류). A·B 계약은 바꾸지 않음.
- 선행: 표별 기간 해석 PR(`B_표별_기간_해석_20261103.md`)이 먼저 병합되어 있어야 함(같은 `stages.py`를 고침).
- 범위: 질문에 연도를 직접 적었는데 그 일부만 표가 수록한 경우의 조회 범위. 상대 표현(`최근 3년`)의 기존 처리와 A의 차단 완화는 포함하지 않음.

## 1. 기존 동작과 문제

- 질문의 연도 범위(`2020년부터 2027년까지 월별`)가 표의 수록 범위(~2026년 7월) 밖으로 걸치면 B가 `metadata_refresh_required`로 멈췄음.
- 표의 첫 해에 전년 대비를 요청해도(`2003년 연간 전년 대비`) 기준 연도(2002년)가 표에 없어 같은 이유로 멈췄음.
- 수록된 부분은 읽을 수 있는데 사용자는 아무 결과도 받지 못함. 상대 표현은 이미 표의 최신 시점으로 맞춰 안내하고 있어 두 경우의 취급이 달랐음.

## 2. 변경

- 명시 연도는 표가 수록한 범위와 교집합으로 읽음. 안에 든 부분은 조회하고, 밖의 부분은 `missing`으로 기록함. `requested`는 사용자가 적은 연도 그대로 둠.
- 일부가 밖이면 안내 종류 `requested_period_partly_unavailable`(화면에 보임)을 붙임. 문구: `요청하신 기간 중 일부(…)가 표에 수록되어 있지 않아 조회 가능한 기간으로 자료를 조회합니다. / 조회 기간: …`. 기존 `confirmed_period_partly_unavailable`과 같이 한 번만 보임.
- 전년 대비 등 계산용 앞 구간은 표 안에서만 읽음. 기준 구간 전체가 표 밖이면 계산용 구간 없이 조회하며 멈추지 않음.
- 요청 범위 전체가 수록 범위 밖이면 기존대로 `metadata_refresh_required`로 멈춤. 사용자가 적은 연도를 다른 기간으로 바꾸지 않음(메타데이터가 오래되었을 수도 있음).
- 시작이 끝보다 늦은 범위(`2024년부터 2020년까지`)는 `invalid_period`로 먼저 막음(기존 시험이 고정한 동작).
- 조건이 없는 요청(구 A)에도 같은 규칙이 적용됨.

## 4. 알아둘 점

- 시작이 끝보다 늦은 범위는 한 표짜리 나열(`2024년과 2023년`)도 같이 `invalid_period`임. 순서 무관 읽기는 별도 결정이 필요함.
- 요청이 전부 수록 범위 밖이면 계속 멈춤. 이 경우도 안내 후 가까운 기간으로 바꿀지는 정책 결정 사항으로 남김.
