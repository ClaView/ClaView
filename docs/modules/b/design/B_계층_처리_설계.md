# B 계층 처리 설계

표 안의 분류 값이 상하위 관계(계층)를 가질 때 B가 값을 선택·확장·표시하는 방식을 정리함. 기준은 2026-10-16 코드([stages.py](../../../../modules/b/claview_b/stages.py), [graphs.py](../../../../modules/b/claview_b/graphs.py), [contracts.py](../../../../modules/b/claview_b/contracts.py))임. 표 선택(A)과 KOSIS 조회(fetch)는 범위에 포함하지 않음. 기간·주기 확정과 이름 보정(12장), 모델에 보내는 표의 축소와 요청 크기 관리(8장)를 포함함. 실측 경과는 [B 계층 처리 검증 기록](../research/B_계층_처리_검증_2026-10-13.md)을 참고함.

## 1. 결정 사항

| 항목 | 결정 |
|---|---|
| 확장 방식 | 모델은 축마다 `none` / `children` / `leaves` 중 하나를 냄. 확장은 코드가 메타의 `parent_code`·`is_leaf`로 수행함 |
| 값 자신 포함 여부 | 확장 결과에 값 자신은 포함하지 않음. "상위 + 하위"는 selection 두 개(상위 `none`, 하위 `children`)로 표현함 |
| 확장 축 수 | 한 selection에서 확장하는 축은 최대 하나임 |
| 확장 후 계열 수 상한 | 기본 30개. 초과하면 조회하지 않고 사용자 확인 요청(`needs_confirmation`)으로 멈춤 |
| 상위·하위를 함께 선택 | 오류로 보지 않음. 결과 status는 `ok`이고 `relations`에 상하위 쌍만 기록함 |
| 라벨 | 같은 이름이 한 축에서 2회 이상 나올 때만 상위 이름을 한 단계씩 앞에 붙임. 공식 이름(`dimensions[].name`)은 그대로 둠 |
| "~별" 요청의 깊이 | 단계 한정어가 없으면 최하위(`leaves`) 전체로 해석함. 예: "업권별" = 가계신용 최하위 14개 |

## 2. 입출력 계약

### 2.1 모델 출력

분해 표현이 있는 질문(3장)에서만 selection마다 `expand`를 요구함. 축 이름을 키로, 값은 `none`/`children`/`leaves`임.

```json
{"item_id": "…", "dimensions": {"objL1": "…ACC_ITEM.1000000"},
 "period": {"frequency": "Q", "start": "202001", "end": "202602"},
 "expand": {"objL1": "leaves"}}
```

### 2.2 B 결과

확장이 끝난 뒤의 `selections` 행 구조는 기존과 같음(`series_id`, `label`, `org_id`, `table_id`, `item_id`, `dimensions`, `period`, `unit`). fetch가 다시 검증하는 스키마도 `expand`가 없는 기존 형태이며, fetch 계약은 바뀌지 않음.

| 필드 | 내용 |
|---|---|
| `selections` | 확장된 계열 목록 |
| `relations` | 상하위 쌍 목록(없으면 빈 배열). 항목: `axis`, `ancestor_series_id`, `descendant_series_id`, `levels` |
| `period_notices` | 상대기간 안내(기존). 있을 때만 포함 |
| `expand_notices` | 코드가 확장 지정이나 고른 값을 바꾼 내역(6장). 있을 때만 포함 |
| `frequency_alternatives` | 질문이 주기를 말하지 않고 표에 다른 주기도 있을 때의 대안 주기 결과(12.2). 있을 때만 포함 |

`relations`는 두 계열이 항목·기간이 같고 정확히 한 축에서만 달라서, 그 축의 두 값이 조상-자손 관계일 때 기록함. 계열을 지우거나 가중하지 않으며, 누적 막대 등에서의 처리는 C(렌더) 단계가 결정함.

### 2.3 계열 수 초과 시

`status=needs_confirmation`, 이슈 코드 `selection_count_requires_confirmation`으로 B가 끝나고 `selections`는 반환하지 않음. `result`는 아래 필드를 가짐. 파이프라인은 `status != ok`이면 조회 없이 응답하며, 응답의 `confirmation`에 이 `result`가 담김.

| 필드 | 내용 |
|---|---|
| `message` | 안내 문구 |
| `selection_count` | 확장 후 누적 계열 수 |
| `limit` | 상한(`max_expanded_selections`) |
| `candidate_labels` | 후보 계열의 라벨 목록 |

## 3. 모델에 expand를 보내는 조건

- 질문에 분해 표현이 있을 때만 `expand`가 들어간 스키마와 프롬프트(`B_PROMPT`)를 보냄. 판단은 `asks_for_breakdown`이 함.
- 분해 표현: `세부`, `세분`, `하위`, `구성`, `내역`, `분해`, `나눠`, `나누어`, `쪼개`, `상세`, `모든|전체|각 + 항목|분류|업권|지역|산업|업종|품목`, 그리고 시간 단위가 아닌 "~별"(예: 업권별, 지역별).
- 시간 단위 "~별"(연, 월, 일, 주, 분기, 반기, 연도, 기간, 시기, 계절)은 분해 표현이 아님.
- 분해 표현이 없으면 `expand`가 없는 기존 스키마와 프롬프트(`B_PROMPT_PLAIN`)를 보내고, 코드가 `expand: none`을 채움.
- 이유: 실제 모델 확인에서 `expand` 스키마·프롬프트가 분해와 무관한 질문의 답에도 영향을 주었음(검증 기록 참고).

## 4. validate 처리 순서

| 순서 | 처리(함수) | 하는 일 | 알림 reason |
|---|---|---|---|
| 1 | `check_output` | 모델 출력의 스키마 준수 확인 | - |
| 2 | `normalize_model_periods`, `with_default_expand` | 기간 표기("2024-01" 등)를 표 형식으로 정리, `expand`가 없는 행에 전 축 `none` 채움 | - |
| 3 | `correct_to_named_value` | 질문의 이름과 어긋난 값을 질문이 말한 값으로 교체(12.3) | `query_names_longer_value`, `query_names_parent_value`, `query_excludes_named_value` |
| 4 | `apply_expand_guard` | 분해 표현이 없는데 `expand`가 있으면 `none`으로 낮추고 같아진 행은 병합 | `no_breakdown_wording` |
| 5 | `lower_expand_on_leaves` | 최하위 값에 지정된 `children`/`leaves`를 `none`으로 낮추고 같아진 행은 병합 | `expand_on_bottom_level_value` |
| 6 | `select_named_children` | 질문이 이름으로 말한 하위 값만 선택 | `query_names_children` |
| 7 | `promote_children_to_leaves` | "~별"이고 깊이 한정어가 없으면 `children`을 `leaves`로 올림 | `split_by_wording_all_levels` |
| 8 | `repair_unused_split` | "~별" 축에서 모델이 확장하지 않았으면 확장 | `split_axis_not_expanded` |
| 9 | `expand_selections` | `children`/`leaves`를 실제 계열로 펼침. 실패 시 1회 재시도(7장) | - |
| 10 | `canonicalize_selections` | 기간 확정·검증(`resolved_period`가 있으면 그 값을 그대로 사용), 이름·단위·라벨 채움, 중복 점검 | - |
| 11 | 계산 정의 점검 | 기여도·연쇄가중 질의는 라벨에 지표가 있는 계열만 허용 | - |
| 12 | 계열 수 점검 | 표 누적 계열 수가 상한을 넘으면 사용자 확인 요청 | - |
| 13 | `find_relations` | 상하위 쌍 기록, 결과 확정 | - |

4번은 안전장치임. 3장의 조건 때문에 정상 경로에서는 분해 표현이 없는 질문에 `expand`가 들어오지 않음. 3번은 `expand`가 `none`인 값에만 적용하므로 분해 표현이 없는 질문에서도 동작함. 기간은 이 순서 이전의 모델 호출 전(문맥 단계)에 코드가 정함(12.1).

## 5. 보정 규칙

모델이 `expand`를 지시대로 쓰지 않는 경우를 코드가 질문 표현으로 바로잡는 규칙임. 모두 `expand_notices`에 남김.

### 5.1 이름으로 말한 하위 값 선택 (`select_named_children`)

- 조건: 한 축에서 `children`/`leaves`로 확장되는 값의 바로 아래 값 중, 이름(정규화 후 2자 이상)이 질문에 나오는 것이 2개 이상임.
- 동작: 확장하지 않고 그 하위 값들만 selection으로 만듦. 모델이 같은 행을 이미 쓴 경우 중복으로 만들지 않음.
- 예: "시설자금·운전자금·특별자금 용도별로" → 총대출금의 바로 아래 6개 중 3개만 선택함.
- 이름이 하나만 나오거나 더 깊은 단계 이름만 나오면 적용하지 않음.
- 알림에 선택한 코드 목록(`selected`)을 포함함.

### 5.2 `children`을 `leaves`로 승격 (`promote_children_to_leaves`)

- 조건: 시간 단위가 아닌 "~별" 표현이 있고, 깊이 한정어(`한 단계`, `1단계`, `첫 단계`, `한 층`, `바로 아래·밑·하위`, `직접 하위`, `직하위`, `대·중·소분류`)가 없음.
- 동작: 모델이 낸 `children`을 `leaves`로 올림. 바로 아래 값이 모두 최하위면 바꾸지 않음.
- "세부", "하위"만 있고 "~별"이 없으면 승격하지 않음.

### 5.3 확장하지 않은 분해 요청 보정 (`repair_unused_split`)

모두 만족할 때만 동작함.

- 어느 행에도 `expand`가 없음(전 축 `none`).
- 질문의 "~별" 단어가 축의 공식 이름에 포함되는 축이 정확히 하나임. 앞말에 붙은 경우("수출을지역별")를 위해 단어 끝 2자 이상으로 대조함. 예: "지역" ↔ "지역코드별".
- 그 축에서 모든 행이 같은 값을 갖고, 그 값이 최하위가 아님.
- 동작: 그 값을 `leaves`로 확장함. 깊이 한정어가 있으면 `children`.
- 같은 축에서 값을 둘 이상 직접 나열했거나 최하위 값을 고른 경우, 축 이름과 단어가 맞지 않는 경우에는 건드리지 않음.

### 5.4 참고 항목 제외

- 이름이 `[참고]`로 시작하는 값(예: `[참고] 구 M2(말잔 원계열)`)은 구성 항목이 아닌 비교용 줄이므로 `children`/`leaves` 확장에서 제외함.
- 대상은 메타 전체에서 8개 값, 6개 표임. 코드로 직접 고르는 것은 막지 않음.

## 6. 알림 형식 (`expand_notices`)

| reason | requested | applied | 추가 필드 |
|---|---|---|---|
| `no_breakdown_wording` | `children`/`leaves` | `none` | - |
| `query_names_children` | `children`/`leaves` | `named_children` | `selected` |
| `split_by_wording_all_levels` | `children` | `leaves` | - |
| `split_axis_not_expanded` | `none` | `leaves`/`children` | - |
| `expand_on_bottom_level_value` | `children`/`leaves` | `none` | - |
| `query_names_longer_value`, `query_names_parent_value`, `query_excludes_named_value` | `none` | `named_value` | `selected`(바꾼 값 코드) |
| `repeated_row_dropped` | - | - | `item_id`, `dimensions`(제거한 행의 항목·분류 코드). `axis`·`code`·`requested`·`applied` 없음 |

공통 필드: `table`, `axis`, `code`(확장 대상 값), `requested`, `applied`, `reason`. 단 `repeated_row_dropped`는 `table`, `item_id`, `dimensions`, `reason`만 가짐(모델이 항목·분류·펼치기·기간이 모두 같은 행을 반복해 첫 행만 남긴 경우, 확장 검사보다 앞에서 처리). 표가 여러 개이면 표 순서대로 이어 붙임.

## 7. 재시도

- 대상 오류: `expand_target_has_no_children`(하위가 없는 값에 확장 지정), `expand_multiple_axes`(한 selection에서 두 축 확장).
- 첫 실패 시 같은 표로 모델을 한 번 더 호출함(`max_expand_retries=1`). 문맥은 다시 만들지 않고 `retry_feedback`만 추가함.
- `retry_feedback`: `error`, `message`, `previous_answer`, `expandable_values`(하위가 있는 값의 축·코드·이름).
- 재시도 후에도 실패하면 해당 오류 코드(status `error`)로 B가 끝남. 재시도 횟수는 표마다 초기화함.

## 8. 요청 크기 관리

모델에 보내는 표의 축소(8.1), 출력 상한(8.2), 요청 한도의 성격(8.3), 가지치기(8.4)로 구성함. 실측은 [검증 기록](../research/B_계층_처리_검증_2026-10-13.md) 8장에 있음.

### 8.1 모델에 보내는 표 (`model_table`)

- 모델은 저장된 표가 아니라 축소한 사본을 받음(`compact_model_context=True`). 저장된 표(확장·라벨·검증에 쓰임)는 바뀌지 않고 값 코드도 같으므로, 모델의 답을 검사하는 방식은 이전과 같음.
- 값마다 보내는 필드:

| 필드 | 내용 |
|---|---|
| `name` | 공식 이름 그대로. 질문이 이 이름을 그대로 말하면 일치함 |
| `under` | 같은 이름이 한 축에서 2회 이상 나올 때만 씀. 9장 라벨에서 값 이름을 뺀 앞부분(상위 이름을 ` > `로 이은 문자열). 가지치기 전 축 전체로 계산하므로 줄인 축에서도 같은 값이 나옴 |
| `parent_code` | 있을 때만 |
| `is_leaf` | **모든 값**에 `true`/`false`로 씀 |
| `unit` | 비어 있지 않을 때만 |

- 보내지 않는 것: `path`(상위 경로 전체)와 빈 `unit`. `path`가 큰 표 크기의 약 70%였고 `parent_code`와 `under`로 같은 정보를 전달할 수 있음.
- 프롬프트: `B_PROMPT_HEAD`가 `parent_code`와 `under`를 읽는 방법을 안내함(`compact_model_context=False`이면 `path`가 다시 전달됨).
- 효과(2026-10-16 측정): 골든 22건의 모델 문맥(`selection_context`) 합계 655,077자 → 260,576자(약 40%). CV-AB-04는 가지치기를 적용한 상태에서 30,126자 → 9,959자. 전체 348개 표를 표+스키마 크기로 비교하면 합계 8,093,888자 → 3,886,804자(약 48%)이고, 120,000자 기준을 넘는 표가 8개 → 1개(DT_404Y016, 151,454자)로 줄어듦.
- `is_leaf`를 하위가 있는 값에만 쓰면 CV-AB-03이 하위 값(3010501)을 골랐고, 모든 값에 쓰면 통과함. `under`를 빼면 다른 가지(901 등)를 골랐음. 원인은 확인하지 못했고 변형당 1회 실행 결과임(검증 기록 8.2).

### 8.2 출력 상한

- `max_b_output_tokens=6144`(이전 8192). 골든에서 가장 긴 답이 약 2,600자이고, 계열 30개(확인 없이 허용하는 최대)를 모두 나열해도 약 8,000자임.
- 상한에서 잘린 답은 `output_truncated`로 실패하며 사용하지 않음.

### 8.3 요청 한도의 성격

- HCX-007의 한도는 분당 요청 수(QPM)와 분당 토큰 수(TPM)임. TPM에는 입력 토큰에 요청한 최대 출력 토큰(`maxCompletionTokens`)을 더한 값이 계산됨(작은 핑 요청이 102토큰을 소비한 것으로 확인: 입력 약 38 + 최대 출력 64).
- 공식 문서 표(2025-07-17 기준)는 테스트/플레이그라운드 앱을 60 QPM·60,000 TPM, 서비스 앱을 180 QPM·300,000 TPM으로 적음. 현재 키의 응답 헤더는 요청 60, 토큰 60000으로 테스트 앱 값과 같음.
- 측정: 축소 전 형식의 CV-AB-04(요청 본문 147,564자)는 HTTP 429(service_code 42901, remaining_tokens 0)였고, 축소 형식으로 가지치기 없이 보낸 같은 요청(46,556자, 출력 상한 6144)은 HTTP 200이며 약 23,890토큰(약 0.38토큰/자)을 소비함.
- 해석: 429의 원인은 문자 수 자체의 한도가 아니라 분당 토큰 한도로 보임. 다만 토큰이 가득 찬 상태에서 축소 전 요청을 다시 보내 직접 확인하지는 못했음(A파트가 같은 키를 사용 중). 같은 키로 한 분 안에 여러 호출이 이어지면 작은 요청도 한도에 닿을 수 있음.
- 따라서 `max_b_context_chars=120000`은 호출 한도의 경계가 아니라 **가지치기를 시작하는 기준**으로 씀(8.4).

### 8.4 가지치기

- 발동 기준: 스키마를 포함한 **저장 형식**(축소 전) 크기 + 질의 + 2,000자가 `min(max_context_chars, max_b_context_chars)` = 120,000자를 넘으면 값이 80개를 넘는 축만 줄임. 축소한 크기로 판단하지 않음(해당 표는 348개 중 8개).
- 줄이는 순서: 질문 단어가 값 이름에 들어 있는 정도(조사가 붙은 단어는 앞부분으로 대조) → 이름의 2-gram 겹침 → 상위 경로의 2-gram 겹침 → 코드순. 남긴 값의 조상은 함께 남김.
- 가지치기 뒤에도 모델에 보내는 문맥(축소 표)과 문맥+스키마가 120,000자를 넘으면 `context_too_large`로 멈춤. 이 검사는 축소한 크기로 함.
- 줄여야 하는 표에서 질문에 `모든 항목|분류` 또는 `업권|상품|지역|산업|업종|품목별`이 있으면 `broad_scope_context_incomplete`로 멈춤.
- 크기 외의 효과: CV-AB-04·05를 가지치기 없이 보내면 0/2였음(04는 서비스·본원소득·이전소득 수지를 빼고 하위 5개를 선택, 05는 하위 13개를 더해 18행). 가지치기를 적용하면 둘 다 통과함. 가지치기가 후보를 줄여 과선택을 막는 효과도 있다는 추정을 뒷받침하지만 이 효과만 분리한 실험은 아니며 질문당 1회임.
- 그래서 가지치기 기준을 축소한 크기로 바꾸지 않음. 바꾸면 기준을 넘는 표 8개 중 7개가 가지치기 없이 나가게 되고, 그중 CV-AB-04·05의 표(DT_301Y013)에서 품질이 나빠짐을 확인함.
- 한도 120,000자는 요청 오류 경계를 측정한 값이 아니라 가지치기 기준으로서의 추정치임.

## 9. 관계와 라벨

- 상하위가 함께 선택되면 `relations`에만 기록하고 status는 `ok`로 유지함.
- 같은 축에서 같은 이름이 2회 이상 나오면 상위 이름을 한 단계씩 앞에 붙여(` > ` 구분) 같은 이름끼리 구분될 때까지만 늘림. 이름이 한 번만 나오면 그대로 둠.
- 모델에는 이 라벨을 한 문자열로 바꿔 보내지 않고, 공식 이름 `name`과 상위 이름 `under`로 나누어 보냄(8.1).
- 예: 가계신용의 `여신전문기관` 2개 → `판매신용 > 여신전문기관`, `기타금융기관 등 > 여신전문기관`. 실제 표에서 DT_200Y101 `objL1`은 113개 중 49개 라벨이 이 방식으로 길어짐.

## 11. 한계와 미확정

- 5장의 규칙은 골든 CV-AB-08·09·10·13의 실제 모델 실패에서, 12장의 규칙은 골든 07·12·16·17·19·20·21번의 실패에서 도출함. 이 질문들 밖에서 같은 효과가 나는지, 오탐이 없는지는 확인하지 못함(골든 22건의 정답 값은 바뀌지 않음을 확인).
- 5.3은 "총계와 지역별을 함께" 같은 질문에서 모델이 총계 한 줄만 냈다면 총계를 지역 값으로 바꿈. 알림은 남지만 총계는 결과에서 빠짐.
- 5.1은 일부 이름을 말하면서 전체를 원하는 질문에서 이름이 나온 값만 남김.
- `expand_notices`, `relations`, `frequency_alternatives`는 B 결과(`b_result`)에만 있고 응답(`response.notices`)에는 연결하지 않음. 응답에 노출하는 것은 `period_notices`뿐임. 노출 여부와 대안 주기를 고르는 화면·조회 흐름은 팀 결정이 필요함.
- 하위가 있는 값을 `expand` 없이 고르면 그 값 자신만 선택됨(하위는 포함되지 않음).
- 429의 원인을 분당 토큰 한도로 보는 해석은 가득 찬 토큰 한도에서 축소 전 요청을 다시 보내 직접 확인하지 못했음(8.3). A파트 작업이 같은 키 사용을 끝낸 뒤 확인할 예정임.
- 현재 키는 테스트 앱 값(60 QPM, 60,000 TPM)으로 보임. 서비스 앱(문서 기준 180 QPM, 300,000 TPM) 전환의 절차와 비용은 확인하지 못함.
- 축소 후에도 DT_404Y016은 151,454자(표+스키마)라 가지치기가 필요함. 가지치기 기준(저장 형식 크기)과 효과는 8.4에 적음.
- 축소 표의 형식(`is_leaf` 전체 표기, `under`)은 CV-AB-03 한 건의 변형 실험으로 정했음. 골든 22건이 모두 통과했으나 질문당 1회이고, 라벨이 긴 표에서 같은 효과가 나는지는 골든 밖에서 확인하지 못함.
- KOSIS 데이터 응답에서 계층 값의 조회 결과는 확인하지 않음.
- 누적 막대에서 `relations`를 이용한 중복 합산 방지는 C 단계에서 구현해야 함.

## 12. 기간·주기 확정과 이름 보정 (2026-10-13)

골든 22건 전체를 실제 모델로 돌린 뒤 실패 원인을 코드로 처리한 변경임. 실측 경과는 [검증 기록](../research/B_계층_처리_검증_2026-10-13.md) 7장에 있음.

### 12.1 기간과 주기를 코드가 정함

| 항목 | 내용 |
|---|---|
| 주기(`decide_frequency`) | 질문이 말한 주기가 우선(반기 → 분기 → 월 또는 "어느/몇/한 달" → 연간·연도별). 말한 주기가 없고 표에 주기가 하나뿐이면 그 주기. 여러 개이면 가장 긴 주기(`Y` > `H` > `Q` > `M`)를 기본으로 하고 나머지는 대안 주기로 남김 |
| 상대 기간(`resolve_relative_period`) | 기존 규칙에 위에서 정한 주기를 넘겨 계산함. 이전에는 주기를 정하지 못하면 `conditions_incomplete`로 멈추는 경우가 있었음 |
| 명시 기간(`resolve_explicit_period`) | 상대 표현 없이 연도가 적힌 질문의 기간을 질문에서 계산함. 연간은 첫·마지막 연도, 분기·월·반기는 "n분기/n월/n반기" 문구(없으면 시작 01, 끝 분기 04·월 12·반기 02). 전월·전년 대비 표현은 필요한 기간만큼 시작을 앞당김. 표 수록 범위를 벗어나면 `validate_period`와 같은 오류 |
| 모델이 쓴 기간 | `resolved_period`가 있으면 쓰지 않음(상대 기간과 명시 기간 모두). 연도를 못 찾았거나 정한 주기가 표에 없으면 `resolved_period`가 없고, 모델의 기간을 기존 `validate_period`가 대조함 |
| 모델 문맥의 `resolved_period` | **상대 기간 질문에서만** 값을 채우고, 연도를 적은 질문은 `null`. 상태에는 계산한 기간을 유지함. 근거: CV-AB-04에서 값을 보여주면 3회 모두 14개를 골라 틀렸고 `null`이면 3회 모두 5개로 맞았음. 원인은 확인하지 못함 |
| 기간 표기 정리(`normalize_model_periods`) | 모델이 쓴 월·분기·반기 값의 "2024-01", "2024.1", "2024/1"을 "202401"로 바꿈. 이미 표 형식인 값, 연간 값, 해석할 수 없는 값은 그대로 둠 |

### 12.2 대안 주기 (`frequency_alternatives`)

- 질문이 주기를 말하지 않고 표에 주기가 여러 개이면, 기본 주기가 아닌 주기마다 같은 질문의 기간을 모델 호출 없이 계산해 둠.
- 그 주기가 표에 없거나 그 기간을 보여줄 수 없으면 그 주기는 대안으로 내지 않음.
- `b_result.frequency_alternatives` 항목: `table`, `frequency`, `period`, `selections`(같은 계열에 대안 기간만 바꾼 목록). 질문이 주기를 말하면 만들지 않음.
- 응답·fetch에는 연결하지 않았고, 대안을 고르는 화면과 대안 주기 조회 흐름은 구현하지 않음. 대안 주기의 KOSIS 조회 결과는 확인하지 않음.

### 12.3 이름으로 말한 값으로 바로잡기 (`correct_to_named_value`)

모델이 이름이 비슷한 다른 값을 같은 입력에서 반복해 고르는 경우를 질문의 이름으로 바로잡음. `expand`가 `none`인 축의 값에만 적용하고, 값마다 아래 순서로 처음 맞는 규칙을 씀. 같아진 행은 병합하고 알림에 남김.

| 규칙 | 조건 | 예 |
|---|---|---|
| 긴 이름(`named_longer_value`) | 고른 이름이 다른 한 값 이름의 일부이고, 그 긴 이름(3자 이상, `[참고]` 제외)이 질문에 그대로 있으며, 짧은 이름은 긴 이름을 뺀 질문에 따로 나오지 않음 | 대외금융자산 → 순대외금융자산 (CV-AB-12) |
| 상위 항목(`named_parent_value`) | 고른 값의 조상 중 이름(3자 이상)이 질문에 나오고, 고른 이름이 그 이름으로 시작하며, 고른 이름 전체는 질문에 없음. 질문이 그 이름을 포함한 더 긴 값을 직접 말하면 적용하지 않음. 가장 가까운 조상을 씀 | 원재료국내출하 → 원재료 (CV-AB-21) |
| 제외 표현(`excluded_named_value`) | 고른 이름이 "~이외"인데 그 이름과 앞부분이 질문에 없고, "X를 뺀·빼고·제외한" 표현이 가리키는 "X이외" 값(이름 5자 이상)이 정확히 하나 | 식료품이외 → 신선식품이외 (CV-AB-17) |

- 근거: 한 번 더 모델에게 확인시키는 호출은 같은 오답을 반복해 효과가 없었음(검증 기록 7장).
- 검증 범위: 골든 22건의 정답 값을 넣어도 바뀌는 값이 0건임을 시험으로 확인함. 이름이 조금이라도 겹치면 바꾸는 넓은 규칙은 골든 05·17번을 바꿔 쓰지 않았음. 세 규칙은 실패한 질문에서 도출했고 다른 질문에서의 효과는 확인하지 못함.

### 12.4 최하위 값의 펼침 낮춤 (`lower_expand_on_leaves`)

- 하위가 없는 값에 `children`/`leaves`가 지정되면 `none`으로 낮춰 그 값 자신을 선택함. 같아진 행은 병합하되 모델이 직접 쓴 중복 행은 합치지 않음. 알림 reason은 `expand_on_bottom_level_value`.
- 이전에는 `expand_target_has_no_children`으로 재시도·오류가 될 수 있었음(CV-AB-07). 최하위 값의 펼침은 재시도하지 않고 낮춤. 7장의 재시도는 `expand_multiple_axes`와, 낮춤 이후에도 남는 `expand_target_has_no_children`에 해당함.
